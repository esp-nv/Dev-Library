## 1. КАКВО Е ИНДЕКС И КАК РАБОТИ B-TREE СТРУКТУРАТА?

**Индексът** е допълнителна структура от данни на диска (подобна на азбучния указател в края на дебел учебник), която позволява на базата да намери конкретен ред, **без да чете цялата таблица от начало до край**.

Повечето SQL бази (MS SQL Server, PostgreSQL, MySQL) използват **B+ Tree (Balanced Tree)** структура:
* При таблица с **10 000 000 реда**, търсенето без индекс проверява всички 10 милиона реда (O(n)).
* С B+ Tree индекс базата прави едва **3 или 4 скока** (от корена `Root` ➔ междинни възли `Intermediate` ➔ листа `Leaf`), за да стигне до точния ред за под **1 милисекунда** (\(O(\log n)\)).

```text
                       [ Root Node: 1..10,000,000 ]
                         /                       \
            [ 1..5,000,000 ]                 [ 5,000,001..10,000,000 ]
               /         \                        /             \
     [ Leaf: 1..100 ] [ Leaf: 101..200 ] ... [ Leaf: 5M..5.1M ] [ Leaf: ... ]
```

### Главният търговски компромис (Trade-off):
* **Ускорява `SELECT` (`WHERE`, `JOIN`, `ORDER BY`):** Четенето става стотици пъти по-бързо.
* **Забавя `INSERT`, `UPDATE` и `DELETE` + заема място на диска:** При всеки запис или промяна базата трябва да обнови не само таблицата, но и всички нейни индекси.

## 2. CLUSTERED СРЕЩУ NON-CLUSTERED ИНДЕКС (КЛЮЧОВА РАЗЛИКА)

| Критерий | Clustered Index (Клъстерен индекс) | Non-Clustered Index (Неклъстерен индекс) |
| :--- | :--- | :--- |
| **Къде са реалните данни?** | **Самата таблица Е индексът.** Листата (`Leaf Nodes`) съдържат целия ред (всички колони). | Отделна структура на диска. Листата съдържат само индексираната колона + **указател (`Id`)** към реда. |
| **Физическа подредба** | Подрежда редовете физически на диска по ключа (като страниците в книга). | Не променя подредбата на таблицата (като съдържанието в края на книгата). |
| **Колко броя може да има?** | **Само 1 на таблица** *(една таблица не може да е подредена едновременно по `Id` и по `Email`)*. | **Много на таблица** (до 999 в MS SQL Server). |
| **Кога се създава?** | Автоматично върху **`PRIMARY KEY`** (освен ако не укажеш друго). | Създава се ръчно от теб върху колони за търсене (`Email`, `UserId`, `OrderDate`). |

## 3. СПЕЦИАЛИЗИРАНИ ИНДЕКСИ: COMPOSITE, COVERING (INCLUDE) И FILTERED

```sql
-- ============================================================
-- 1. СТАНДАРТЕН NON-CLUSTERED И UNIQUE ИНДЕКС
-- ============================================================
CREATE INDEX IX_Orders_CustomerId ON Orders(CustomerId);
CREATE UNIQUE INDEX UX_Users_Email ON Users(Email);

-- ============================================================
-- 2. COMPOSITE INDEX (СЪСТАВЕН ИНДЕКС ВЪРХУ 2+ КОЛОНИ)
-- ============================================================
-- Важно: Редът на колоните има огромно значение (Правило на левия префикс)!
CREATE INDEX IX_Orders_Status_OrderDate ON Orders(Status, OrderDate DESC);

-- ============================================================
-- 3. COVERING INDEX С INCLUDE (ЕЛИМИНИРА KEY LOOKUP!)
-- ============================================================
-- Заявката търси по CustomerId, но иска да покаже и TotalAmount и Status.
-- С INCLUDE ги слагаме директно в листата на индекса -> базата изобщо не ходи до таблицата!
CREATE INDEX IX_Orders_CustomerId_Covering 
ON Orders(CustomerId) 
INCLUDE (TotalAmount, Status);

-- ============================================================
-- 4. FILTERED INDEX (ЧАСТИЧЕН ИНДЕКС - ПЕСТИ МНОГО МЯСТО)
-- ============================================================
-- Индексираме само неплатените поръчки (5% от таблицата), защото само тях следим постоянно:
CREATE INDEX IX_Orders_Unpaid 
ON Orders(OrderDate) 
WHERE IsPaid = 0;
```

## 4. ЧЕТЕНЕ НА EXECUTION PLAN: SEEK СРЕЩУ SCAN И KEY LOOKUP

В **SSMS** (натисни `Ctrl + M` за *Include Actual Execution Plan*) или в **PostgreSQL** (`EXPLAIN ANALYZE SELECT ...`) гледаш тези 4 основни операции:

| Операция в Execution Plan | Какво означава? | Оценка |
| :--- | :--- | :--- |
| **`Index Seek`** | Базата скача директно по B-Tree клоните до точните редове. | **Отлично** (най-бързото възможно). |
| **`Index Scan`** | Базата чете целия индекс от край до край (по-леко от Table Scan, но пак чете всичко). | **Средно** (приемливо при малки таблици). |
| **`Table Scan` / `Clustered Index Scan`** | Базата чете **всеки един ред** в цялата таблица от начало до край. | **Лошо** (ако таблицата има милиони редове). |
| **`Key Lookup` (RID Lookup)** | Намира `Id`-то през Non-Clustered индекс, но за всяка намерена позиция скача обратно в основната таблица, за да вземе останалите колони. | **Внимание** (ако е за хиляди редове, бави; лекува се с `INCLUDE` колони). |

```sql
-- Проверка на реалния план и четенията от диска в MS SQL Server:
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT Id, TotalAmount, Status
FROM Orders
WHERE CustomerId = 42;
```

## 5. ЧЕСТИ ГРЕШКИ, КАПАНИ И КАК ДА ГИ ИЗБЕГНЕМ

### Грешка 1: Нарушаване на „Правилото на левия префикс“ при съставен индекс
* **Какво се случва:** Създаваш индекс `CREATE INDEX IX_Users_LastName_FirstName ON Users(LastName, FirstName)`. Ако търсиш `WHERE LastName = N'Иванов'`, индексът работи. Ако търсиш `WHERE LastName = N'Иванов' AND FirstName = N'Георги'`, работи. Но ако търсиш **само** `WHERE FirstName = N'Георги'`, индексът е **напълно безполезен** (все едно да търсиш в телефонен указател само по малко име, когато той е подреден по фамилия!).
* **Как да избегнеш:** В съставен индекс винаги слагай най-често филтрираната (и най-селективната) колона **на първо място вляво**.

### Грешка 2: Създаване на 15–20 индекса на една таблица („Over-Indexing“)
* **Какво се случва:** Слагаш индекс на всяка колона за всеки случай. При всяко `INSERT` или `UPDATE` базата трябва да преподреди 20 B-Tree дървета на диска, което прави записа 10 пъти по-бавен и удвоява размера на бекъпите.
* **Как да избегнеш:** Индексирай само `Primary Keys`, `Foreign Keys`, колоните в чести `WHERE` / `ORDER BY` клаузи и премахвай неизползваните индекси.

### Грешка 3: Индексиране на колона с ниска уникалност (Low Cardinality), като `Gender` или `IsActive`
* **Какво се случва:** Слагаш обикновен индекс върху колона `IsActive` (`0` или `1`), където 95% от редовете са `1`. Когато напишеш `WHERE IsActive = 1`, оптимизаторът **игнорира индекса** и прави `Table Scan`, защото е по-евтино да прочете таблицата наведнъж, отколкото да прави милион `Key Lookup` скока.
* **Как да избегнеш:** Не слагай обикновен индекс на булеви флагове. Ако ти трябват само редките записи (`IsActive = 0`, които са 2%), направи **Filtered Index** (`WHERE IsActive = 0`).

### Грешка 4: Писане на `SELECT *` вместо конкретни колони
* **Какво се случва:** Имаш перфектен Covering индекс върху `(CustomerId) INCLUDE (TotalAmount)`, но в кода пишеш `SELECT * FROM Orders WHERE CustomerId = 42`. Заради `*` базата е принудена да прави скъп `Key Lookup` до основната таблица, за да вземе и останалите 15 колони.
* **Как да избегнеш:** Винаги изброявай в `SELECT` само колоните, които реално трябват на приложението.
