## 1. КАКВО Е ТРАНЗАКЦИЯ И ACID ПРИНЦИПИТЕ

**Транзакцията** е логическа единица работа, съставена от една или повече SQL команди, които трябва да се изпълнят **всички заедно успешно, или нито една от тях** („All or Nothing“).

Класически пример е банков превод на 500 лв. от Сметка А към Сметка Б:
1. Изваждаме 500 лв. от Сметка А (`UPDATE Accounts SET Balance = Balance - 500 WHERE Id = 1`).
2. Добавяме 500 лв. към Сметка Б (`UPDATE Accounts SET Balance = Balance + 500 WHERE Id = 2`).
Ако между стъпка 1 и стъпка 2 спре токът, транзакцията връща Сметка А в началното състояние (**Rollback**), за да не изчезнат парите.

| Буква | Принцип | Какво гарантира? | Как базата го постига под капака? |
| :--- | :--- | :--- | :--- |
| **A** | **Atomicity (Атомарност)** | Всичко или нищо — при грешка всички промени се отменят (`ROLLBACK`). | Чрез транзакционния лог (**WAL / Transaction Log**). |
| **C** | **Consistency (Консистентност)** | Базата преминава от едно валидно състояние в друго (спазват се всички `CHECK`, `PK`, `FK`). | Чрез Constraints и валидации преди `COMMIT`. |
| **I** | **Isolation (Изолация)** | Едновременните транзакции на 1000 потребители не си пречат и не виждат недовършени данни. | Чрез заключвания (**Locks**) или версии на редовете (**MVCC / Row Versioning**). |
| **D** | **Durability (Трайност)** | След `COMMIT` данните са записани трайно и не се губят дори при срив на сървъра. | Записва промените първо във физическия лог файл на диска. |

## 2. СИНТАКСИС НА ТРАНЗАКЦИИТЕ В SQL И C#

### А. В MS SQL Server (T-SQL) с `TRY...CATCH` и `XACT_ABORT`
```sql
-- ============================================================
-- СИГУРНА ТРАНЗАКЦИЯ В MS SQL SERVER
-- ============================================================
CREATE PROCEDURE usp_TransferMoney
    @FromAccountId INT,
    @ToAccountId INT,
    @Amount DECIMAL(18, 2)
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON; -- Автоматично отменя транзакцията при тежка грешка!

    BEGIN TRY
        BEGIN TRANSACTION;

            -- 1. Теглим от изпращача (с проверка за наличност)
            UPDATE Accounts
            SET Balance = Balance - @Amount
            WHERE Id = @FromAccountId AND Balance >= @Amount;

            IF @@ROWCOUNT = 0
                THROW 50001, N'Недостатъчна наличност или невалидна сметка!', 1;

            -- 2. Превеждаме на получателя
            UPDATE Accounts
            SET Balance = Balance + @Amount
            WHERE Id = @ToAccountId;

            IF @@ROWCOUNT = 0
                THROW 50002, N'Сметката на получателя не съществува!', 1;

        COMMIT TRANSACTION; -- Всичко е наред -> потвърждаваме окончателно!
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION; -- Връщаме всичко назад при каквато и да е грешка!
        THROW; -- Препращаме грешката нагоре към C# приложението
    END CATCH
END;
```

### Б. В PostgreSQL (`BEGIN; ... COMMIT;`) и в C# (`EF Core`)
```csharp
// ============================================================
// УПРАВЛЕНИЕ НА ТРАНЗАКЦИЯ В C# (EF CORE)
// ============================================================
await using var transaction = await _db.Database.BeginTransactionAsync();
try
{
    var sender = await _db.Accounts.FindAsync(fromId);
    var receiver = await _db.Accounts.FindAsync(toId);

    sender!.Balance -= amount;
    receiver!.Balance += amount;

    await _db.SaveChangesAsync();
    await transaction.CommitAsync(); // Потвърждава двете промени заедно
}
catch
{
    await transaction.RollbackAsync(); // Отменя всичко при грешка
    throw;
}
```

## 3. ПРОБЛЕМИ ПРИ ПАРАЛЕЛЕН ДОСТЪП

Когато двама потребители четат и пишат върху едни и същи данни едновременно, могат да възникнат 3 аномалии:

1. **Dirty Read (Мръсно четене):** Транзакция А променя цена от 100 лв. на 50 лв., но **още не е направила `COMMIT`**. Транзакция Б прочита 50 лв., но след секунда Транзакция А прави `ROLLBACK` заради грешка. Транзакция Б е работила с несъществуваща цена!
2. **Non-Repeatable Read (Неповтаряемо четене):** Транзакция А прочита наличност `5 бр.`. Преди Транзакция А да приключи, Транзакция Б купува 2 бр. и прави `COMMIT`. Когато Транзакция А провери същия ред втори път в същата транзакция, вижда `3 бр.` (редът се е променил).
3. **Phantom Read (Фантомно четене):** Транзакция А брои поръчките за деня (`COUNT(*) = 10`). Транзакция Б вмъква нова поръчка (`INSERT`) и прави `COMMIT`. При второ преброяване в същата транзакция Транзакция А вижда `11` реда (появил се е нов ред „фантом“).

## 4. НИВА НА ИЗОЛАЦИЯ (ISOLATION LEVELS) И OPTIMISTIC CONCURRENCY

Колкото по-високо е нивото на изолация, толкова по-сигурни са данните, но толкова по-бавно работи базата заради повече заключвания:

| Ниво на изолация | Dirty Read | Non-Repeatable Read | Phantom Read | Как работи и кога се ползва? |
| :--- | :--- | :--- | :--- | :--- |
| **`READ UNCOMMITTED`** *(или `WITH (NOLOCK)`)* | Възможно | Възможно | Възможно | Чете без заключвания (включително недовършени данни). Само за груби статистики/логове. |
| **`READ COMMITTED`** *(По подразбиране в MS SQL & Postgres)* | **Защитено** | Възможно | Възможно | Чете само потвърдени (`COMMIT`) данни. Балансиран стандарт за 90% от уеб приложенията. |
| **`REPEATABLE READ`** *(По подразбиране в MySQL InnoDB)* | **Защитено** | **Защитено** | Възможно *(в MS SQL)* | Заключва прочетените редове до края на транзакцията, за да не ги промени друг. |
| **`SERIALIZABLE`** | **Защитено** | **Защитено** | **Защитено** | Най-строгото ниво — изпълнява транзакциите все едно са една след друга. Много бавно (чести Deadlocks). |
| **`SNAPSHOT` / `READ COMMITTED SNAPSHOT (RCSI)`** | **Защитено** | **Защитено** | **Защитено** | **Златният стандарт:** Използва версии на редовете (MVCC) в `tempdb` — четящите не блокират пишещите и пишещите не блокират четящите! |

## 5. DEADLOCK (ВЗАИМНО БЛОКИРАНЕ) — КАК ВЪЗНИКВА И КАК ДА ГО ИЗБЕГНЕМ

**Deadlock** настъпва, когато две транзакции се чакат взаимно до безкрай:
* **Транзакция 1** заключва **Ред А** и иска да заключи **Ред Б**.
* В същата милисекунда **Транзакция 2** заключва **Ред Б** и иска да заключи **Ред А**.
* Базата засича цикъла след няколко секунди, убива едната транзакция (*Deadlock Victim — Error 1205*) и прави `ROLLBACK` на нея, за да продължи другата.

### 4 правила за предотвратяване на Deadlocks:
1. **Винаги достъпвай таблиците и редовете в един и същи ред:** Ако Транзакция 1 и Транзакция 2 винаги обновяват първо `Orders`, а после `OrderItems` (или сметките по нарастващ `Id`), взаимното блокиране е невъзможно!
2. **Дръж транзакциите максимално кратки:** Никога не прави HTTP заявки към външни API-та, изпращане на имейли или тежки сметки в C# **вътре** в отворена SQL транзакция.
3. **Добави липсващите индекси:** Без индекс една `UPDATE` заявка заключва **цялата таблица** вместо 1 единствен ред, което увеличава риска от Deadlock стократно.
4. **Използвай Optimistic Concurrency (`ROWVERSION` / `Timestamp`):** Вместо да държиш реда заключен, слагаш колона `RowVersion` — при запис базата проверява дали версията не е променена междувременно.

## 6. ЧЕСТИ ГРЕШКИ, КАПАНИ И КАК ДА ГИ ИЗБЕГНЕМ

### Грешка 1: Забравена отворена транзакция (Липсващ `COMMIT` или `ROLLBACK`)
* **Какво се случва:** Пускаш ръчно `BEGIN TRANSACTION; UPDATE Users SET ...` в SSMS, за да тестваш нещо, и забравяш да напишеш `COMMIT` или `ROLLBACK`. Таблицата `Users` остава заключена и целият уеб сайт на фирмата увисва, докато не затвориш прозореца!
* **Как да избегнеш:** Никога не оставяй незатворена транзакция в продукционна среда и винаги ползвай шаблона `BEGIN TRY ... COMMIT ... BEGIN CATCH ... ROLLBACK`.

### Грешка 2: Злоупотреба с `WITH (NOLOCK)` навсякъде
* **Какво се случва:** Някои разработчици слагат `WITH (NOLOCK)` на всяка таблица, мислейки, че така заявката става „турбо бърза“. Резултатът: при преместване на страници (Page Split) заявката може да прочете един и същи ред **два пъти** или изобщо да **пропусне** съществуващ ред — фатално за финансови отчети!
* **Как да избегнеш:** Вместо `NOLOCK`, включи на ниво база данни **`READ_COMMITTED_SNAPSHOT ON`** — получаваш същата скорост без блокиране, но с 100% точни данни:
  ```sql
  ALTER DATABASE ShopDb SET READ_COMMITTED_SNAPSHOT ON;
  ```

### Грешка 3: Липса на Retry логика в C# при Deadlock
* **Какво се случва:** Дори в най-добре написаните системи понякога се случва рядък Deadlock (Error 1205). Ако C# кодът не го прихване, потребителят вижда екран с грешка `500 Internal Server Error`.
* **Как да избегнеш:** В EF Core включи вградения `EnableRetryOnFailure()` при конфигуриране на `UseSqlServer(...)` / `UseNpgsql(...)`, за да повтори автоматично транзакцията след 100 ms:
  ```csharp
  builder.Services.AddDbContext<AppDbContext>(options =>
      options.UseSqlServer(connString, sqlOptions =>
          sqlOptions.EnableRetryOnFailure(maxRetryCount: 3)));
  ```


### Грешка 3: Липса на Retry логика в C# при Deadlock
* **Какво се случва:** Дори в най-добре написаните системи понякога се случва рядък Deadlock (Error 1205). Ако C# кодът не го прихване, потребителят вижда екран с грешка `500 Internal Server Error`.
