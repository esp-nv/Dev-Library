## 1. КАКВО Е НОРМАЛИЗАЦИЯ И КАКВИ АНОМАЛИИ РЕШАВА?

**Нормализацията** е процес на разделяне на една огромна, хаотична таблица на по-малки, логически свързани таблици (`Primary Key` ➔ `Foreign Key`). Ако държиш всички данни в една таблица, възникват **3 фатални аномалии**:

1. **Insert Anomaly (Аномалия при вмъкване):** Не можеш да добавиш нов курс в университета, докато поне един студент не се запише в него, защото курсът няма собствена таблица.
2. **Update Anomaly (Аномалия при промяна):** Клиентът сменя адреса си, но адресът му е записан в 50 стари поръчки. Ако обновиш само 49 от тях, базата вече има противоречиви данни.
3. **Delete Anomaly (Аномалия при изтриване):** Изтриваш единствената поръчка на клиент и заедно с нея неволно изтриваш и самия клиент, телефона и имейла му!

## 2. ПЪРВА НОРМАЛНА ФОРМА (1NF) — АТОМАРНИ СТОЙНОСТИ

**Правило на 1NF:**
* Всяка клетка в таблицата трябва да съдържа **само една единична (атомарна) стойност** — забранени са списъци, разделени със запетая (`"C#, SQL, Git"`), или повтарящи се колони (`Phone1`, `Phone2`, `Phone3`).
* Всеки ред трябва да има уникален идентификатор (`Primary Key`).

```sql
-- ============================================================
-- ПРЕДИ 1NF (ГРЕШНО: списък в една колона!)
-- ============================================================
-- | StudentId | Name | Courses          |
-- | 1         | Иван | C#, SQL, Docker  |  <-- Не можеш лесно да търсиш или броиш!

-- ============================================================
-- СЛЕД 1NF (ПРАВИЛНО: отделен ред за всяка стойност / отделна таблица)
-- ============================================================
CREATE TABLE Students (
    Id INT IDENTITY(1,1) PRIMARY KEY,
    FullName NVARCHAR(100) NOT NULL
);

CREATE TABLE StudentSkills (
    Id INT IDENTITY(1,1) PRIMARY KEY,
    StudentId INT NOT NULL REFERENCES Students(Id),
    SkillName NVARCHAR(50) NOT NULL
);
```

## 3. ВТОРА НОРМАЛНА ФОРМА (2NF) — ПРЕМАХВАНЕ НА ЧАСТИЧНА ЗАВИСИМОСТ

**Правило на 2NF:**
* Таблицата вече е в **1NF**.
* Важи при таблици със **съставен първичен ключ (`Composite Primary Key`)**: всяка неключова колона трябва да зависи от **целия** ключ, а не само от едната му част.

```sql
-- ============================================================
-- ПРЕДИ 2NF (ГРЕШНО: ключът е (OrderId, ProductId), но ProductName зависи само от ProductId!)
-- ============================================================
-- | OrderId | ProductId | ProductName | Quantity |
-- | 100     | 5         | Лаптоп Dell | 2        |  <-- ProductName се повтаря във всяка поръчка!

-- ============================================================
-- СЛЕД 2NF (ПРАВИЛНО: изнасяме ProductName в собствена таблица Products)
-- ============================================================
CREATE TABLE Products (
    Id INT IDENTITY(1,1) PRIMARY KEY,
    Name NVARCHAR(100) NOT NULL
);

CREATE TABLE OrderItems (
    OrderId INT NOT NULL,
    ProductId INT NOT NULL REFERENCES Products(Id),
    Quantity INT NOT NULL,
    PRIMARY KEY (OrderId, ProductId) -- Тук Quantity зависи И от поръчката, И от продукта!
);
```

## 4. ТРЕТА НОРМАЛНА ФОРМА (3NF) — ПРЕМАХВАНЕ НА ТРАНЗИТИВНА ЗАВИСИМОСТ

**Правило на 3NF (Златният стандарт на работа):**
* Таблицата вече е в **2NF**.
* Няма **транзитивна зависимост** — неключова колона не бива да зависи от друга неключова колона (*„Всяка колона зависи от ключа, целия ключ и нищо друго освен ключа“*).

```sql
-- ============================================================
-- ПРЕДИ 3NF (ГРЕШНО: CityName зависи от PostalCode, а не директно от User.Id!)
-- ============================================================
-- | UserId | Name  | PostalCode | CityName |
-- | 1      | Елена | 1000       | София    |  <-- Ако смениш името на града, сменяш хиляди редове!

-- ============================================================
-- СЛЕД 3NF (ПРАВИЛНО: градовете отиват в отделна таблица Cities)
-- ============================================================
CREATE TABLE Cities (
    PostalCode VARCHAR(10) PRIMARY KEY,
    CityName NVARCHAR(100) NOT NULL
);

CREATE TABLE Users (
    Id INT IDENTITY(1,1) PRIMARY KEY,
    FullName NVARCHAR(100) NOT NULL,
    PostalCode VARCHAR(10) NOT NULL REFERENCES Cities(PostalCode)
);
```

## 5. ДЕНОРМАЛИЗАЦИЯ — КОГА УМИШЛЕНО НАРУШАВАМЕ 3NF?

В реалния бизнес има случаи, в които **умишлено дублираме данни (Денормализация)** по две причини:

1. **Историческа точност (Snapshot на данни):**
   * В таблица `OrderItems` **задължително** пазим колона `UnitPrice` (цената на продукта в момента на покупката), въпреки че в таблица `Products` вече има колона `CurrentPrice`. Ако утре продуктът поскъпне, старите фактури не бива да се променят!
2. **Висока скорост при четене (Избягване на тежки `JOIN`-ове):**
   * Ако имаш онлайн магазин с 10 милиона поръчки и на профила на потребителя показваш „Общ брой поръчки“ и „Общо похарчена сума“, вместо при всяко зареждане да правиш `SELECT COUNT(*), SUM(Total) FROM Orders WHERE UserId = @id`, можеш да пазиш готови колони `OrdersCount` и `TotalSpent` директно в таблица `Users`.

## 6. ЧЕСТИ ГРЕШКИ И КАПАНИ ПРИ ПРОЕКТИРАНЕ

### Грешка 1: Пазене на актуална цена само в `Products` без копие в `OrderItems`
* **Какво се случва:** Увеличаваш цената на лаптоп от 1500 лв. на 1700 лв. и всички стари поръчки в системата започват да показват, че клиентите дължат още 200 лв.
* **Как да избегнеш:** Винаги записвай цената и данъчната ставка в момента на сделката вътре в `OrderItems`.

### Грешка 2: Излишно пазене на изчислими стойности (напр. `Age` вместо `BirthDate`)
* **Какво се случва:** Записваш колона `Age INT` в таблица `Users`. След една година всички възрасти в базата ти са грешни!
* **Как да избегнеш:** Пази само факта, който не се променя (`BirthDate DATE`), а възрастта изчислявай в C# или в SQL заявката.

### Грешка 3: Свръх-нормализация (Over-normalization до 5NF)
* **Какво се случва:** Разцепваш един потребител на 12 малки таблици (отделна таблица за имена, отделна за улици, отделна за номера на блокове), което прави всяка елементарна заявка да изисква 10 `JOIN`-а и убива производителността.
* **Как да избегнеш:** В практиката **3NF** (плюс целенасочена денормализация за исторически цени и кеширани броячи) е напълно достатъчна за 99% от системите.
