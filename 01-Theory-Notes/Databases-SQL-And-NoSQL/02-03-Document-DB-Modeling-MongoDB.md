# 02-03. Особености при моделиране в Document БД (MongoDB)

**Цел:** Как да проектираме данни без таблици и без `JOIN` — кога да вграждаме данните вътре в документа (**Embedding**), кога да ги разделяме с връзки (**Referencing**) и как да избегнем капаните с лимита от 16 MB.

## 1. ЗЛАТНОТО ПРАВИЛО НА MONGODB: ДАННИТЕ, КОИТО СЕ ЧЕТАТ ЗАЕДНО, ЖИВЕЯТ ЗАЕДНО

В SQL мислим: *„Как да разделя данните в отделни таблици, за да няма дублиране?“*.  
В MongoDB мислим: ***„Как моето приложение ще чете и показва тези данни на екрана с ЕДНА единствена заявка?“***.

| Критерий | Embedding (Вграждане в документа) | Referencing (Връзка чрез `_id`) |
| :--- | :--- | :--- |
| **Тип връзка** | `1:1` или `1:Few` (1 към няколко — напр. 1 поръчка с 5 продукта). | `1:Many` (огромен брой — напр. 1 статия с 50 000 коментара) или `Many:Many`. |
| **Скорост на четене** | **Светкавична** (1 четене от диска връща целия обект). | По-бавна (изисква 2 заявки или `$lookup`, което е аналог на `JOIN`). |
| **Атомарност** | Промяната на целия документ е **100% атомарна** в една операция. | Промяната на 2 колекции изисква многодокументна транзакция. |
| **Ограничение** | Един документ в MongoDB не може да надвишава **16 MB**. | Няма лимит за общия брой свързани документи. |

## 2. EMBEDDING (ВГРАЖДАНЕ / ДЕНОРМАЛИЗАЦИЯ) — КОГА И КАК?

Използвай **Embedding**, когато вложените обекти принадлежат само на родителя и са ограничен брой (напр. адреси на потребител или редове в една поръчка).

```json
// ============================================================
// EMBEDDING: ЕДИН ДОКУМЕНТ В КОЛЕКЦИЯ "orders"
// ============================================================
{
  "_id": "6730a1b2c3d4e5f600112233",
  "orderNumber": "ORD-2026-089",
  "createdAt": "2026-11-08T10:30:00Z",
  "shippingAddress": {
    "city": "Видин",
    "street": "ул. Цар Симеон Велики 15",
    "postalCode": "3700"
  },
  "items": [
    { "productName": "Монитор Dell 27", "quantity": 1, "unitPrice": 549.00 },
    { "productName": "HDMI Кабел", "quantity": 2, "unitPrice": 15.00 }
  ]
}
```

```csharp
// ============================================================
// C# МОДЕЛ ЗА ВГРАДЕНИЯ ДОКУМЕНТ (БЕЗ ОТДЕЛНИ ТАБЛИЦИ!)
// ============================================================
public class OrderDocument
{
    public string Id { get; set; } = null!;
    public string OrderNumber { get; set; } = null!;
    public AddressSubDoc ShippingAddress { get; set; } = null!;
    public List<OrderItemSubDoc> Items { get; set; } = new();
}

public record AddressSubDoc(string City, string Street, string PostalCode);
public record OrderItemSubDoc(string ProductName, int Quantity, decimal UnitPrice);
```

## 3. REFERENCING (РЕФЕРИРАНЕ / НОРМАЛИЗАЦИЯ) — КОГА И КАК?

Използвай **Referencing**, когато дъщерните записи могат да растат до безкрайност (напр. логове, коментари под популярно видео, сензорни данни) или се споделят между много обекти.

```json
// ============================================================
// REFERENCING: ДВЕ ОТДЕЛНИ КОЛЕКЦИИ ("posts" И "comments")
// ============================================================
// Колекция "posts":
{
  "_id": "post_101",
  "title": "Как работят индексите в MongoDB?",
  "author": "Елена Петрова"
}

// Колекция "comments" (всеки коментар пази postId):
{
  "_id": "comm_9981",
  "postId": "post_101",
  "user": "Георги",
  "text": "Много ясно обяснено!",
  "createdAt": "2026-11-08T11:00:00Z"
}
```

## 4. ХИБРИДЕН МОДЕЛ (EXTENDED REFERENCE PATTERN) — НАЙ-ЧЕСТИЯТ В ПРАКТИКАТА

В реалните проекти не избираме крайности, а вграждаме **само 2–3 най-често показвани полета** от свързания обект, за да не правим излишни заявки:

```json
// В колекция "orders" пазим userId (за връзка), НО вграждаме името и имейла,
// защото на екрана "Списък с поръчки" винаги показваме кой е клиентът!
{
  "_id": "6730a1b2c3d4e5f600112299",
  "totalPrice": 579.00,
  "customer": {
    "userId": "user_55",
    "fullName": "Елена Петрова",
    "email": "elena@example.com"
  }
}
```

## 5. ЧЕСТИ ГРЕШКИ, КАПАНИ И КАК ДА ГИ ИЗБЕГНЕМ

### Грешка 1: Безкрайно растящи масиви (Unbounded Arrays)
* **Какво се случва:** Правиш колекция `users` и вътре в документа на всеки потребител слагаш масив `"loginHistory": [ ... ]`, в който добавяш нов елемент при всяко влизане. След 2 години документът става огромен, премества се постоянно на диска и накрая удря лимита от **16 MB**, при което потребителят изобщо не може да се логне!
* **Как да избегнеш:** Никога не вграждай масив, който расте неограничено във времето. Изнасяй логовете, коментарите и историята в отделна колекция (`login_logs` с `userId`).

### Грешка 2: Проектиране на MongoDB като SQL (10 колекции с `$lookup`)
* **Какво се случва:** Разделяш една поръчка в 5 колекции (`orders`, `order_items`, `addresses`, `payments`, `statuses`) и после правиш тежки `$lookup` заявки (еквивалента на `JOIN`). MongoDB не е оптимизирана за много `$lookup`-и и става много по-бавна от PostgreSQL или MS SQL.
* **Как да избегнеш:** Ако данните ти изискват 5 `JOIN`-а и строги релации, използвай релационна база (PostgreSQL / MS SQL), а не MongoDB.

### Грешка 3: Липсващи индекси върху полетата за филтриране
* **Какво се случва:** MongoDB автоматично индексира само `_id`. Ако търсиш често по `customer.userId` или `orderNumber` без да си създал индекс (`db.orders.createIndex({ "customer.userId": 1 })`), MongoDB прави **COLLSCAN** (чете всеки един документ в колекцията).
* **Как да избегнеш:** Винаги слагай индекс върху полетата, по които правиш `Find()` или `Sort()`.
