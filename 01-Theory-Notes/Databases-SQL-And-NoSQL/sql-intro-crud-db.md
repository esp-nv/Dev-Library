## 🏛️ 1. КАКВО Е РЕЛАЦИОННА БАЗА ДАННИ (RDBMS) И КАК РАБОТИ ПОД КАПАКА?

**RDBMS (Relational Database Management System)** е софтуерна система (MS SQL Server, PostgreSQL, MySQL), която съхранява данните в двумерни таблици (редове и колони), свързани помежду си чрез ключове.

### 🔍 Какво се случва при изпълнение на една SQL заявка?
1. **Parser & Binder:** Проверява синтаксиса (дали си написал правилно `SELECT`) и дали таблиците и колоните съществуват в системния каталог.
2. **Query Optimizer (Мозъкът на базата):** Тъй като SQL е **декларативен език** (казваш *какво* искаш, а не *как* да го намери), оптимизаторът изчислява десетки варианти (Execution Plans) — дали да прочете цялата таблица (`Table Scan`) или да използва индекс (`Index Seek`).
3. **Storage Engine:** Чете или записва страниците (Pages) в RAM буфера (`Buffer Pool`) и ги синхронизира с диска чрез транзакционния лог (`WAL`).

## 🏗️ 2. DDL: СЪЗДАВАНЕ И ПРОМЯНА НА СТРУКТУРАТА НА ТАБЛИЦИТЕ

Добрата структура на таблицата пази данните от грешки още преди C# кодът да се е изпълнил. Използваме **Constraints (Ограничения)**: `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`.

```sql
// ==================== MS SQL SERVER: СЪЗДАВАНЕ НА ТАБЛИЦА ====================
CREATE DATABASE ShopDb;
GO

USE ShopDb;
GO

CREATE TABLE Employees (
    Id INT IDENTITY(1,1) PRIMARY KEY, -- Автоматично нарастващо ID (1, 2, 3...)
    FirstName NVARCHAR(50) NOT NULL,
    LastName NVARCHAR(50) NOT NULL,
    Email VARCHAR(100) NOT NULL UNIQUE, -- Забранява дублиращи се имейли
    Salary DECIMAL(18, 2) NOT NULL CHECK (Salary >= 933.00), -- Бизнес правило на ниво БД
    Department NVARCHAR(50) NOT NULL DEFAULT N'Общ отдел',
    HireDate DATETIME2 NOT NULL DEFAULT GETUTCDATE(),
    IsActive BIT NOT NULL DEFAULT 1
);

// ==================== POSTGRESQL: ЕКВИВАЛЕНТНА ТАБЛИЦА ====================
CREATE TABLE employees (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    first_name VARCHAR(50) NOT NULL,
    last_name VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL UNIQUE,
    salary NUMERIC(18, 2) NOT NULL CHECK (salary >= 933.00),
    department VARCHAR(50) NOT NULL DEFAULT 'Общ отдел',
    hire_date TIMESTAMPTZ NOT NULL DEFAULT (NOW() AT TIME ZONE 'UTC'),
    is_active BOOLEAN NOT NULL DEFAULT TRUE
);
```

### 🔧 Промяна и изтриване на структура (`ALTER` и `DROP`):

```sql
// ==================== ПРОМЯНА НА СЪЩЕСТВУВАЩА ТАБЛИЦА ====================
-- Добавяне на нова колона
ALTER TABLE Employees
ADD PhoneNumber VARCHAR(20) NULL;

-- Промяна на тип или размер на колона
ALTER TABLE Employees
ALTER COLUMN FirstName NVARCHAR(100) NOT NULL;

-- Изтриване на колона
ALTER TABLE Employees
DROP COLUMN PhoneNumber;

-- Изтриване на цялата таблица (структура + данни)
DROP TABLE IF EXISTS Employees;
```

## 🔄 3. DML & DQL: ПЪЛЕН ЦИКЪЛ НА CRUD ОПЕРАЦИИТЕ

### 1️⃣ CREATE (`INSERT`) — Вмъкване на единични и множествени редове

```sql
// ==================== INSERT ПРИМЕРИ ====================
-- Единичен запис (Винаги изброявай колоните изрично!)
INSERT INTO Employees (FirstName, LastName, Email, Salary, Department)
VALUES (N'Георги', N'Димитров', 'g.dimitrov@company.bg', 3200.00, N'Разработка');

-- Множествено вмъкване в една транзакция (много по-бързо от отделни INSERT-и)
INSERT INTO Employees (FirstName, LastName, Email, Salary)
VALUES 
    (N'Мария', N'Иванова', 'm.ivanova@company.bg', 2850.50),
    (N'Петър', N'Стоянов', 'p.stoyanov@company.bg', 4100.00);

-- Връщане на генерираното ID веднага след запис (както прави EF Core!)
-- MS SQL Server:
INSERT INTO Employees (FirstName, LastName, Email, Salary)
OUTPUT INSERTED.Id
VALUES (N'Елена', N'Николова', 'e.nikolova@company.bg', 3500.00);

-- PostgreSQL:
-- INSERT INTO employees (first_name, last_name, email, salary)
-- VALUES ('Елена', 'Николова', 'e.nikolova@company.bg', 3500.00) RETURNING id;
```

### 2️⃣ READ (`SELECT`) — Филтриране, Изчисления, Сортиране и Странициране

```sql
// ==================== SELECT И ФИЛТРИРАНЕ ====================
-- Изчисляване на колони в реално време + Алиаси (AS)
SELECT 
    Id,
    CONCAT(FirstName, N' ', LastName) AS FullName,
    Salary AS MonthlySalary,
    Salary * 12 AS AnnualSalary
FROM Employees
WHERE IsActive = 1 
  AND Salary BETWEEN 2500 AND 4500
  AND Email LIKE '%@company.bg'
ORDER BY Salary DESC, LastName ASC;

-- Работа с NULL стойности (Тризначна логика: TRUE, FALSE, UNKNOWN)
SELECT FirstName, LastName, COALESCE(Department, N'Няма отдел') AS Dept
FROM Employees
WHERE Department IS NOT NULL;
```

### 3️⃣ UPDATE — Безопасно обновяване на данни

```sql
// ==================== UPDATE С ПРОВЕРКА ====================
-- Увеличаване на заплатата с 10% само за конкретен отдел
UPDATE Employees
SET Salary = Salary * 1.10
WHERE Department = N'Разработка' AND IsActive = 1;
```

### 4️⃣ DELETE срещу Soft Delete (Златен стандарт в работата)

В реалните фирмени проекти **рядко трием физически редове** с `DELETE`, защото губим историята и чупим отчетите. Вместо това ползваме **Soft Delete** (колона `IsDeleted` или `DeletedAt`):

```sql
// ==================== HARD DELETE СРЕЩУ SOFT DELETE ====================
-- Физическо изтриване (Hard Delete) - само за временни/грешни данни
DELETE FROM Employees
WHERE Id = 5;

-- Логическо изтриване (Soft Delete) - записът остава в БД, но е скрит за приложението
UPDATE Employees
SET IsActive = 0
WHERE Id = 3;
```

## ⚖️ 4. ДЪЛБОКО СРАВНЕНИЕ: `CHAR` / `VARCHAR` СРЕЩУ `NCHAR` / `NVARCHAR`

Разбирането на тези 4 типа пести гигабайти памет и предотвратява счупени текстове:

* **`CHAR(n)` / `NCHAR(n)` (Фиксирана дължина):** Ако дефинираш `CHAR(10)` и запишеш `'BG'`, базата заделя **всичките 10 символа** и допълва останалите 8 с интервали (`'BG        '`). Използва се **само** за кодове с гарантирана постоянна дължина (ISO кодове на валути `EUR`, `BGN`, ЕГН, пощенски кодове).
* **`VARCHAR(n)` / `NVARCHAR(n)` (Променлива дължина):** Ако дефинираш `NVARCHAR(100)` и запишеш `N'Иван'`, базата заема място само за **4 символа** + 2 байта за дължината.
* **Префиксът `N` (National / Unicode):** В MS SQL `VARCHAR` ползва 1 байт на символ (само латиница/ASCII), докато `NVARCHAR` ползва 2 байта (UTF-16) и съхранява безпроблемно кирилица, немски умлаути, китайски йероглифи и емоджита 🚀.

## 🚨 5. ПРАКТИЧЕСКИ КАПАНИ И ДОБРИ ПРАКТИКИ

1. **Никога `SELECT *` в продукционен C# код:** Когато пишеш `SELECT *`, теглиш излишни колони по мрежата (напр. големи описания или снимки) и чупиш оптимизацията на индексите. Изброявай само нужните колони.
2. **SQL Injection защита:** Никога не слепвай потребителски вход със `+` в SQL заявка (`"SELECT * FROM Users WHERE Name = '" + userInput + "'"`). Винаги използвай параметризирани заявки (`@Name`) или EF Core / Dapper.
3. **Затваряне на заявките с `;`:** Въпреки че T-SQL позволява изпускане на точка и запетая в някои случаи, стандартът ANSI SQL и функции като `WITH (CTE)` изискват предходната команда да завършва с `;`.

## 💾 6. ФИЗИЧЕСКО ЗАЕМАНЕ НА ПАМЕТТА И КАК БАЗАТА ЗАПИСВА ДАННИТЕ НА ДИСКА

Всеки избор на тип данни в `CREATE TABLE` определя колко реда ще се поберат в една **8 KB (8192 байта) страница (Data Page)** в MS SQL Server или PostgreSQL. Колкото по-тесни са колоните, толкова повече редове влизат в RAM буфера (`Buffer Pool`) с едно четене от диска.

### 🔍 1. Как изглежда един ред физически в паметта (Row Anatomy)?
Когато запишеш ред в таблица, двигателят го разделя на две зони:
1. **Fixed-Length зона (Фиксирана дължина):** Всички колони с постоянен размер (`INT`, `BIGINT`, `BIT`, `DATETIME2`, `CHAR`, `UNIQUEIDENTIFIER`) се записват плътно една до друга в началото на реда. Базата знае на кой точно байт започва всяка колона и я чете мигновено.
2. **Variable-Length зона (Променлива дължина):** Всички динамични колони (`VARCHAR`, `NVARCHAR`, `VARBINARY`) се записват в края на реда, придружени от **2-байтов указател (Offset Array)**, който казва къде свършва всяка стойност.

```text
+---------------+------------------+------------------+------------------------+------------------------+

| Row Header    | Fixed Columns    | Null Bitmap      | Variable Offset Array  | Variable Data          |
| (4 байта)     | (INT=4B, BIT=1B) | (1 бит на колона)| (2 байта на колона)    | (N'Иван' = 8 байта)    |
+---------------+------------------+------------------+------------------------+------------------------+
```

### ⚖️ 2. ДЕТАЙЛЕН АНАЛИЗ: КАКВО ПЕЧЕЛИШ И КАКВО ГУБИШ ПРИ ВСЕКИ ИЗБОР?

#### 🔹 А. Цели числа: `TINYINT` (1 B) vs `INT` (4 B) vs `BIGINT` (8 B)
* **Как се записват:** В двоичен вид (Two's Complement) с фиксиран брой байтове.
  * `TINYINT`: 1 байт (`0` до `255`) — идеален за `OrderStatus`, `RoleId`, възраст.
  * `SMALLINT`: 2 байта (`-32,768` до `32,767`).
  * `INT`: 4 байта (до ~`2.14 милиарда`).
  * `BIGINT`: 8 байта (до ~`9.22 квинтилиона`).
* **Предимство на по-малкия тип:** При таблица със 100 милиона реда разликата между `INT` (4 B) и `BIGINT` (8 B) е **400 MB само в основната таблица** + още по 400 MB във **всеки един индекс** (защото всеки Non-Clustered индекс съдържа копие на Primary Key-а!).
* **Недостатък:** Ако сложиш `INT` на таблица с логове или транзакции, която надхвърли 2.14 милиарда записа, базата ще хвърли фатална грешка *Arithmetic overflow error* и спира приемането на нови данни.

#### 🔹 Б. Пари и дробни числа: `DECIMAL(p, s)` vs `FLOAT`
* **Как се записват:**
  * `DECIMAL(18, 2)` заема **9 байта** (при прецизност 1–9 цифри = 5 B; 10–19 цифри = 9 B; 20–28 = 13 B; 29–38 = 17 B). Записва цифрите в десетична система без загуба на точност.
  * `FLOAT(53)` заема **8 байта** и записва числото в двоична научна нотация (мантиса + експонента).
* **Предимство на `DECIMAL`:** Гарантира, че `100.00 / 3 * 3` или сумирането на 10 милиона фактури няма да изгуби нито една стотинка.
* **Недостатък на `DECIMAL`:** По-тежък за процесора (CPU) при сложни тригонометрични/статистически формули в сравнение с `FLOAT`, който се смята директно от хардуерния копроцесор (FPU).

#### 🔹 В. Текстови данни: `CHAR(n)` vs `VARCHAR(n)` vs `NVARCHAR(n)` vs `NVARCHAR(MAX)`
* **Как се записват:**
  * `CHAR(10)`: Винаги записва **10 байта**, допълвайки празното място с интервали (`0x20`).
  * `VARCHAR(100)`: Записва `Дължина на текста (в байтове) + 2 байта`. За `'Sofia'` заема `5 + 2 = 7 байта`.
  * `NVARCHAR(100)`: Записва `2 * Брой символи + 2 байта` (UTF-16 / UCS-2 кодировка). За `N'София'` заема `5 * 2 + 2 = 12 байта`. *(В PostgreSQL `VARCHAR` ползва UTF-8: латиницата е 1 байт, кирилицата е 2 байта).*
  * `NVARCHAR(MAX)` (над 8000 байта / до 2 GB): Ако текстът надхвърли ~8 KB, базата **не го пази в основния ред**, а го изнася в специални **LOB (Large Object) страници** и оставя в реда само 16-байтов указател.
* **Критичен капан при `UPDATE` (Page Split):**
  * При `CHAR(50)`, ако обновиш стойността от 5 символа на 45 символа, размерът на реда **не се променя** — записът става на място без фрагментация.
  * При `NVARCHAR(200)`, ако първо запишеш празен низ `''` (2 B), а по-късно при `UPDATE` запишеш 150 символа (302 B), редът може да не се побере в текущата 8 KB страница. Базата прави **Page Split** — разцепва страницата на две, мести половината редове и забавя писането!
* **Капанът на `NVARCHAR(MAX)` при `SELECT`:** Колони с `(MAX)` изискват допълнително четене на LOB страници и **не могат да бъдат ключови колони в стандартен индекс**. Използвай `(MAX)` само за дълги статии, HTML или JSON логове, а за имена и имейли винаги слагай точен лимит (`NVARCHAR(100)`).

#### 🔹 Г. Идентификатори: `INT IDENTITY` (4 B) vs `UNIQUEIDENTIFIER` / `Guid` (16 B)
* **Как се записват:** `INT` е 4 байта последователни числа (`1, 2, 3...`). `UNIQUEIDENTIFIER` е 16 байта (128 бита) псевдослучаен шестнадесетичен низ (`3F2504E0-4F89-11D3-9A0C-0305E82C3301`).
* **Предимство на `Guid`:** Приложението (C#) може да генерира ID-то само, преди да прати данните към базата, и не разкрива колко записа имаш в таблицата (за разлика от `/api/orders/105`).
* **Недостатък на `Guid` (Тежка фрагментация):** Тъй като стандартният `Guid.NewGuid()` е напълно случаен, всеки нов запис иска да влезе **някъде по средата** на B-Tree индекса, а не в края му. Това причинява масови **Page Splits**, раздува индексите с до 30–50% празно място и забавя `INSERT` заявките.
  * *Решение в .NET 9+ / SQL:* Използвай последователни UUID v7 (`Guid.CreateVersion7()` в C# или `NEWSEQUENTIALID()` в MS SQL), които подреждат новите записи в края на индекса по време!

#### 🔹 Д. Логически стойности (`BIT`) — Скрита оптимизация
* **Как се записва:** Една колона `BIT` заема **1 байт**, но ако имаш **до 8 `BIT` колони** в една таблица (`IsActive`, `IsDeleted`, `IsVerified`, `IsAdmin`...), базата ги пакетира **всичките в един единствен байт** (по 1 бит за всяка колона)! Едва при 9-тата `BIT` колона заделя втори байт.
