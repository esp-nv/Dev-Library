## 1. МОДЕЛИРАНЕ В GRAPH БД (NEO4J): ВЪЗЛИ, ВРЪЗКИ И СВОЙСТВА

В релационните бази връзките се изчисляват по време на заявката чрез `JOIN`. В **Graph базите данни** връзките са **първокласни обекти (First-Class Citizens)** — те се записват физически на диска заедно със свои собствени свойства.

### Трите градивни елемента (Labeled Property Graph):
1. **Node (Възел):** Обектът — напр. `(:User)` или `(:Product)` *(аналог на ред в SQL таблица)*.
2. **Relationship (Връзка):** Насочена стрелка между два възела — напр. `-[:BOUGHT]->` или `-[:FRIENDS_WITH]->` *(замества Mapping таблиците)*.
3. **Properties (Свойства):** Ключ-стойност данни вътре във възела ИЛИ вътре в самата връзка (напр. `-[:BOUGHT {date: '2026-11-08', price: 120}]->`).

```cypher
// ============================================================
// МОДЕЛИРАНЕ И ЗАЯВКИ В NEO4J (CYPHER ЕЗИК)
// ============================================================

// 1. Създаване на възли и директна връзка със свойства между тях:
CREATE (u:User {id: 101, name: "Елена"})
CREATE (p:Product {id: 55, title: "Механична клавиатура"})
CREATE (u)-[:BOUGHT {boughtAt: date("2026-11-08"), rating: 5}]->(p);

// 2. Препоръки ("Хора, купили този продукт, купиха също и..."):
// Обхожда 3 нива на връзки за милисекунди без тежки JOIN-ове!
MATCH (me:User {name: "Елена"})-[:BOUGHT]->(item:Product)<-[:BOUGHT]-(other:User)-[:BOUGHT]->(rec:Product)
WHERE NOT (me)-[:BOUGHT]->(rec)
RETURN rec.title AS RecommendedProduct, COUNT(*) AS Score
ORDER BY Score DESC LIMIT 5;
```

## 2. МОДЕЛИРАНЕ В TIME-SERIES БД (TIMESCALEDB / INFLUXDB): ТАГОВЕ И ЧЪНКОВЕ

При IoT сензори, сървърен мониторинг и финансови борси данните са **Append-Only** (само се добавят нови измервания с времеви печат `Timestamp` и никога не се редактират стари).

### Как разделяме колоните при моделиране?
1. **Time (Време):** Задължителният `TIMESTAMPTZ` (в UTC), по който базата автоматично реже данните на времеви парчета (**Chunks** — напр. по 1 ден или 1 седмица).
2. **Tags / Dimensions (Метаданни за филтриране):** Колони с ограничен брой стойности (`device_id`, `city`, `sensor_type`), които се индексират.
3. **Fields / Measurements (Измервания):** Самите числови стойности (`temperature`, `cpu_percent`, `stock_price`), по които смятаме средни стойности (`AVG`, `MAX`).

```sql
-- ============================================================
-- МОДЕЛИРАНЕ В TIMESCALEDB (РАЗШИРЕНИЕ НА POSTGRESQL)
-- ============================================================
CREATE TABLE sensor_metrics (
    recorded_at TIMESTAMPTZ NOT NULL,       -- 1. Времеви печат
    device_id VARCHAR(50) NOT NULL,         -- 2. Tag (индексиран идентификатор)
    location VARCHAR(50) NOT NULL,          -- 2. Tag (филтър по зона)
    temperature DOUBLE PRECISION NOT NULL,  -- 3. Field (измерена стойност)
    humidity DOUBLE PRECISION NOT NULL      -- 3. Field (измерена стойност)
);

-- Превръщане в Hypertable (автоматично разделя данните по дни/седмици):
SELECT create_hypertable('sensor_metrics', 'recorded_at');
CREATE INDEX idx_device_time ON sensor_metrics (device_id, recorded_at DESC);
```

## 3. МОДЕЛИРАНЕ ВЪВ VECTOR БД ЗА AI (PGVECTOR / QDRANT): CHUNKING И МЕТАДАННИ

Векторните бази не съхраняват цели книги или PDF файлове като един обект, защото един вектор може да побере смисъла само на ограничен брой думи (обикновено 300–500 думи).

### Трите задължителни компонента на един запис във Vector БД:
1. **Chunk (Текстов откъс):** Оригиналният параграф (с малко застъпване — *Overlap* от 10–15% между съседните парчета, за да не се реже смисълът по средата на изречението).
2. **Embedding (Вектор):** Масивът от числа (напр. `1536` числа), генериран от AI модела.
3. **Metadata (Филтриращи колони):** Обикновени полета (`document_id`, `department`, `is_public`), които позволяват **Hybrid Search** (първо филтрираш по права/отдел, после търсиш по смисъл).

```sql
-- ============================================================
-- ХИБРИДЕН МОДЕЛ В PGVECTOR (МЕТАДАННИ + ВЕКТОР)
-- ============================================================
CREATE TABLE ai_document_chunks (
    id BIGSERIAL PRIMARY KEY,
    document_name VARCHAR(200) NOT NULL,
    department VARCHAR(50) NOT NULL,        -- Метаданни за сигурност (RBAC)
    chunk_text TEXT NOT NULL,               -- Реалният текст, който се подава на LLM
    embedding VECTOR(1536) NOT NULL         -- Числовият вектор на смисъла
);

-- Търсене по смисъл САМО в документите на отдел "HR":
SELECT document_name, chunk_text
FROM ai_document_chunks
WHERE department = 'HR'
ORDER BY embedding <-> '[0.014, -0.18, ...]'
LIMIT 3;
```

## 4. ЧЕСТИ ГРЕШКИ, КАПАНИ И КАК ДА ГИ ИЗБЕГНЕМ

### Грешка 1: „Supernodes“ (Супер-възли) в Graph БД
* **Какво се случва:** Създаваш един общ възел `(:Country {name: "Bulgaria"})` и свързваш 5 милиона потребители към него с `-[:LIVES_IN]->`. Когато заявката мине през този възел, базата трябва да обходи 5 милиона стрелки и забива.
* **Как да избегнеш:** Не превръщай общи категории (държави, държавни статуси, пол) в общи възли, ако имат милиони връзки — пази ги като свойство (`user.country = "Bulgaria"`) или ги раздели на по-малки възли (градове/квартали).

### Грешка 2: Висока кардиналност на таговете в Time-Series БД (High Cardinality)
* **Какво се случва:** В InfluxDB или TimescaleDB слагаш уникално `request_id` (UUID) или точен час като **Tag** (индексирано измерение) вместо като **Field**. Индексът в паметта се раздува до десетки гигабайти и сървърът умира от липса на RAM.
* **Как да избегнеш:** Индексираните тагове трябва да са ограничен брой категории (`server_name`, `sensor_id`, `region`), а уникалните стойности да са обикновени полета.

### Грешка 3: Липса на метаданни и права във Vector БД (Изтичане на данни в AI)
* **Какво се случва:** Качваш всички фирмени документи (включително заплатите на мениджърите) във векторната база без колона за права (`role` / `department`). Обикновен служител пита AI бота *„Колко е бонусът на директора?“* и ботът намира документа по смисъл и го цитира!
* **Как да избегнеш:** Винаги моделирай векторните записи с **Metadata колони** (`allowed_roles`, `tenant_id`, `user_id`) и задължително прилагай `WHERE` филтър преди векторното сравнение.
