# 03-02-00. Redis Caching Архитектура и Структури от данни (Теория, Cache-Aside и Капани)

## 1. ЗАЩО REDIS Е СВРЪХБЪРЗ: RAM ПАМЕТ СРЕЩУ DISK I/O И SINGLE-THREADED EVENT LOOP

Традиционните релационни бази данни (SQL Server, PostgreSQL, MySQL) съхраняват данните върху твърдия диск (SSD/NVMe) и извършват сложни операции по парсване на SQL, заключване на таблици и четене от диска. **Redis** е отворено **In-Memory Key-Value хранилище**, което държи целия набор от данни директно в оперативната памет (**RAM**):

* **Скорост на достъп:** Достъпът до RAM отнема **наносекунди**, докато четенето от диск отнема **милисекунди** — Redis обслужва над **100 000+ заявки в секунда** с латентност под `0.5ms`.
* **Еднонишков модел (Single-Threaded Event Loop + I/O Multiplexing):** Redis изпълнява командите в една главна нишка. Това напълно елиминира нуждата от тежки заключвания (`Locks` / `Mutexes`) и превключване на контекста на процесора (`Context Switching`), които често забавят многонишковите бази данни.
* **Устойчивост (Persistence — RDB & AOF):** Въпреки че работи в RAM, Redis може да записва периодични снимки на диска (**RDB Snapshots**) или лог на всяка промяна (**AOF — Append-Only File**), за да не губи данните при рестарт на сървъра.

---

## 2. ПЕТТЕ ОСНОВНИ СТРУКТУРИ ОТ ДАННИ В REDIS (DATA STRUCTURES)

Redis не съхранява просто текстови низове — той е сървър за структури от данни в паметта:

1. **`String` (Низ / JSON / Брояч):** Най-базовият тип. Използва се за кеширане на сериализирани JSON обекти, HTML фрагменти, сесийни токени и атомарни броячи (`INCR` за прегледи или Rate Limiting).
2. **`Hash` (Речник от полета и стойности):** Идеален за представяне на обекти (напр. `user:1042` с полета `name`, `email`, `role`). Позволява промяна само на едно поле без презаписване на целия обект.
3. **`List` (Двойно свързан списък):** Подредена колекция по ред на вмъкване (`LPUSH` / `RPOP`). Използва се за опашки от задачи (Background Jobs) и последни 10 активности.
4. **`Set` (Множество от уникални елементи):** Гарантира липса на дубликати и поддържа светкавични операции за сечение и обединение (напр. уникални посетители за деня, тагове, онлайн потребители).
5. **`Sorted Set` / `ZSet` (Сортирано множество с рейтинг `Score`):** Всеки уникален елемент има числов резултат (`Score`), по който се подрежда автоматично. Златен стандарт за класации в реално време (**Leaderboards**).

## 3. КЕШИРАЩИ СТРАТЕГИИ: CACHE-ASIDE (LAZY LOADING) & INVALIDATION

Най-използваният шаблон в индустрията е **Cache-Aside**, при който приложението първо проверява в Redis и пада към базата данни само при липса на запис:

```text
 ┌──────────────────┐     1. GET product:55      ┌──────────────────────────┐
 │   Backend API    │ ─────────────────────────► │   REDIS (RAM Cache)      │
 └────────┬─────────┘                            └────────────┬─────────────┘
          │                                                   │
          │ 3. Ако е Cache MISS:                              │ 2. Cache HIT -> Връща
          │    SELECT * FROM Products WHERE Id = 55           │    JSON веднага (<1ms)
          ▼                                                   │
 ┌──────────────────┐     4. SET product:55 "{...}" EX 600    │
 │  SQL Database    │ ────────────────────────────────────────┘
 └──────────────────┘        (Записва в кеша с TTL 10 мин.)
```

* **Cache Invalidation (Инвалидиране при промяна):** Когато администратор обнови цената на продукт в SQL базата, сървърът задължително изпълнява **`DEL product:55`**, за да изтрие остарелия запис от Redis и да предотврати показването на неактуални данни (**Stale Data**).

## 4. СИСТЕМНИ КАПАНИ: ЛИПСВАЩ TTL (OOM CRASH), CACHE STAMPEDE И CACHE PENETRATION

### 🚨 Капан №1: Записване на ключове без TTL (`EXPIRE`) и срив `OOM command not allowed`
* **Какво правиш:** Записваш хиляди кеширани страници и сесии с `SET key value`, без да зададеш срок на валидност (`TTL — Time To Live`).
* **Какво се случва:** RAM паметта на Redis се запълва до 100% и сървърът започва да хвърля фатална грешка при всеки нов запис:
  ```text
  (error) OOM command not allowed when used memory > 'maxmemory'.
  ```
* **Решение:** Винаги задавай изричен `TTL` (`EX 300` за 5 минути) и конфигурирай политика за изчистване в `redis.conf`: **`maxmemory-policy allkeys-lru`** (автоматично изтрива най-отдавна неизползваните ключове при запълване на паметта).

### 🚨 Капан №2: Cache Stampede (Лавинообразен удар върху базата данни)
* **Защо се случва:** Изключително популярен ключ (напр. началната страница на онлайн магазин в Черен петък) изтича в точно определена секунда. В същия миг 5 000 едновременни потребители получават `Cache MISS` и всички 5 000 заявки удрят SQL базата данни едновременно, събаряйки сървъра.
* **Решение:** Добави случаен интервал към времето на живот (**TTL Jitter** — напр. `300s + random(0..60s)`), така че ключовете да не изтичат в една и съща милисекунда, или използвай разпределено заключване (**Distributed Lock**), при което само една нишка обновява кеша.

### 🚨 Капан №3: Cache Penetration (Заявки за несъществуващи ID-та)
* **Защо се случва:** Злонамерен бот изпраща хиляди заявки за невалидни идентификатори (`/products/-99999`). Тъй като ги няма нито в Redis, нито в базата данни, всяка заявка минава директно през кеша и товари SQL базата.
* **Решение:** Кеширай и празните резултати (`"NULL"`) за кратък период (напр. `EX 60` секунди).
