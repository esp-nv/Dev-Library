## 1. КАК ДА СЕ ЗАПОМНИ ПО-ЛЕСНО (МНЕМОНИКА: GIT СРЕЩУ GITHUB & ЧЕТИРИТЕ ЗОНИ)

* **Git срещу GitHub (Двигателят срещу Гаража в облака):**
  * **Git** е **локален инструмент** на твоя компютър (работи и без интернет), който пази пълната история на всяка промяна в кода ти.
  * **GitHub** (както и GitLab / Azure DevOps) е **облачен сървър**, където качваш своя Git архив, за да го споделяш с екипа, да правиш Code Review (Pull Requests) и да пускаш автоматични тестове (CI/CD).
* **Четирите зони на Git (Пощенската пратка):**
  1. **Working Directory (Работна маса):** Папката на диска, където редактираш файловете си.
  2. **Staging Area / Index (Кашонът за опаковане — `git add`):** Слагаш вътре само файловете, които искаш да влязат в следващата снимка.
  3. **Local Repository (Запечатаният колет с етикет — `git commit`):** Записваш постоянна версия (Snapshot) с уникален SHA-1 хеш и описание на твоя компютър.
  4. **Remote Repository (Изпращане по куриер в облака — `git push`):** Качваш локалните комити в GitHub.

## 3. СРАВНИТЕЛНА МАТРИЦА: GIT CLI СРЕЩУ GITHUB DESKTOP СРЕЩУ TORTOISEGIT („КОСТЕНУРКАТА“)

| Критерий | 💻 Git CLI (Терминал / Bash) | 🟣 GitHub Desktop | 🐢 TortoiseGit („Костенурката“) | 🔵 VS Code Source Control |
| :--- | :--- | :--- | :--- | :--- |
| **Интерфейс** | Текстови команди в конзолата. | Модерен, минималистичен графичен прозорец (GUI). | Вгражда се директно в **Windows Explorer** (десен бутон + иконки). | Вграден панел отляво в редактора (`Ctrl + Shift + G`). |
| **Визуални индикатори** | Само чрез команда `git status`. | Списък с променени файлове и цветен Diff (червено/зелено). | **Цветни иконки върху самите папки/файлове** (зелена отметка, червен удивителен). | Цветни маркери в полето на кода и в дървото на файловете. |
| **Поддръжка на платформи** | Windows, Linux, macOS (навсякъде). | Windows, macOS. | **Само Windows** (Shell Extension). | Windows, Linux, macOS. |
| **Сложни операции** | **100% от възможностите** на Git (`rebase -i`, `reflog`, `bisect`). | Основните 90% (`commit`, `push`, `branch`, `stash`, `merge`). | Почти 100% — има визуални менюта за `Rebase`, `Cherry-pick`, `Blame`, `Log`. | Основните операции + визуален **3-Way Merge Editor**. |
| **За кого е най-подходящ?** | За всички нива, CI/CD сървъри и сеньор дебъгване. | За начинаещи и бърза ежедневна работа с GitHub. | За хора, свикнали с Windows Explorer и TortoiseSVN, и преглед на детайлна история. | Когато не искаш да напускаш редактора, докато пишеш код. |

## 4. ПЛЮСОВЕ И МИНУСИ НА РАЗПРЕДЕЛЕНИЯ КОНТРОЛ НА ВЕРСИИТЕ (DVCS)

### 🟢 Предимства (Pros):
* **Пълно локално копие на историята:** Всеки разработчик има цялото хранилище на диска си — можеш да правиш комити, да сменяш клонове и да гледаш историята в самолет без интернет.
* **Евтини и мигновени клонове (Branching):** Създаването на нов клон (`feature/login`) отнема милисекунди и заема само 41 байта (указател към комит).

### 🔴 Недостатъци (Cons):
* **Не е подходящ за огромни бинарни файлове:** Видео файлове, големи `.zip` архиви и `.psd` дизайни раздуват папката `.git` завинаги (за тях се използва разширението **Git LFS**).
* **Стъпка за разрешаване на Merge Conflicts:** Когато двама души редактират едни и същи редове в един файл едновременно, Git спира и изисква човешка намеса.

## 5. КОДОВ ОДИТ: ГРЕШЕН (КАЧВАНЕ НА ПАРОЛИ И `NODE_MODULES`) СРЕЩУ ПРАВИЛЕН (`.GITIGNORE` & FEATURE BRANCH)

### ❌ ГРЕШЕН ПОДХОД (Качване на `.env` с пароли и хиляди генерирани файлове директно в `main`):
```text
1. Няма .gitignore файл -> git add . качва 45 000 файла от node_modules/ или bin/obj/!
2. Качва се файл .env с реална парола за базата данни и AWS API ключове!
3. Всички работят директно в клон 'main' без Pull Request и без Code Review.
```
*(Внимание: Дори по-късно да изтриеш файла `.env` с нов комит, паролата **остава завинаги в старата история на Git** и ботовете я крадат за секунди!)*

### 🟢 ПРАВИЛЕН ПОДХОД (Защитен `.gitignore` + Feature Branch Workflow):
```gitignore
# Задължителен .gitignore шаблон преди първия комит!
node_modules/
dist/
out/
bin/
obj/
.vs/
.vscode/
.env
.env.local
*.log
```
* **Работен цикъл:** Създаваш нов клон `git checkout -b feature/user-auth` ➔ правиш малки, логически комити ➔ качваш клона в GitHub (`git push -u origin feature/user-auth`) ➔ отваряш **Pull Request (PR)** за преглед преди сливане в `main`.

## 6. ИНТЕРВЮ КАПАНИ, ВЪПРОСИ И УЛОВКИ (`FETCH` VS `PULL`, `MERGE` VS `REBASE`)

* **Въпрос 1:** *„Каква е разликата между **`git fetch`** и **`git pull`**?“*
  * **Отговор:** **`git fetch`** е напълно безопасна команда — тя само изтегля новите комити и клонове от отдалечения сървър (GitHub) в локалната ти памет, **без да пипа или променя твоите работни файлове**. **`git pull`** е комбинация от две команди: **`git fetch` + `git merge`** — тя изтегля промените и веднага ги слива в текущия ти клон (което може да предизвика Merge Conflict).
* **Въпрос 2:** *„Каква е разликата между **`git merge`** и **`git rebase`**?“*
  * **Отговор:** И двете интегрират промените от един клон в друг. **`git merge`** запазва пълната хронологична история такава, каквато е била, и създава нов общ **Merge Commit** (разклонено дърво). **`git rebase`** пренаписва историята, като взима твоите комити и ги „премества“ най-отгоре на целевия клон, създавайки **чиста, права линейна история** без излишни Merge комити. *(Златно правило: Никога не прави `rebase` върху публичен споделен клон като `main`!)*
