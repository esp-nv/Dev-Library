## ⚙️ 1. ВЪВЕДЕНИЕ В SOLID АРХИТЕКТУРАТА

### 🧠 ИДЕЯТА ПОД КАПАКА
SOLID не е синтаксис на C# и не е компилаторно правило. Това са 5 фундаментални конвенции за обектно-ориентиран дизайн, които управляват начина, по който софтуерните компоненти се обвързват помежду си в паметта. 

При лош дизайн (т.нар. **STUPID код**) промените в едно уеб приложение водят до "ефекта на доминото" — коригираш бъг в оценките, а базата данни спира да работи. Правилното прилагане на SOLID гарантира:
1. **Low Coupling (Ниска обвързаност):** Класовете не зависят директно от конкретните имплементации на други класове.
2. **High Cohesion (Висока споделеност):** Всеки клас е силно специализиран и върши само своята работа.
3. **Елиминиране на Техническия дълг:** Кодът се разширява без нужда от пренаписване на съществуващи производствени алгоритми.

## 🟥 2. S — SINGLE RESPONSIBILITY PRINCIPLE (Принцип за Единствена Отговорност)

### ❓ Какъв проблем решава?
Елиминира т.нар. **"God Classes" (Класове-Богове)**. В Junior проектите често се среща един масивен клас (напр. `StudentManager`), който съдържа в себе си 2000 реда код и извършва едновременно: бизнес изчисления, валидация на низове, генериране на HTML изгледи, директни SQL заявки и запис на логове във файловата система. 
Когато бизнес изискванията за логване се променят, ти си принуден да промениш този огромен файл. По този начин рискуваш неволно да счупиш критичната математическа логика за изчисляване на студентски стипендии.

### 💡 Аналогия от живота
**Швейцарско ножче срещу специализиран комплект инструменти.** Швейцарското ножче има нож, тирбушон, ножица и трион, пакетирани на едно място. Ако обаче тирбушонът се изкриви или счупи, ти трябва да смениш или поправиш цялото ножче. При професионалните инструменти готвачът има нож, а сомелиерът има специализиран тирбушон. Всеки инструмент върши една задача, но я върши перфектно и се подменя независимо.

### 🎯 Приложение в StudentManagement
Всеки софтуерен компонент (клас, метод, интерфейс) трябва да има **само една причина за промяна** (Only one reason to change).
* **Грешна логика:** Класът за обработка на данни познава пътя до твърдия диск или стринга за връзка с базата данни.
* **Правилна логика:** Бизнес логиката извиква абстрактни методи, а инфраструктурните задачи (файлове, бази, мрежа) са изнесени в изолирани услуги.

### 💻 Практически пищов (Преди vs Сега)

#### ЛОШИЯТ НАЧИН (Анти-модел — Всичко в един кюп)
```csharp
// ❌ ТОЗИ КЛАС Е "БОГ" — Има 3 причини за промяна: Бизнес логика, База данни, Логване във файл.
public class StudentService
{
    public void RegisterStudent(string name, double grade)
    {
        // 1. Бизнес Валидация
        if (string.IsNullOrEmpty(name))
        {
            throw new ArgumentException("Името е празно!");
        }

        // 2. Директна работа с ниско ниво инфраструктура (SQL Симулация)
        Console.WriteLine(\$"Запис в SQL базата: {name} с оценка {grade}");

        // 3. Директна работа с файловата система (Твърдо кодиран път)
        System.IO.File.WriteAllText(@"C:\Logs\app.log", \$"[LOG] Регистриран студент: {name}");
    }
}
```

#### ДОБРИЯТ НАЧИН (SOLID модел — Разделени отговорности)
```csharp
// ✅ Слой 1: Чист Domain модел (Държи само състоянието и валидацията на субекта)
public class Student
{
    public string Name { get; private set; }
    public double Grade { get; private set; }

    public Student(string name, double grade)
    {
        if (string.IsNullOrEmpty(name)) throw new ArgumentException("Името е задължително!");
        Name = name;
        Grade = grade;
    }
}

// ✅ Слой 2: Data Access Слой (Отговаря ЕДИНСТВЕНО за комуникацията с базата данни)
public class StudentRepository
{
    public void Add(Student student)
    {
        Console.WriteLine(\$"[SQL] Успешен запис на обект {student.Name} в базата данни.");
    }
}

// ✅ Слой 3: Логваща Услуга (Отговаря ЕДИНСТВЕНО за операционната система и файловете)
public class FileLogger
{
    private const string LogPath = "app.log";
    public void LogInfo(string message)
    {
        System.IO.File.AppendAllText(LogPath, \$"[INFO] {DateTime.Now}: {message}\n");
    }
}

// ✅ Слой 4: Оркестратор (Оркестрира процеса, без да знае как точно работят подсистемите)
public class RegistrationProcessor
{
    private readonly StudentRepository _repository = new StudentRepository();
    private readonly FileLogger _logger = new FileLogger();

    public void Process(string name, double grade)
    {
        Student student = new Student(name, grade); // 1. Създаване и вътрешна валидация
        _repository.Add(student);                  // 2. Запис
        _logger.LogInfo(\$"Студент {name} е обработен успешно."); // 3. Лог
    }
}
```

## 🟩 3. O — OPEN/CLOSED PRINCIPLE (Принцип Отворен/Затворен)

### ❓ Какъв проблем решава?
Предотвратява безкрайното "рязане", модифициране и дописване на работещ, тестван и внедрен в продукция софтуерен код. Когато бизнесът поиска нова функционалност (напр. нов вид отстъпка или нов тип изпит), Junior разработчиците отварят съществуващия метод и добавят нов `else if` или `case` в масивни логически структури. 
Това модифициране на работещ файл нарушава стабилността и е най-честата причина за поява на неочаквани регресионни бъгове в старата функционалност.

### 💡 Аналогия от живота
**USB портовете на твоята дънна платка.** Дънната платка и процесорът на компютъра ти са фабрично запечатани. Те са **затворени за модификация** — ти не вземаш поялник, за да преправяш пистите на процесора, когато искаш да включиш нова клавиатура. Вместо това, дънната платка предоставя стандартна абстракция — USB порт. Компютърът е **отворен за разширение** — чрез включване на външни устройства ти добавяш нова функционалност (мишка, слушалки, принтер), без да променяш ядрото на хардуера.

### 🎯 Приложение in StudentManagement
Софтуерните субекти трябва да бъдат **отворени за разширение (Extension), но затворени за модификация (Modification)**. Постига се чрез замяна на твърдите логически проверки с **полиморфизъм и интерфейси**.

### 💻 Практически пищов (Преди vs Сега)

#### ЛОШИЯТ НАЧИН (Анти-модел — Счупен Open/Closed с безкраен `switch`)
```csharp
// ❌ ГРЕШНО: При всяка нова изпитна форма (напр. Практически изпит, Защита на проект),
// ти трябва да отвориш този работещ клас и да добавиш нов "case" блок. Риск от счупване!
public class ExamEvaluator
{
    public double CalculateScore(string examType, double basePoints)
    {
        switch (examType)
        {
            case "Theory":
                return basePoints * 1.2;
            case "OnlineQuiz":
                return basePoints * 1.0;
            default:
                return basePoints;
        }
    }
}
```

#### ДОБРИЯТ НАЧИН (SOLID модел — Разширение чрез Полиморфизъм)
```csharp
// ✅ Дефинираме чист договор (Абстракция), отворен за бъдещи разширения
public interface IExamType
{
    double Evaluate(double basePoints);
}

// ✅ Всеки конкретен изпит имплементира договора в собствен, изолиран файл
public class TheoryExam : IExamType
{
    public double Evaluate(double basePoints) => basePoints * 1.2;
}

public class OnlineQuizExam : IExamType
{
    public double Evaluate(double basePoints) => basePoints * 1.0;
}

// 🚀 НОВА ФУНКЦИОНАЛНОСТ: Добавяме я в НАПЪЛНО НОВ КЛАС, без да докосваме старите!
public class ProjectDefenseExam : IExamType
{
    public double Evaluate(double basePoints) => (basePoints * 1.5) + 10;
}

// ✅ Оценяването работи с абстракцията. Този клас е ЗАТВОРЕН за промяна завинаги.
public class ExamProcessor
{
    public double ProcessEvaluation(IExamType exam, double points)
    {
        // Полиморфизъм в действие — C# определя типа автоматично под капака
        return exam.Evaluate(points); 
    }
}
```

## 🟨 4. L — LISKOV SUBSTITUTION PRINCIPLE (Принцип за Заменяемост на Лисков)

### ❓ Какъв проблем решава?
Предотвратява създаването на изкуствени, грешни и принудителни наследявания, които нарушават логиката на полиморфизма. В софтуерната деградация често срещан анти-модел е Junior разработчик да наследи даден клас просто за да "преизползва" 2-3 негови свойства или методи, въпреки че наследникът реално не притежава пълното поведение на родителя. 
Когато този подклас бъде подаден на по-високите архитектурни слоеве, които очакват стабилно басово поведение, програмата забива с невидими по време на компилация грешки (напр. `NotImplementedException`).

### 💡 Аналогия от живота
**Жива патица срещу пластмасова патица за баня.** Имаш базов клас `Duck` (Патица) с виртуален метод `Swim()` (Плувай). Ако създадеш подклас `ToyDuck` (Гумена патица) и го пуснеш в метод, който симулира езеро, но гумената патица изисква батерии или хвърля изключение, защото не може да плува автономно, полиморфизмът се чупи. 
Ако софтуерният субект изглежда като патица и квака като патица, но се нуждае от батерии или специално отношение, за да не счупи кода — наследяването ти е грешно.

### 🎯 Приложение in StudentManagement
Всеки производна инстанция (подклас) трябва да може да замени своя базов (родителски) клас, **без това да променя коректността на програмата** или да изисква специални `if` проверки от тип `if (course is OnlineCourse)`.
* **Грешна логика:** Създаване на клас `OnlineCourse`, който наследява `BaseCourse`, но хвърля грешка в метода `GetPhysicalClassroom()`, защото онлайн курсовете нямат физическа стая.
* **Правилна логика:** Базовият клас съдържа само свойства, валидни за абсолютно всички курсове, а физическите локации се изнасят в интерфейсна структура.

### 💻 Практически пищов (Преди vs Сега)

#### ЛОШИЯТ НАЧИН (Анти-модел — Нарушен Liskov, кодът гърми в Runtime)
```csharp
// ❌ ГРЕШНО: Базовият клас налага поведение, което не е универсално за всички наследници.
public class StudentAccount
{
    public virtual void ApplyScholarship(decimal amount) => Console.WriteLine($"Начислена стипендия: {amount}");
    public virtual void BookDormitoryRoom() => Console.WriteLine("Стая в общежитието е резервирана.");
}

// Онлайн студентите не живеят в общежития. Нарушаваме договора на родителя!
public class OnlineStudentAccount : StudentAccount
{
    public override void BookDormitoryRoom()
    {
        throw new NotImplementedException("Онлайн студентите нямат право на общежитие!"); 
        // ❌ БУУМ! Всеки foreach, който върти акаунти и заделя стаи, ще счупи целия сървър.
    }
}
```

#### ДОБРИЯТ НАЧИН (SOLID модел — Правилна йерархия чрез интерфейсно разделение)
```csharp
// ✅ Базовият клас налага единствено споделеното и 100% сигурно поведение
public abstract class BaseStudentAccount
{
    public string StudentId { get; set; }
    public abstract void ApplyScholarship(decimal amount);
}

// ✅ Дефинираме договор само за специфичното инфраструктурно поведение
public interface IOnCampusResident
{
    void BookDormitoryRoom();
}

// ✅ Редовен студент: Има право и на двете операции
public class RegularStudentAccount : BaseStudentAccount, IOnCampusResident
{
    public override void ApplyScholarship(decimal amount) => Console.WriteLine($"Стипендия: {amount}");
    public void BookDormitoryRoom() => Console.WriteLine("Стая 402Б е резервирана успешно.");
}

// ✅ Онлайн студент: Безопасен замяна на базовия клас, без скрити "капани" и празни методи
public class DistanceStudentAccount : BaseStudentAccount
{
    public override void ApplyScholarship(decimal amount) => Console.WriteLine($"Онлайн стипендия: {amount}");
    // Тук изобщо няма метод за общежитие — няма риск от неволно извикване и краш!
}
```

## 🟦 5. I — INTERFACE SEGREGATION PRINCIPLE (Принцип за Разделяне на Интерфейсите)

### ❓ Какъв проблем решава?
Елиминира създаването на т.нар. **"Fat Interfaces" (Дебели интерфейси / Интерфейси-Чудовища)**. Когато проектират система, Junior разработчиците често слагат абсолютно всички възможни методи за даден модул в един общ, масивен интерфейс (напр. `IManagerActions`). 
В резултат на това, класовете, които са принудени да имплементират този договор, се натоварват с празен код, пишейки фиктивни `return;` или хвърляйки грешки за методи, които бизнес логиката им изобщо не изисква.

### 💡 Аналогия от живота
**Договорът за абонамент в съвременна телевизия.** Представи си, че искаш да гледаш само спортни канали. Ако телевизионният доставчик те задължи да подпишеш "Глобален Договор за Стрийминг", който те таксува и задължава да инсталираш детски канали, кулинарни програми и научнопопулярни пакети, ти ще се откажеш. 
Вместо това, доставчикът предлага модулно разделение на пакети (интерфейси) — плащаш и имплементираш само това, което реално ще консумираш.

### 🎯 Приложение in StudentManagement
**Клиентите на един интерфейс не трябва да бъдат принуждавани да зависят от методи, които не използват.** По-добре е да имаш 10 малки, силно специализирани (атомарни) интерфейса, отколкото един масивен.
* **Грешна логика:** Интерфейс `IStudentRepository`, който съдържа методи за четене, запис, изтриване, експорт към Excel и архивиране на базата на системно ниво.
* **Правилна логика:** Разделяне на `IReadOnlyRepository<T>` (само за четене/справки) и `IWriteOnlyRepository<T>` (за административни записи).

### 💻 Практически пищов (Преди vs Сега)

#### ЛОШИЯТ НАЧИН (Анти-модел — Масивен интерфейс, генериращ "мъртъв код")
```csharp
// ❌ ТОЗИ ИНТЕРФЕЙС Е ПРЕКАЛЕНО ДЕБЕЛ. Той смесва роли на Студенти, Преподаватели и Счетоводство.
public interface ISchoolSystemActions
{
    void AttendLecture();
    void GradeAssignment();
    void ProcessTuitionPayment();

// Класът Student е принуден да имплементира GradeAssignment, което е софтуерен абсурд.
public class StudentUser : ISchoolSystemActions
{
    public void AttendLecture() => Console.WriteLine("Студентът присъства на лекция.");
    public void ProcessTuitionPayment() => Console.WriteLine("Таксата за семестъра е платена.");
    
    public void GradeAssignment() 
    {
        throw new InvalidOperationException("Студентът НЕ може да оценява домашни!"); // ❌ Мъртъв код/Капан
    }
}
```

#### ДОБРИЯТ НАЧИН (SOLID модел — Атомарни, силно специализирани договори)
```csharp
// ✅ Разделяме отговорностите на ниво архитектурен договор (Интерфейс)
public interface ILearner { void AttendLecture(); }
public interface IEvaluator { void GradeAssignment(); }
public interface IFinancialContributor { void ProcessTuitionPayment(); }

// ✅ Студентът имплементира само това, което го засяга директно
public class SharpStudent : ILearner, IFinancialContributor
{
    public void AttendLecture() => Console.WriteLine("Присъствие в аулата.");
    public void ProcessTuitionPayment() => Console.WriteLine("Плащане през ePay.");
}

// ✅ Преподавателят има своя собствена чиста имплементация без излишен баланс в паметта
public class Professor : IEvaluator
{
    public void GradeAssignment() => Console.WriteLine("Оценка: Отличен (6.00) на практическа задача.");
}
```

## 🟪 6. D — DEPENDENCY INVERSION PRINCIPLE (Принцип за Обръщане на Зависимостите)

### ❓ Какъв проблем решава?
Предотвратява твърдото "заваряване" и високата софтуерна зависимост (**High Coupling**) между бизнес логиката и нискоуровневата хардуерна/инфраструктурна имплементация. Без този принцип, ако твоят високоуровнев контролер или услуга директно инстанцира с `new` конкретен клас за база данни (напр. `SqliteRepository`), софтуерът ти се превръща в заложник на технологията. 
Ако утре решиш да преминеш от SQLite към PostgreSQL или Azure Cloud, ще трябва да пренапишеш и прекомпилираш цялото приложение от уеб интерфейса до бизнес ядрото.

### 💡 Аналогия от живота
**Електрическият контакт в твоята стая.** Твоят лаптоп, телевизор или зарядно за телефон се нуждаят от електричество (високо ниво нужда). Те обаче не са директно запоени за медните проводници, идващи от електроцентралата в стената (ниско ниво имплементация). 
Между тях има **Абстракция — стандартният електрически контакт**. Лаптопът ти зависи от профила на щепсела (контакта), и стената предоставя същия контакт. Благодарение на това обръщане на зависимостите, в контакта можеш да включиш както лаптоп, така и прахосмукачка, без да преправяш електрическата мрежа на блока.

### 🎯 Приложение in StudentManagement
**Модулите от високо ниво не трябва да зависят от модулите от ниско ниво. И двата вида трябва да зависят от абстракции.** Това е фундаменталното правило зад **Dependency Injection (DI)** в .NET Core.
* **Грешна логика:** Използване на `private SqlService _db = new SqlService();` в контролерите ти.
* **Правилна логика:** Контролерът изисква през конструктора си просто интерфейс `IStudentData`, без изобщо да го интересува кой реално е класът зад него.

### 💻 Практически пищов (Преди vs Сега)

#### ЛОШИЯТ НАЧИН (Анти-модел — Твърдо заварена зависимост чрез `new`)
```csharp
// Ниско ниво инфраструктурен клас
public class SqliteDatabase
{
    public List<string> FetchStudents() => new List<string> { "Анна", "Борис" };
}
```

```csharp
// ✅ Стъпка 1: Създаваме контакта (Абстракцията)
public interface IStudentDataProvider
{
    List<string> FetchStudents();
}

// ✅ Стъпка 2: Ниското ниво имплементира интерфейса (Реална База Данни)
public class PostgresDatabase : IStudentDataProvider
{
    public List<string> FetchStudents() => new List<string> { "Димитър", "Елена" };
}

// ✅ За нуждите на Бързи Тестове (Unit Testing) можем да създадем фалшив доставчик без база:
public class MockDatabase : IStudentDataProvider
{
    public List<string> FetchStudents() => new List<string> { "Тестов Студент 1", "Тестов Студент 2" };
}

// ✅ Стъпка 3: Високото ниво зависи ЕДИНСТВЕНО от абстракцията
public class DecoupledDashboard
{
    private readonly IStudentDataProvider _dataProvider;

    // Конструкторно инжектиране (Dependency Injection под капака)
    // .NET Core автоматично ще подаде правилния клас, конфигуриран в Program.cs
    public DecoupledDashboard(IStudentDataProvider dataProvider)
    {
        _dataProvider = dataProvider; // Обръщане на контрола!
    }

    public void PrintReport()
    {
        var students = _dataProvider.FetchStudents(); // Работим с чистия договор
        foreach (var s in students) 
        {
            Console.WriteLine(s);
        }
    }
}
```

## 🚨 КРИТИЧНИ JUNIOR КАПАНИ (Част 2)

* **Капан №3: Лъжливото `NotImplementedException`:** Всеки път, когато се хванеш, че оставяш метод празен или пишеш `throw new NotImplementedException();` само за да успокоиш компилатора, защото наследяваш "дебел" интерфейс или родителски клас — **Спри веднага!** Нарушаваш едновременно **Liskov Substitution** и **Interface Segregation**. Разбий софтуерния договор на по-малки, имунни части.
* **Капан №4: Наличие на `new` за бизнес услуги:** В съвременната уеб и десктоп архитектура (ASP.NET Core / Web API), бизнес услугите (`Services`) и слоевете за данни (`Repositories`) **никога** не трябва да се инстанцират ръчно с ключовата дума `new` вътре в твоите контролери или мениджъри. Остави IoC контейнера в `Program.cs` да управлява жизнения им цикъл (`Transient`, `Scoped`, `Singleton`) и да ги инжектира чисто.
