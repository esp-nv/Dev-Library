# 📘 Глава 5: SOLID Принципи под капака (Част 1)

**Статус:** Нов архитектурен модул | **Цел:** Писане на нечуплив и гъвкав софтуер

## 🟥 1. S – Single Responsibility Principle (Единствена отговорност)

### ❓ Какъв проблем решава?
Спира създаването на т.нар. **"God Classes" (Класове-Богове)** – огромни файлове по 2000 реда код, които правят всичко: смятат оценки, четат от базата, пращат имейли и записват файлове. Когато промениш логиката за имейлите, без да искаш чупиш оценките.

### 💡 Аналогия от живота
**Швейцарско ножче срещу специализирани инструменти.** Швейцарското ножче има всичко, но ако му се счупи тирбушонът, трябва да хвърлиш целия инструмент. По-добре е да имаш отделен нож, отделен тирбушон и отделна отвертка.

### 🎯 Приложение в StudentManagement
Всеки клас трябва да има **само една причина да бъде променян**.
* **Анти-модел (Junior грешка):** Клас `StudentService`, който изчислява средния успех, сглобява SQL заявка и записва Log файл на диска.
* **Правилен модел:** `Student` (държи само данните), `StudentRepository` (говори с базата), `LoggerService` (записва грешките).

### 🛠️ Практически пищов
```csharp
// ❌ ГРЕШНО: Този клас отговаря за бизнес логика И за файлова система
public class StudentManager
{
    public void RegisterStudent(Student student)
    {
        // 1. Логика за запис в базата...
        // 2. Логване във файл:
        File.WriteAllText("log.txt", \$"Студент {student.Name} е регистриран.");
    }
}

// ✅ ПРАВИЛНО: Разделяне на две независими отговорности
public class StudentRepository 
{
    public void Save(Student student) { /* Само запис в DB */ }
}

public class LoggerService
{
    public void Log(string message) { File.WriteAllText("log.txt", message); }
}
```

## 🟩 2. O – Open/Closed Principle (Отворен / Затворен)

### ❓ Какъв проблем решава?
Спира безкрайното рязане и модифициране на работещ код всеки път, когато клиентът поиска нова функционалност. Променянето на готов код е най-честият източник на нови бъгове.

### 💡 Аналогия от живота
**Слотове за разширение на компютър (PCI Express / USB).** Когато искаш да добавиш нова видеокарта или да включиш мишка, ти не отваряш процесора с поялник, за да преправяш архитектурата му. Компютърът е *затворен за промяна*, но *отворен за разширение* чрез портовете.

### 🎯 Приложение в StudentManagement
Кодът трябва да е **отворен за разширение (Extension), но затворен за модификация (Modification)**. Постига се чрез **Интерфейси**.

### 🛠️ Практически пищов
```csharp
// ❌ ГРЕШНО: При всеки нов формат трябва да разрязваме този метод и да добавяме "case"
public class ReportGenerator
{
    public void Generate(string type)
    {
        if (type == "PDF") { /* Код за PDF */ }
        else if (type == "Excel") { /* Код за Excel */ }
    }
}

// ✅ ПРАВИЛНО: Използваме полиморфизъм. За нов формат просто пишем нов клас!
public interface IReport
{
    void Export();
}

public class PdfReport : IReport { public void Export() { /* PDF логика */ } }
public class ExcelReport : IReport { public void Export() { /* Excel логика */ } }

// Този клас е ЗАТВОРЕН за промяна. Той работи с абстракцията.
public class ReportEngine
{
    public void ProcessReport(IReport report) => report.Export();
}
```

## 🚨 КРИТИЧНИ JUNIOR КАПАНИ

* **Капан 1: "Предозиране" с класове (Over-engineering):** Не разцепвай класовете прекалено фанатично. Ако направиш отделен файл за един единствен ред код (напр. `class FirstNameValidator`), кодът ще стане толкова разхвърлян, че няма да можеш да го дебъгваш. Спазвай баланса.
* **Капан 2: Скритите if-else лабиринти:** Всеки път, когато се хванеш, че пишеш дълъг `switch` или `if-else` блок, проверяващ текстови низове за определяне на типа обект, ти нарушаваш **Open/Closed** принципа. Замени го с интерфейс.

## 🟨 3. L – Liskov Substitution Principle (Заменяемост на Лисков)

### ❓ Какъв проблем решава?
Спира създаването на грешни и принудителни наследявания. Ако един наследник не може да изпълни наследеното поведение от родителя и хвърля `NotImplementedException`, софтуерната архитектура се чупи при полиморфизъм.

### 💡 Аналогия от живота
**Електрическа играчка срещу жива патица.** Ако имаш родителски клас `Duck` (Патица) и негов наследник `ToyDuck` (Гумена патица), но гумената патица изисква батерии, за да плува, тогава замяната на жива патица с гумена в езерото ще доведе до проблем. Ако изглежда като патица и квака като патица, но се нуждае от батерии – наследяването вероятно е грешно.

### 🎯 Приложение в StudentManagement
Всеки подклас (наследник) трябва да може да замени своя базов (родителски) клас, без това да счупи програмата.
* **Анти-модел (Junior грешка):** Създаване на клас `OnlineCourse`, който наследява `BaseCourse`, но хвърля грешка в метода `GetClassroom()`, защото онлайн курсовете нямат физическа стая.
* **Правилен модел:** Изнасяне на специфичното поведение в интерфейси (напр. `IPhysicalCourse`) или разделяне на базовите класове.

### 🛠️ Практически пищов
```csharp
// ❌ ГРЕШНО: Наследникът чупи логиката на родителя и програмата гърми!
public class BaseCourse
{
    public virtual string GetClassroom() => "Стая 301";
}

public class OnlineCourse : BaseCourse
{
    public override string GetClassroom() 
        => throw new NotImplementedException("Онлайн курсовете нямат стая!");
}

// ✅ ПРАВИЛНО: Интерфейсна сегментация, която гарантира сигурност
public class Course { /* Общи данни за курса */ }

public interface IPhysicalCourse { string GetClassroom(); }

public class InPersonCourse : Course, IPhysicalCourse
{
    public string GetClassroom() => "Стая 301";
}

public class HybridCourse : Course, IPhysicalCourse { public string GetClassroom() => "Стая 102"; }
public class ZoomCourse : Course { /* Няма физическа стая */ }
```

## 🟦 4. I – Interface Segregation Principle (Разделяне на интерфейсите)

### ❓ Какъв проблем решава?
Спира създаването на "дебели" интерфейси-чудовища. Когато един интерфейс съдържа твърде много методи, класовете, които го имплементират, са принудени да пишат празен код за методи, които изобщо не са им нужни.

### 💡 Аналогия от живота
**Силно специализирано меню в ресторант.** Ако отидеш в кафене само за еспресо, не искаш сервитьорът да те задължава да си поръчаш и тристепенно месно меню, просто защото всичко е пакетирано в един общ "Договор за храна". Искаш менюто за напитки да е отделно.

### 🎯 Приложение в StudentManagement
По-добре много малки и специализирани интерфейси, отколкото един голям и всеобхватен.
* **Анти-модел:** Интерфейс `IStudentActions`, съдържащ `.SubmitHomework()`, `.GradeHomework()`, `.PayTuitionFee()`. Студентът не може да оценява домашни, а преподавателят не плаща такси.
* **Правилен модел:** Разделяне на `IHomeworkSubmitter`, `IGrader` и `IPayer`.

### 🛠️ Практически пищов
```csharp
// ❌ ГРЕШНО: Преподавателят е принуден да имплементира метод за плащане на такси
public interface IUserActions
{
    void Teach();
    void PayTuition();
}

// ✅ ПРАВИЛНО: Малки, силно специализирани (атомарни) интерфейси
public interface ITeacher { void Teach(); }
public interface IStudent { void PayTuition(); }

public class Professor : ITeacher
{
    public void Teach() { /* Преподава лекция */ }
}
```

## 🟪 5. D – Dependency Inversion Principle (Обръщане на зависимостите)

### ❓ Какъв проблем решава?
Елиминира бруталното и твърдо "заваряване" (High Coupling) между отделните софтуерни слоеве. Без този принцип, ако контролерът ти зависи директно от конкретен клас за база данни, всяка промяна по SQL сървъра изисква пренаписване на уеб интерфейса.

### 💡 Аналогия от живота
**Електрическият контакт в стената.** Твоят лаптоп не е запоен директно за кабелите на електропреносната мрежа в стената. Между тях има абстракция – контакт. Благодарение на контакта, в него можеш да включиш както лаптоп, така и прахосмукачка или настолна лампа. И двете страни зависят от профила на контакта (абстракцията).

### 🎯 Приложение в StudentManagement
**Най-важният принцип за Dependency Injection (DI) в ASP.NET Core.** Класовете от високо ниво (Контролери) не трябва да зависят от класовете от ниско ниво (SQL класове). И двата типа трябва да зависят от абстракции (Интерфейси).

### 🛠️ Практически пищов
```csharp
// ❌ ГРЕШНО: Контролерът е твърдо обвързан с конкретен SQL клас. Не може да се тества!
public class StudentController
{
    private SqlStudentRepository _repo = new SqlStudentRepository(); // Брутална грешка под капака
}

// ✅ ПРАВИЛНО: Контролерът работи само с интерфейс. Истинският клас се инжектира отвън!
public interface IStudentRepository { List<Student> GetAll(); }

public class StudentController
{
    private readonly IStudentRepository _repository;

    // Конструкторно инжектиране (Dependency Injection)
    public StudentController(IStudentRepository repository)
    {
        _repository = repository;
    }
    
    public void Display() => _repository.GetAll();
}
```

## 🚨 КРИТИЧНИ JUNIOR КАПАНИ (Част 2)

* **Капан 1: Лъжливото NotImplementedException:** Ако се усетиш, че пишеш празен метод или хвърляш `NotImplementedException` само за да задоволиш компилатора за даден интерфейс или родителски клас – спри! Веднага нарушаваш **Liskov Substitution** или **Interface Segregation**. Разбий интерфейса на по-малки части.
* **Капан 2: Ръчното създаване на обекти с `new`:** В ASP.NET Core бизнес услугите (`Services`) и репозиторитата (`Repositories`) **никога** не трябва да се създават с ключовата дума `new` вътре в контролерите. Остави IoC контейнерът в `Program.cs` да ги създава и подава автоматично чрез конструктора.
