## 1. ПЪЛЕН СПЕКТЪР НА LINQ ОПЕРАЦИИТЕ В EF CORE

Когато извличаме обекти от базата данни, LINQ изразите се групират в пет архитектурни категории според еквивалентния SQL код, който генерират:

*   **Филтриране (Filtering):** Използва метод `.Where(condition)` ➔ Превежда се като `WHERE` клауза в SQL.
*   **Проекция (Projection):** Използва метод `.Select(x => new { ... })` ➔ Превежда се като точно изброяване на колони след думичката `SELECT` (избягва прахосването на памет с `SELECT *`).
*   **Агрегация (Aggregation):** Методи като `.Count()`, `.Sum()`, `.Max()`, `.Average()` ➔ Изпълняват се директно от ядрото на SQL Server, връщайки само едно крайно единично число по мрежата.
*   **Обединяване (Joining):** Операции като `.Join()` или разширената `.SelectMany()` ➔ Превеждат се като мощни нативни `INNER JOIN / LEFT JOIN` заявки между свързани таблици.
*   **Пагинация (Partitioning):** Съчетание от методите `.Skip(X).Take(Y)` ➔ Генерира светкавично странициране чрез `OFFSET X ROWS FETCH NEXT Y ROWS ONLY` в MS SQL Server.

## 2. ГОЛЕМИЯТ СБЛЪСЪК В ПАМЕТТА: IENUMERABLE СРЕЩУ IQUERYABLE

Разбирането кога точно една софтуерна заявка напуска сървъра ни и кога се материализира в RAM паметта е разликата между работещо приложение и забит сървър на изпит:

### А. IQueryable (Изпълнение в базата данни — Server-Side)
Докато веригата ти е от тип `IQueryable`, ти не работиш с реални данни, а изграждаш текстов план на заявката. 
*   Ако напишеш три филтъра `.Where()`, те се лепят един за друг. Базата данни ще получи само една обща SQL заявка и ще филтрира редовете на диска чрез индексите си.
*   **Кога се материализира:** Заявката се изпраща към SQL Server **ЕДВА** тогава, когато извикаш материализиращ метод: **`.ToList()`**, **`.ToArray()`**, **`.FirstOrDefault()`** или завъртиш данните в `foreach` цикъл.

### Б. IEnumerable (Изпълнение в паметта на приложението — Client-Side Капан)
Ако превърнеш заявката в `IEnumerable` (или извикаш `.AsEnumerable()` твърде рано във веригата), ти извършваш софтуерно престъпление срещу паметта:
*   EF Core спира да дописва SQL кода. Той изпраща незабавно `SELECT *` към SQL Server, изтегля **абсолютно всички милиони редове по мрежата** и ги набива в RAM паметта на твърдия ти диск. Всяко следващо филтриране, което си написала след това, се прави бавно от C# процесора, обхождайки масиви в паметта.

> **Златно правило:** Винаги държи заявката като `IQueryable` възможно най-дълго и слагай `.ToList()` или `.ToArray()` чак на самия ѝ край!

## 3. ТРИ СТРАТЕГИИ ЗА ЗАРЕЖДАНЕ НА РЕЛАЦИИ (LOADING TYPES)

Когато работим с релационни таблици, Entity Framework Core ни предоставя три различни софтуерни подхода за изтегляне на свързаните обекти (децата) от базата данни:

### А. Eager Loading (Предварително зареждане)
Изискваме свързаните данни изрично още по време на първоначалната LINQ заявка чрез метода `.Include()`.
*   **Как работи:** EF Core генерира една обща, мощна `LEFT JOIN` заявка към SQL Server и връща родителя заедно с децата с един единствен мрежов ход.
*   **Кога се използва:** Когато със сигурност знаем, че софтуерът ни ще има нужда от данните на съседната таблица веднага в текущия бизнес контекст.

### Б. Explicit Loading (Изрично/Следващо зареждане)
Изтегляме обекта-родител напълно чист от базата данни, а по-късно, само при специфично бизнес условие в кода, извикваме децата насила по мрежата.
*   **Как работи:** Използват се служебните методи `context.Entry(parent).Collection(p => p.Children).Load();` за колекции или `.Reference().Load();` за единични обекти. Извършва се втора самостоятелна заявка към SQL Server.

### В. Lazy Loading (Мързеливо зареждане)
Свързаните данни не се теглят първоначално от диска, но в момента, в който се опиташ да прочетеш свойството в кода (напр. `student.Course.Name`), EF Core скрито спира работата на нишката и прави нова фонова заявка към SQL Server на място.
*   **Как работи:** Изисква инсталиране на NuGet пакета `Microsoft.EntityFrameworkCore.Proxies` и маркиране на всички навигационни свойства с ключовата дума `virtual`.
*   **Критичен капан (Проблемът N+1):** Ако завъртиш 100 студенти в `foreach` цикъл и прочетеш името на курса им чрез Lazy Loading, системата ще извърши **101 отделни заявки по мрежата** към SQL Server, което ще срине тотално производителността на уеб сървъра.

## 4. КОНКУРЕНТЕН ДОСТЪП И ЗАЩИТА (CONCURRENCY CHECKS)

В силно натоварени системи възниква казусът с **Едновременната промяна (Concurrency)**. Ако Оператор А и Оператор Б заредят едновременно от базата данни един и същ продукт с наличност `10` бройки в паметта си:
1.  Оператор А продава 3 бройки и записва наличност `7` в SQL.
2.  Една милисекунда след това Оператор Б (който все още вижда старите `10` в своя браузър) продава 2 бройки и записва в SQL наличност `8`.
3.  *Резултат:* Промяната на Оператор А се презаписва незаконно, наличността се счупва и бизнесът губи пари.

За да се предостави защита, се използва **Оптимистичен конкурентен контрол (Optimistic Concurrency)**.

### Налагане на защита чрез Data Attributes (`[Timestamp]`):
Добавяме специално свойство (обикновено масив от байтове), което SQL Server обновява автоматично с нов уникален хеш при всяка една модификация на реда:

```csharp
using System.ComponentModel.DataAnnotations;

public class Product
{
    public int Id { get; set; }
    public int Stock { get; set; }

    [Timestamp] // Автоматична RowVersion колона в SQL Server за Concurrency проверка
    public byte[] RowVersion { get; set; } = null!;
}
```

### Как ни пази защитата в C# кода:
Когато извикаш `.SaveChanges()`, EF Core добавя старата версия на RowVersion в `WHERE` клаузата на `UPDATE` заявката: `UPDATE Products SET Stock = 8 WHERE Id = 1 AND RowVersion = @OldVersion;`. 

Ако Оператор А вече е променил реда, версията в SQL Server ще е различна, заявката на Оператор Б ще засегне `0` редове и EF Core моментално ще хвърли изключение **`DbUpdateConcurrencyException`**, спасявайки данните от презаписване!
