## 🏛️ 1. ЗАЩО НИ Е НУЖЕН SQL SERVER (Какъв проблем решава?)

В релационните бази данни е критично **да не дублираме информация** и да съхраняваме данните в строго структуриран вид. Вместо да пазим името на курса, цената му и името на лектора във всеки отделен ред за всеки студент, ние разделяме данните в отделни таблици и ги свързваме чрез ключове.

### 💡 Аналогия от живота
**Гардероб с кутии за обувки.** Вместо да държиш обувките си разхвърляни по пода, ти купуваш кутии. Всяка кутия си има уникален етикет-номер (`PK` - Първичен ключ). На твоя лист-дневник (`Students`) ти не рисуваш обувката – просто записваш: *„Обувки за бягане → виж в Кутия №1“* (`CourseId` - Външен ключ).

## 📊 2. МИСЛОВНАТА СТЪЛБА: СИНТАКТИЧНА ПОДРЕДБА НА SQL

Когато пишеш или четеш SQL заявка, ти я изграждаш по следната максимална стандартна подредба (стълба). Не всяка задача изисква всички стъпки, но редът им е закован:

```text
  1. SELECT     --> [ Какво точно искам да покажа на екрана? ]
  2. FROM       --> [ От коя основна таблица тръгвам? ]
  3. JOIN / ON  --> [ Кои съседни таблици добавям и по какъв ключ? ]
  4. WHERE      --> [ Кои конкретни сурови РЕДОВЕ оставям (Филтър)? ]
  5. GROUP BY   --> [ По коя колона искам да разделя данните на ГРУПИ? ]
  6. HAVING     --> [ Кои от вече създадените ГРУПИ искам да оставя? ]
  7. ORDER BY   --> [ Как да сортирам крайния резултат (ASC / DESC)? ]
```

### 🧠 Как четем логически готов SQL код (Посока на мисълта):
```text
 FROM (Откъде?) ──> JOIN (Свързвам ли?) ──> WHERE (Редове?) ──> GROUP BY (Групи?) ──> HAVING (Групи филтър?) ──> SELECT (Покажи) ──> ORDER BY (Сортирай)
```

## 🔤 3. МОСТЪТ МЕЖДУ СВЕТОВЕТЕ: SQL SERVER ТИПОВЕ ДАННИ ──> C#

При Code-First подход или при проектиране на таблици (като в `StudentManagement` и `EnterpriseReportSystem`), мапингът на типовете данни определя производителността на паметта:

| SQL Server Тип данни | C# Тип данни | Какъв проблем решава / Къде се използва? |
| :--- | :--- | :--- |
| **`INT`** | `int` | За стандартни броячи, вътрешни числа и Идентификатори (`Id`). |
| **`BIGINT`** | `long` | За огромни числа (над 2 милиарда записи). |
| **`DECIMAL(18,2)`**| `decimal` | **Парични и точни стойности.** Задължителен за суми и баланси! |
| **`BIT`** | `bool` | Съхранява само `0` (False) или `1` (True). (напр. `IsActive`). |
| **`VARCHAR(n)`** | `string` | Текст на латиница (заема 1 байт на символ). |
| **`NVARCHAR(n)`** | `string` | **Unicode текст. Задължителен за кирилица (български имена)!** |
| **`DATETIME2`** | `DateTime` | Модерен, точен стандарт за дата и час (напр. `CreatedAt`). |
| **`UNIQUEIDENTIFIER`**| `Guid` | Глобално уникален идентификатор (`Guid.NewGuid()`). |

### 🛡️ Управление на NULL стойности (Nullable Types):
Ако в SQL колоната е дефинирана като `NULL` (може да няма стойност), в C# стойността **задължително** трябва да бъде nullable:
*   SQL: `Age INT NULL` \(\longrightarrow\) C#: `public int? Age { get; set; }`
*   SQL: `Price DECIMAL(18,2) NULL` \(\longrightarrow\) C#: `public decimal? Price { get; set; }`

## 🔀 4. СВЕЩЕНИЯТ ГРААЛ НА JOIN ЗАЯВКИТЕ (Визуални Схеми)

### 🤝 A. INNER JOIN (Само пълните съвпадения)
Връща записи, само ако стойността на външния ключ съществува и в двете таблици. Ако има несъвпадение, редовете отпадат.

```text
   Таблица A (Students)             Таблица B (Courses)
 ┌─────────────────────┐          ┌─────────────────────┐
 │    Alex (Course 1)  │ ────────>│  1. C# Advanced     │  🎯 ИЗХОД:
 │   Maria (Course 1)  │ ────────>│                     │  - Alex -> C# Advanced
 │    Ivan (Course 99) │ ───X     │  2. ASP.NET Core    │  - Maria -> C# Advanced
 └─────────────────────┘          └─────────────────────┘
 (Ivan отпада, защото курс 99 липсва в Таблица B)
```

### ⬅️ B. LEFT JOIN (Всичко отляво + каквото съвпадне отдясно)
Връща **абсолютно всички** записи от лявата таблица (`Students`), независимо дали имат записан курс. Ако нямат, връща `NULL`.

```text
   Таблица A (Students)             Таблица B (Courses)
 ┌─────────────────────┐          ┌─────────────────────┐
 │    Alex (Course 1)  │ ────────>│  1. C# Advanced     │  🎯 ИЗХОД:
 │   Maria (Course 1)  │ ────────>│                     │  - Alex -> C# Advanced
 │    Ivan (Course 99) │ ────────>│  [ NULL / Няма ]    │  - Maria -> C# Advanced
 └─────────────────────┘          └─────────────────────┘  - Ivan -> NULL
 (Ivan ОСТАВА в крайния резултат, системата не го изхвърля!)
```

## 🔒 5. СИГУРНОСТ НА ДАННИТЕ: TRANSACTION, COMMIT И ROLLBACK

Когато извършваме критични промени (CRUD операции като `UPDATE` и `DELETE`), ние ги обвиваме в **Трансакция**, за да ги третираме като едно цяло и да имаме право на заден ход, ако сгрешим.

```text
  BEGIN TRANSACTION ──> Изпълняваме Удар (DELETE/UPDATE) ──> Проверяваме (SELECT)
                                                                    │
                                          ┌─────────────────────────┴─────────────────────────┐
                                      Доволни сме?                                       Има грешка?
                                          │                                                   │
                                          ▼                                                   ▼
                                       COMMIT                                              ROLLBACK
                                [ Запази трайно в DB ]                              [ Отмени и върни назад ]
```

### 🛠️ Практически пищов за Безопасно изтриване:
```sql
BEGIN TRANSACTION;

-- Изтриваме конкретен клиент
DELETE FROM Orders WHERE CustomerId = 5;

-- Преди да е станало късно, проверяваме какво сме направили:
SELECT * FROM Orders WHERE CustomerId = 5;

-- Ако сме изтрили нещо грешно:
ROLLBACK; -- Базата се връща в начално състояние!

-- Ако всичко е перфектно:
-- COMMIT;
```

🔎 5.5. СИЛАТА НА WILDCARDS (Търсене по шаблон с LIKE)


❓ Какъв проблем решава?

Елиминира ограничението на оператора за точно равенство (=). Ако потребителят не помни точното име на клиента, а знае само, че започва с "Ма" или съдържа "ан", операторът LIKE, съчетан с Wildcards (специални символи), позволява гъвкаво търсене по частичен текст.

💡 Аналогия от живота

Търсене на дума в хартиена кръстословица. Знаеш, че думата има 5 букви, започва с „К“ и завършва на „А“ (К _ _ _ А). Ти не знаеш кои са средните букви, но шаблонът ти помага да намериш съвпадения като „КНИГА“, „КЪЩА“ или „КА какао“.

🛠️ Практически пищов: Символи, Код и Изход

В SQL Server има 4 основни Wildcard символа. Ето как работят съчетани с NVARCHAR (кирилица):

Символ	Какво означава логически?	Пример в SQL	Какво ще намери като изход?
%	Нула или повече произволни символи.	WHERE Name LIKE N'Ма%'	Всички, започващи с Ма: Мария, Мартин, Марио.
%	Текстът може да е навсякъде.	WHERE Name LIKE N'%ан%'	Всички, съдържащи "ан": Иван, Ананас, Снежана.
_	Точно един произволен символ.	WHERE Name LIKE N'П_т_р'	Изрази с точно 5 букви: Петър, Петар.
[]	Един символ от изброения списък.	WHERE Name LIKE N'[МИ]ва%'	Започващи с М или И: Милен, Иван, Ивайло.
[^]	Един символ, който НЕ е в списъка.	WHERE Name LIKE N'[^М]%	Всички имена, които НЕ започват с буквата М.

sql
-- ПРИМЕР: Търсим студенти, чието име съдържа "ив" и са активни
SELECT Id, Name, Grade 
FROM Students 
WHERE Name LIKE N'%ив%' AND IsActive = 1;
Use code with caution.

🖥️ Реален резултат на екрана (Output):

text
┌────┬──────────┬───────┐
│ Id │ Name     │ Grade │
├────┼──────────┼───────┤
│ 1  │ Ивайло   │ 5.80  │
│ 4  │ Живко    │ 4.50  │
└────┴──────────┴───────┘
Use code with caution.

🚨 КЪДЕ ЩЕ НИ ДАДЕ ГРЕШКИ И КАК ДА ГИ ОПРАВИМ ВЕДНАГА?

Ето най-честите ситуации, при които търсачката ти ще върне грешка или празен екран, и точните софтуерни решения за по-бързо ориентиране:

❌ Ситуация А: Счупен синтаксис (Грешка на компилатора)

• Код с грешка: SELECT * FROM Students WHERE Name LIKE [Ма%];
• Грешка в конзолата: Msg 102, Level 15: Incorrect syntax near '%'.
• Защо гърми: Забравила си да обвиеш целия шаблон в единични кавички ' '. Квадратните скоби без кавички се възприемат като име на колона, а не като текст.
• Как се оправя веднага: Обвиваш израза правилно: LIKE N'[Ма]%'

❌ Ситуация Б: Търсене на реални символи % или _ (Граничен случай)

• Казус: Имаш таблица с промоционални кодове (напр. Промо_10%, Бонус_5%). Искаш да намериш всички кодове, съдържащи символа %.
• Код с логическа грешка: SELECT * FROM Coupons WHERE Code LIKE '%%';
• Защо не работи: SQL Server се обърква, защото мисли средния процент за Wildcard и ти изплюва всички възможни редове от таблицата.
• Как се оправя веднага (Чрез ESCAPE): Използваш наклонена черта (или друг символ) и указваш, че тя „нулира“ силата на процента:sql
SELECT * FROM Coupons WHERE Code LIKE '%\%%' ESCAPE '\';
-- Първият и последният % са шаблони, а средният \% е реалният знак за процент!
Use code with caution.

❌ Ситуация В: Търсачката връща празен екран (Празен Изход)

• Ситуация: Пишеш WHERE Name LIKE 'Мария', знаеш, че в базата има такава студентка, но екранът остава празен.
• Защо се случва: Ако колоната в SQL е дефинирана като фиксиран CHAR(10), а името е „Мария“ (5 букви), SQL Server автоматично допълва останалите 5 позиции с празни пространства ('Мария     '). Точното равенство или шаблон без процент накрая няма да я намери.
• Как се оправя веднага: Добавяш процент накрая, за да обхванеш скритите празни пространства: LIKE N'Мария%'.

## ❌ 6. ВНИМАНИЕ: 6-ТЕ КРИТИЧНИ SQL КАПАНИ

*   **Капан №1 (UPDATE/DELETE без WHERE):** Ако напишеш `UPDATE Students SET Grade = 6;` без клауза `WHERE`, SQL Server ще подмени оценката на **абсолютно всички студенти** в базата данни! Винаги подсигурявай с `WHERE Id = ...`.
*   **Капан №2 (WHERE срещу HAVING):** `WHERE` филтрира суровите редове *преди* те да бъдат групирани. `HAVING` филтрира вече готовите групи *след* `GROUP BY` въз основа на агрегати (напр. `HAVING SUM(Price) > 500`).
*   **Капан №3 (Забравеният Unicode Префикс `N`):** При търсене на кирилица в `NVARCHAR` колона, задължително слагай префикса `N` пред текста: `WHERE Name = N'Мария'`. Без него SQL Server може да превърне символите в питанки (`???`).
*   **Капан №4 (Невалидни колони в `GROUP BY`):** Ако използваш `GROUP BY Customer`, в секцията `SELECT` имаш право да покажеш само колоната `Customer` ИЛИ агрегатни функции (`SUM`, `COUNT`). Извикването на произволна колона като `Date` ще счупи заявката.
*   **Капан №5 (`Reverse` не е Сортиране):** Функцията `Reverse()` в SQL просто обръща текста огледално. За обръщане на реда на редовете винаги използвай `ORDER BY ... DESC`.
*   **Капан №6 (Изчезване на данни при INNER JOIN):** Ако правиш статистика за студенти по курсове с `INNER JOIN`, всички студенти без избран курс (`NULL`) ще бъдат тихо изтрити от резултата. За отчети винаги залагай на `LEFT JOIN`.
