## 1. АРХИТЕКТУРА НА СВЪРЗВАНЕТО (КЛЮЧОВЕ И ОГРАНИЧЕНИЯ)

В релационните бази данни основната цел е премахването на дублирането на данни (Нормализация). Моделирането стъпва на два фундаментални инструмента:

*   **`PK` (Primary Key / Първичен ключ):** Уникалният идентификатор (ЕГН) на всеки ред. Той автоматично създава `Clustered Index` и физически подрежда данните на диска.
*   **`FK` (Foreign Key / Външен ключ):** Колона, която пази стойността на `PK` от съседна таблица, налагайки релационен интегритет ( Referential Integrity ) — базата няма да позволи да запишеш несъществуващ номер на курс.

### Видове правила за изтриване (Delete Behaviors) на ниво SQL Server:
1.  **`ON DELETE CASCADE`:** Ако изтриеш ред от главната таблица (напр. `Course`), SQL Server автоматично изтрива всички свързани редове в подчинената таблица (`Students`).
2.  **`ON DELETE RESTRICT / NO ACTION`:** Спира изтриването на главния ред и хвърля грешка, ако в подчинената таблица има поне един свързан запис. Това пази бизнес историята от заличаване.
3.  **`ON DELETE SET NULL`:** Изтрива главния ред, а във външния ключ на подчинените записи автоматично записва `NULL` (изисква колоната да е Nullable).

## 2. ФИЗИЧЕСКО ЗАЕМАНЕ НА ПАМЕТТА (ROW ANATOMY)

Всеки избор на тип данни в `CREATE TABLE` определя колко реда ще се поберат в една **8 KB (8192 байта) дискова страница (Data Page)** в SQL Server. Колкото по-оптимални са колоните, толкова по-малко дискови операции (I/O) извършва сървърът.

Когато запишеш ред в таблица, SQL Server го разделя в паметта на две основни зони:
*   **Fixed-Length зона (Фиксирана дължина):** Всички колони с постоянен размер (`INT`, `BIGINT`, `BIT`, `DATETIME2`, `UNIQUEIDENTIFIER`) се записват плътно една до друга. Базата данни знае точния байтов адрес на всяка колона и я чете веднага.
*   **Variable-Length зона (Променлива дължина):** Всички динамични колони (`VARCHAR`, `NVARCHAR`, `VARBINARY`) се записват в края на реда, придружени от **2-байтов указател (Offset Array)**, описващ къде свършва всяка стойност.

```text
+---------------+------------------+------------------+------------------------+------------------------+

| Row Header    | Fixed Columns    | Null Bitmap      | Variable Offset Array  | Variable Data          |
| (4 байта)     | (INT=4B, BIT=1B) | (1 бит на колона)| (2 байта на колона)    | (N'Иван' = 8 байта)    |
+---------------+------------------+------------------+------------------------+------------------------+
```

### Сравнение на типовете текстово съхранение:
*   **`CHAR(n)` срещу `VARCHAR(n)`:** `CHAR(10)` заделя твърдо 10 байта, дори да запишеш само 2 символа. `VARCHAR(100)` заделя само реалната дължина на текста + 2 байта служебна информация.
*   **Префиксът `N` (Unicode):** В SQL Server `VARCHAR` заема 1 байт на символ (само латиница), докато `NVARCHAR` използва 2 байта (UTF-16) и е **задължителен за поддръжка на кирилица**. Ако пропуснеш префикса `N` при запис на български текст (напр. `N'Иван'`), базата данни ще запише символи с питанки (`????`).

## 3. ЧЕСТИ ГРЕШКИ, КАПАНИ И КАК ДА ГИ ИЗБЕГНЕМ

### Грешка 1: Масово използване на напълно случайни GUID идентификатори
* **Какво се случва:** Използваш стандартен `UNIQUEIDENTIFIER` (`Guid.NewGuid()`) като Primary Key с Clustered Index. Тъй като стойностите са напълно случайни, всеки нов запис се вмъква произволно по средата на дисковата страница, вместо накрая. Това води до масови **Page Splits** (разцепване на страници), фрагментира индексите и забавя операциите по запис с до 40%.
* **Как да избегнеш:** В съвременния .NET 9+ използвай последователни UUID v7 (`Guid.CreateVersion7()`), а на ниво SQL Server – функцията `NEWSEQUENTIALID()`, които подреждат новите записи хронологично най-отзад.

### Грешка 2: Скрит Page Split при неправилен ъпдейт на `VARCHAR`
* **Какво се случва:** Създаваш колона `NVARCHAR(200)` и първоначално записваш празен низ `''` (2 байта). По-късно през C# обновяваш записа с текст от 150 символа (302 байта). Ако страницата е вече пълна с други редове, този нов обем не може да се събере и базата данни е принудена да извърши тежък Page Split на диска.
* **Как да избегнеш:** За колони, които често се разширяват драстично, подсигурявай добър фактор на запълване на индекса (Fill Factor).
