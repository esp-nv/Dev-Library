## 1. КАКВО ПРЕДСТАВЛЯВА SOFT DELETE И КАК РАБОТИ СОФТУЕРНО

В стандартния Entity Framework Core, ако извикаш метода `.Remove()`, базата данни изпълнява сурова `DELETE FROM` команда и данните изчезват физически от диска. В продукционни финансови, банкови и ERP системи това е напълно забранено, тъй като се нарушава бизнес одитът (Audit Trail) и се губи историята.

При **Soft Delete (Логическо изтриване)** данните остават непокътнати на твърдия диск. Вместо физическо триене, таблицата съдържа допълнителна булева колона (например `IsDeleted` или `IsActive`), която служи за маркиране на записа:

*   **Нормален статус:** `IsDeleted = 0 (False)` ➔ Записът е активен и достъпен за потребителите.
*   **Изтрит статус:** `IsDeleted = 1 (True)` ➔ Записът се счита за заличен от бизнес гледна точка, но остава архивиран в SQL Server.

Предизвикателството при този подход е, че програмистът трябва ръчно да пише `.Where(x => !x.IsDeleted)` във всяка една заявка в контролерите си. Ако забрави филтъра на едно единствено място, изтритите данни ще „изтекат“ в потребителския интерфейс. За да предотвратим този капан, използваме **Глобални филтри за търсене (Global Query Filters)** директно на ниво конфигурация на DbContext.

## 2. НАЛАГАНЕ НА ФИЛТРИ ПРЕЗ MODELBUILDER В ONMODELCREATING

За да наложим глобално правило, използваме метода `.HasQueryFilter()` в конфигурацията на съответното Entity. По този начин казваме на EF Core: *"Всеки път, когато някой чете от тази таблица, винаги добавяй това логическо условие"*.

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    base.OnModelCreating(modelBuilder);

    // Глобален филтър за автоматично скриване на изтритите трансакции
    modelBuilder.Entity<AssetTransaction>()
        .HasQueryFilter(t => !t.IsDeleted); // ➔ SQL: WHERE is_deleted = 0
}
```

### 🔄 Какво се случва зад кулисите:
Когато в твоя уеб контролер или сървиз извикаш чиста LINQ заявка без никакви филтри:
```csharp
var activeTransactions = context.AssetTransactions.ToList();
```
EF Core автоматично прихваща заявката и я превежда към SQL Server с принудително дописана клауза:
```sql
SELECT [id], [amount], [is_deleted]
FROM asset_transactions
WHERE is_deleted = 0; -- Добавено на софтуерно ниво зад кулисите!
```

## 3. НАПРЕДНАЛИ РЕЛАЦИОННИ ФИЛТРИ (ФИЛТРИРАНЕ ПРЕЗ РОДИТЕЛ)

Един от най-тежките капани при Soft Delete е свързан с детайлните таблици (децата). Ако маркираш една основна трансакция-родител като изтрита (`IsDeleted = true`), нейните детайлни стойности (`AssetAttributeValue`) все още имат `IsDeleted = false` в своята таблица. Ако потребителят направи заявка директно към детайлите, те ще се визуализират, въпреки че родителят им е изтрит!

За да предотвратим това, налагаме **Релационна защита през навигационното свойство**:

```csharp
// ТВОЯТА НАПРЕДНАЛА ЗАЩИТА: Автоматично скриване на детайлите, ако главната им трансакция-родител е Soft Deleted
modelBuilder.Entity<AssetAttributeValue>()
    .HasQueryFilter(av => !av.Transaction.IsDeleted); // Обхожда връзката и проверява флага на родителя
```

Сега, дори в детайлната таблица записите да са активни, EF Core автоматично ще направи `JOIN` заявка към родителя и ще ги скрие, ако трансакцията е била логически изтрита.

## 4. КАК ДА ПРОБИЕМ ЗАЩИТАТА НАСИЛА (IGNOREQUERYFILTERS)

Има специфични администраторски или одиторски ситуации, в които системата трябва да прочете насила абсолютно всички данни от диска, включително и логически изтритите (например в кошчето за възстановяване на записи или при финансова ревизия).

За да заобиколим глобалния филтър за конкретна LINQ заявка, използваме метода **`.IgnoreQueryFilters()`**:

```csharp
// Връща абсолютно всички записи от диска, пробивайки софтуерната защита на DbContext
var allTransactionsIncludingDeleted = context.AssetTransactions
    .IgnoreQueryFilters() // Изключва автоматичното дописване на WHERE IsDeleted = 0
    .Where(t => t.Amount > 1000)
    .ToList();
```
