## 1. ОБЩАТА КАРТИНА НА ПОТОКА ДАННИ В ORM АРХИТЕКТУРАТА

Когато създаваме софтуер чрез Code-First подход, жизненият път на модела преминава през строго определени технологични етапи от нашето C# приложение до физическата база данни:

```text
 C# Class ➔ Entity ➔ Mapping ➔ DbContext ➔ Table + Columns ➔ DbSet ➔ LINQ ➔ EF Core ➔ SQL ➔ Database
```

Всеки C# клас, предназначен за съхранение, се нарича **Entity (Домейн модел)**. Преди обаче да се генерира реалната таблица, трябва изрично да посочим правилата за превод на свойствата (Properties) към SQL колони (Columns).

---

## 2. ТРИТЕ НАЧИНА ЗА MAPPING: СРАВНИТЕЛЕН АНАЛИЗ И ПРАВИЛА ЗА ИЗБОР

Entity Framework Core предоставя три коренно различни инструмента за дефиниране на правилата на базата данни:

### А. Convention / Auto Mapping (Конвенции по подразбиране)
Не пишем никакъв конфигурационен код. Оставяме EF Core сам да анализира имената и типовете на C# класа и да се досети за структурата в SQL.
*   **Именуване:** Клас `Product` автоматично се превежда в таблица `Products`. Свойство `Id` или `ProductId` автоматично става `Primary Key` и `Identity(1,1)`.
*   **Кога се използва:** При стандартни проекти, където имената в C# и SQL съвпадат напълно и липсват специфични бизнес ограничения.
*   **Мисловно правило:** *„Ако всичко следва стандартния шаблон ➔ оставям EF Core сам да свърши работата.“*

### Б. Data Attributes (Анотации на данни)
Пишем конфигурационните правила под формата на метаданни (атрибути в квадратни скоби) изрично над самия C# клас или над неговите свойства.
*   **Пример в кода:** `[Table("store_products")]` над класа и `[Column("product_name")]`, `[MaxLength(50)]`, `[Required]` над свойствата.
*   **Кога се използва:** При по-малки проекти или прости структури, където искаме да виждаме правилата на базата директно на място върху самите свойства.
*   **Мисловно правило:** *„Искам да знам как се мапва колоната в същия момент, в който чета C# свойството.“*

### В. Fluent API (Конфигуриране чрез ModelBuilder)
Държим Entity класа напълно чист от атрибути (чист POCO клас). Всички сложни релации, ограничения, типове памет и индекси се разписват чрез програмни методи вътре в специалния метод `OnModelCreating` в нашия `DbContext`.
*   **Пример в кода:** `modelBuilder.Entity<Product>().ToTable("store_products");`
*   **Кога се използва:** Инженерен стандарт за средни, големи и корпоративни системи. Задължителен при сложни връзки (`Many:Many`), съставни ключове, индекси и когато искаме пълно разделение на отговорностите (Separation of Concerns).
*   **Мисловно правило:** *„C# класът описва само бизнес обекта, а Fluent API описва изцяло как той се превежда към реалния SQL Server.“*

## 3. МИСЛОВНА КАРТА: ОТ FLUENT API КЪМ СУРОВ SQL (РЕД ПО РЕД)

Ето как се мапва софтуерната верига от C# до физическия SQL Server:

```csharp
modelBuilder.Entity<Product>()                   // ➔ SQL: CREATE TABLE [име]
    .ToTable("store_products");                  // ➔ SQL: ... store_products (Преименува таблицата)

modelBuilder.Entity<Product>()                   // ➔ SQL: (Конфигурираме колона вътре в таблицата)
    .Property(p => p.Price)                      // ➔ SQL: Взима C# свойството Price...
    .HasColumnName("product_price")              // ➔ SQL: ... и го преименува на колона [product_price]
    .HasColumnType("decimal(18,2)")              // ➔ SQL: ... със строго фиксиран тип DECIMAL(18,2) - Задължителен за пари!
    .HasDefaultValue(0.00)                       // ➔ SQL: DEFAULT 0.00 (Ако няма стойност, записва 0.00)
    .IsRequired();                               // ➔ SQL: NOT NULL (Полето става задължително!)
```

### Двупосочен превод (Съпоставка в таблица)

| Fluent API Метод в C# | Еквивалентна клауза в SQL Server | Какво се случва физически на диска? |
| :--- | :--- | :--- |
| `.ToTable("store_products")` | `CREATE TABLE store_products` | Преименува таблицата на ниво реална база данни. |
| `.HasKey(p => p.Id)` | `PRIMARY KEY (Id)` | Създава първичен ключ и автоматично изгражда `Clustered Index`. |
| `.Property(p => p.Name)` | `[Name]` | Избира конкретното C# свойство за последваща конфигурация. |
| `.HasColumnName("product_name")` | `product_name` | Променя заглавието на самата колона във физическия SQL Server. |
| `.HasMaxLength(50)` | `NVARCHAR(50)` | Налага твърд лимит в байтове на диска (Unicode поддръжка за кирилица). |
| `.IsRequired()` | `NOT NULL` | Забранява празни (`NULL`) стойности за този конкретен запис. |
| `.IsRequired(false)` | `NULL` | Позволява колоната в базата данни да бъде празна и незадължителна. |
| `.HasDefaultValue(true)` | `DEFAULT 1` | SQL автоматично записва `1` (True), ако C# не подаде изрична стойност. |

## 4. БЪРЗА СЪПОСТАВКА НА ТРИТЕ ПОДХОДА ЧРЕЗ РЕАЛЕН КОД

Искаме да свържем C# клас с таблица `store_products`, като колоната `product_name` е ограничена до 50 символа и е задължителна (`NOT NULL`):

### 1. Подход чрез Convention / Auto Mapping (Чист, но изисква пълно съвпадение)
```csharp
// Изисква таблицата в SQL да се казва абсолютно по същия начин ("Products")
public class Product
{
    public int Id { get; set; } // Автоматично става Primary Key в SQL
    public string Name { get; set; } 
    public decimal Price { get; set; }
}
```

### 2. Подход чрез Data Attributes (Конфигуриране на място в класа)
```csharp
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;

[Table("store_products")] // Променя името на таблицата в SQL
public class Product
{
    [Key] // Изричен първичен ключ
    [Column("product_id")]
    public int Id { get; set; }

    [Required] // Прави колоната NOT NULL
    [MaxLength(50)] // NVARCHAR(50) на ниво SQL Server за поддръжка на кирилица
    [Column("product_name")]
    public string Name { get; set; }

    [Column("product_price")]
    public decimal Price { get; set; }
}
```

### 3. Подход чрез Fluent API (Инженерен стандарт — чист модел + правила в DbContext)
```csharp
// 1. Entity класът остава 100% чист и независим от архитектурата на базата (POCO)
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
}

// 2. Правилата се разписват в OnModelCreating метода на твоя DbContext
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Product>()
        .ToTable("store_products");

    modelBuilder.Entity<Product>()
        .HasKey(p => p.Id);

    modelBuilder.Entity<Product>()
        .Property(p => p.Name)
        .HasColumnName("product_name")
        .HasMaxLength(50)
        .IsRequired(); // Налага NOT NULL в SQL Server

    // decimal(18,2) в SQL Server - Задължителна точна стойност за пари и баланси
    modelBuilder.Entity<Product>()
        .Property(p => p.Price)
        .HasColumnName("product_price")
        .HasColumnType("decimal(18,2)")
        .IsRequired();
}
```

## 5. МИСЛОВЕН НАРЪЧНИК ЗА ПРАКТИЧЕСКА ПОСЛЕДОВАТЕЛНОСТ

За да предотвратиш объркване, фрагментация и пропуснати полета, преминавай през следния златни чеклист всеки път, когато създаваш или променяш модел данни в C#:

*   **Стъпка 1: Деклариране на Entity класа** — Дефинирай чистия C# клас и свойства със съответните им софтуерни типове.
*   **Стъпка 2: Валидация на съвпадението** — Провери дали имената на класа и свойствата съвпадат напълно с колоните в SQL. Ако не, избери изричен подход за Mapping.
*   **Стъпка 3: Мапинг на ниво таблица (Entity ➔ Table)** — Конфигурирай точното име на реалната таблица на диска в `OnModelCreating`.
*   **Стъпка 4: Мапинг на ниво свойства (Property ➔ Column)** — Обходи свойствата едно по едно и дефинирай техните SQL имена, максимални дължини (`HasMaxLength`) и задължителност (`IsRequired`).
*   **Стъпка 5: Регистрация в контекста (DbSet)** — Добави свойство `DbSet<T>` в своя `DbContext` клас, за да кажеш на EF Core, че това е официален набор от данни.

## 6. ЧЕСТИ ГРЕШКИ, КАПАНИ И КАК ДА ГИ ИЗБЕГНЕМ

### Капан 1: Изчезване на празния конструктор при въвеждане на параметри
*   **Какво се случва:** Създаваш конструктор с параметри в твоето Entity (напр. `public Product(string name) { ... }`) с цел по-лесно инстанциране. Пускаш приложението и то забива фатално.
*   **Грешка на екрана:** `InvalidOperationException: Each entity type requires a parameterless constructor.`
*   **Защо се случва:** Когато EF Core извлича данни от SQL Server, той трябва да създаде празен софтуерен обект и да го напълни ред по ред. Ако в класа имаш конструктор с параметри, C# автоматично скрива фабричния празен конструктор и EF Core губи възможност да инстанцира обекта.
*   **Как да избегнеш:** Винаги изрично дописвай по един празен конструктор `public Product() { }` под твоя нов конструктор с параметри.

### Капан 2: Ръчно триене на локални файлове в папка Migrations
*   **Какво се случва:** Решаваш, че последната ти миграция не ти харесва, отваряш Solution Explorer и изтриваш физическите `.cs` файлове на миграцията с десен бутон. Проектът ти се обърква тотално и спира да приема нови миграции.
*   **Защо се случва:** Вътрешният двигател на EF Core следи историята на промените чрез специален служебен модел и служебна SQL таблица (`__EFMigrationsHistory`). Когато изтриеш файлове за миграция на ръка, ти нарушаваш синхронизацията между кода и базата данни.
*   **Как да избегнеш:** Никога не трий миграционни файлове ръчно! Винаги използвай официалната PMC команда **`Remove-Migration`** — тя ще премахне локалния файл безопасно и ще изчисти служебния модел автоматично.
