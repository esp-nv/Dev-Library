## 🏛️ 1. ЗАЩО Е ВАЖЕН ТОЗИ ФАЙЛ (Какъв проблем решава?)

В големи бизнес системи (като ERP и финансови платформи), `ApplicationDbContext` не е просто списък с таблици.
Той работи като **Централен команден пункт и Пазител на сигурността**. 

Вместо да разчитаме, че потребителят или уеб контролерите винаги ще въвеждат данните правилно,
този файл налага **железни глобални правила и бизнес защити** директно на ниво Entity Framework Core,
преди данните да стъпят физически в SQL Server

### 🗺️ Визуална схема на архитектурния поток:
```text
   [ UI / Уеб Контролер ] ──> Заявка за промяна (Add / Update / Delete)
                                        │
                                        ▼
                     ┌──────────────────────────────────────┐
                     │        ApplicationDbContext          │
                     ├──────────────────────────────────────┤
                     │ 1. Сканира паметта (ChangeTracker)   │
                     │ 2. Извиква EnforceGlobalTheme...     │ ──> [ Блокира промяна на Тема 1 ]
                     │ 3. Налага Глоб. Филтри (QueryFilter) │ ──> [ Скрива Soft Deleted записи ]
                     └──────────────────────────────────────┘
                                        │
                               ( base.SaveChanges() )
                                        │
                                        ▼
                             [ Физически SQL Server ]
```

## 🛡️ 2. РАЗГЛОБЯВАНЕ НА ТРИТЕ НАПРЕДНАЛИ ЗАЩИТИ (Как работят?)

### ⚓ Защита А: Жизнен цикъл на SaveChanges (Theme Protection)
Ти си пренаписала (overridden) методите `SaveChanges()` и `SaveChangesAsync()` . Преди EF Core да запише каквото и да е в SQL, данните задължително преминават през твоя частен метод `EnforceGlobalThemeProtection()`.

*   **Как работи в кода:** Чрез `ChangeTracker` програмата проверява дали има обекти от тип `GlobalTheme` в състояние `Modified` или `Deleted`. Ако тяхното `Id == 1`, C# моментално блокира операцията и хвърля `InvalidOperationException`.
*   **Защо е направено:** За да се гарантира, че потребител или администратор няма случайно да счупи интерфейса на сайта, изтривайки фабричната Bootstrap котва-тема №1, около която е изграден дизайнът.

### 🚫 Защита Б: Глобално спиране на Каскадно триене (Cascade Delete Restriction)
В метода `OnModelCreating` ти си написала динамичен `foreach` цикъл, който претърсва абсолютно всички дефинирани връзки (Foreign Keys) в проекта:
```csharp
foreach (var foreignKey in modelBuilder.Model.GetEntityTypes().SelectMany(e => e.GetForeignKeys()))
{
    foreignKey.DeleteBehavior = DeleteBehavior.Restrict;
}
```
*   **Как работи софтуерно:** Подменя стандартното поведение на EF Core към **`DeleteBehavior.Restrict`** .
*   **Защо е направено:** **Счетоводна сигурност.** Ако изтриеш `Region`, SQL Server по подразбиране ще изтрие автоматично всички градове и трансакции в него. Благодарение на този Restrict филър, SQL Server ще откаже изтриването, ако в тази локация има направена дори една финансова операция в миналото. Данните са защитени от случайно заличаване.

### 🕵️ Защита В: Глобални филтри за Скриване (Soft Delete)
```csharp
modelBuilder.Entity<AssetTransaction>().HasQueryFilter(t => !t.IsDeleted);
modelBuilder.Entity<AssetAttributeValue>().HasQueryFilter(av => !av.Transaction.IsDeleted);
```
*   **Как работи софтуерно:** Когато в контролера напишеш `context.AssetTransactions.ToList()`,
*      EF Core автоматично дописва към SQL заявката клаузата `WHERE IsDeleted = 0` зад кулисите.
*      Втората ти защита автоматично скрива детайлните стойности (`AssetAttributeValue`), ако тяхната главна трансакция-родител е била маркирана като изтрита.
*   **Защо е направено:** Данните във финансовите системи никога не се трият реално от диска.
*       Те просто се маркират като "изтрити" през булево свойство, а филтърът гарантира, че те няма да се виждат в интерфейса на потребителя.

## 🧱 3. ЧИСТ ОРГАНИЗАЦИОНЕН МОДЕЛ (ApplyConfigurations)

Ако се чудиш защо в този голям файл няма дълги свитъци от Fluent API правила за дължина на колоните и ограничения, виж този вълшебен ред:
```csharp
modelBuilder.ApplyConfigurationsFromAssembly(typeof(ApplicationDbContext).Assembly);
```
*   **Какво означава:** Използвала си най-модерния архитектурен подход в .NET! Вместо да пълниш `ApplicationDbContext` с хиляди редове Fluent API код,
*   тази команда казва на EF Core: *"Отиди в проекта, намери всички отделни класове, които имплементират интерфейса `IEntityTypeConfiguration<T>`,
*    и им зареди специфичните правила автоматично"*. Така този файл остава чист и прегледен.

## 🛠️ 4. НАРЪЧНИК ЗА ПРЕРАБОТКА (Как да действаш при промяна?)

### ➕ Ситуация 1: Добавяне на Нова Таблица (Entity)
Ако създадеш нов C# клас (напр. `Warehouse.cs`), трябва да го регистрираш като `DbSet` в горната част на файла под съответния коментар,
за да поддържаш твоя перфектен визуален ред :
```csharp
public DbSet<Warehouse> Warehouses { get; set; } = null!;
```

### 🛡️ Ситуация 2: Добавяне на нов Soft Delete филтър за друга таблица
Ако утре направиш таблицата `Facilities` да поддържа Soft Delete (добавиш ѝ свойство `IsDeleted`), 
трябва да отидеш в най-долната част на метода `OnModelCreating` и да допишеш:
```csharp
modelBuilder.Entity<Facility>().HasQueryFilter(f => !f.IsDeleted);
```
готов код: 
```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
    {

        base.OnModelCreating(modelBuilder);

        // ЖЕЛЯЗНО ПРАВИЛО: Автоматично сканиране и зареждане на всички конфигурационни класове от папката
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(ApplicationDbContext).Assembly);

        // ГЛОБАЛНО ПРЕДОТВРАТЯВАНЕ НА КАСКАДНО ТРИЕНЕ ЗА СИГУРНОСТ НА ДАННИТЕ
        foreach (var foreignKey in modelBuilder.Model.GetEntityTypes().SelectMany(e => e.GetForeignKeys()))
        {
            foreignKey.DeleteBehavior = DeleteBehavior.Restrict;
        }

        // Глобален филтър за скриване на изтритите трансакции през Soft Delete
        modelBuilder.Entity<AssetTransaction>().HasQueryFilter(t => !t.IsDeleted);

        // ТВОЯТА НОВА СЧЕТОВОДНА ЗАЩИТА: Автоматично скриване на детайлите, ако главната трансакция е Soft Deleted
        modelBuilder.Entity<AssetAttributeValue>().HasQueryFilter(av => !av.Transaction.IsDeleted);

    }
```

🔌 1. ЗАЩО СЪЩЕСТВУВАТ ТЕЗИ ЗАЩИТИ (Какъв проблем решават?)

В стандартния EF Core, ако изтриеш даден запис, той изчезва завинаги от диска, а ако изтриеш запис-родител (напр. Град), базата данни автоматично изтрива и всички свързани записи (напр. Финансови трансакции в този град). В реалния бизнес софтуер това е фатално.
Този шаблон решава три основни проблема:
1. Предотвратява случайно изтриване на критични системни настройки (котви), без които дизайнът на приложението ще се счупи.
2. Забранява каскадното заличаване на финансова история (налага бизнес сигурност).
3. Скрива данните от потребителя, без реално да ги трие от диска (Soft Delete), запазвайки одиторската следа.

🗺️ Схема на защитния филтър (Преди SaveChanges):

text
  [ C# Код / Контролер ] ──> Заявка за промяна (Add/Update/Delete)
                                        │
                                        ▼
                     ┌──────────────────────────────────────┐
                     │          ApplicationDbContext        │
                     ├──────────────────────────────────────┤
                     │ 1. Сканира паметта (ChangeTracker)   │
                     │ 2. Извиква EnforceGlobalProtection() │ ──> [ Проверява защитени ID-та ]
                     │ 3. Налага Глоб. Филтри (QueryFilter) │ ──> [ Автоматично WHERE IsDeleted=0 ]
                     └──────────────────────────────────────┘
                                        │
                               ( base.SaveChanges() )
                                        │
                                        ▼
                             [ Физически SQL Server ]
Use code with caution.

❌ 4. УЧЕБНИ КАПАНИ: КЪДЕ МОЖЕ ДА СГРЕШИМ?

• Капан №1 (Четене на изтрити данни насила): Използвайте метода .IgnoreQueryFilters() в LINQ заявката, за да изключите филтъра за изтрити записи при нужда.
• Капан №2 (Проблемът с Restrict при миграции): Тъй като каскадното триене е забранено, подсигурявайте софтуерно проверки в контролерите преди триене.
