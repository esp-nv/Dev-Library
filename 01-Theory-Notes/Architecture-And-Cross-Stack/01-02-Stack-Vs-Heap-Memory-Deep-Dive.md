## 1. СРАВНЕНИЕ МЕЖДУ STACK И HEAP ПАМЕТТА

Оперативната памет (RAM), заделена за приложението от операционната система, се разделя логически на две основни структури:

| Характеристика | Stack (Стек памет) | Heap (Купчина памет) |
| :--- | :--- | :--- |
| **Структура от данни** | LIFO (Last-In, First-Out) — силно подредена кула от кутии (Stack Frames). | Неподредено, свободно разпределено пространство (глобален склад). |
| **Управление / Скорост** | Светкавично бърза. СУБД/Runtime заделя и трие памет автоматично при влизане и излизане от метод. | По-бавна. Изисква търсене на свободно място на адреса и управление от Garbage Collector-а. |
| **Размер** | Силно ограничен (обикновено фиксиран до 1 MB на нишка по подразбиране в .NET). | Много голям (ограничен изцяло от наличната свободна RAM памет на машината). |
| **Жизнен цикъл** | Кратък — паметта на променливите се изчиства веднага щом текущият метод приключи работа. | Дълъг — обектите живеят там, докато има поне един активен указател към тях. |

## 2. VALUE ТИПОВЕ СРЕЩУ REFERENCE ТИПОВЕ В ПАМЕТТА

Данните в съвременните езици се делят според начина им на съхранение:
*   **Value Types (Типове по стойност — `int`, `bool`, `double`, `struct`):** Пазят реалната си стойност директно там, където са декларирани. Ако са локални променливи в метод, те живеят изцяло в Stack-а.
*   **Reference Types (Референтни типове — `class`, `string`, `array`):** Пазят само адреса (указателя) в Stack паметта, докато самият реален обект се заделя в свободното пространство на Heap-а.

```csharp
// ============================================================
// ПРИМЕР: РАЗПРЕДЕЛЕНИЕ НА ПАМЕТТА В C#
// ============================================================
public void ProcessData()
{
    int size = 50;                     // Value Type -> стойността 50 отива в Stack Frame
    string message = "Hello";          // Reference Type -> указателят е в Stack, текстът е в Heap
    
    User current = new User("Ivan");   // Reference Type -> обектът User е в Heap, адресът му е в Stack
}
```

## 3. КАК РАБОТИ GARBAGE COLLECTOR-ЪТ (GC)

В среди с управляван код (.NET CLR, Java JVM) разработчикът не трие паметта ръчно. За това се грижи **Garbage Collector (GC)**, който периодично почиства Heap паметта:

1. **Маркиране (Mark):** GC тръгва от "корените" на приложението (активни Stack Frame променливи, статични обекти) и маркира всички обекти в Heap-а, до които има достъп.
2. **Изчистване (Sweep):** Всички немаркирани обекти (достъпът до които е изгубен) се изтриват от Heap-а.
3. **Компактиране (Compact):** За да избегне фрагментация (дупки в паметта), GC премества оцелелите обекти един до друг, осигурявайки последователно свободно пространство.

## 4. ЧЕСТИ ГРЕШКИ, КАПАНИ И КАК ДА ГИ ИЗБЕГНЕМ

### Грешка 1: Изтичане на памет (Memory Leak) чрез статични събития (Events)
* **Какво се случва:** Абонираш краткотраен обект към събитие на дълготраен (`static`) клас и забравяш да го отпишеш (`-=`). Статичният клас пази указател към обекта в Heap-а, GC вижда активната референция и никога не го изтрива, което пълни паметта.
* **Как да избегнеш:** Винаги прекратявай абонамента за събития, когато обектът вече не е необходим (например в `Dispose()` метода).

### Грешка 2: Безкрайна рекурсия (StackOverflowException)
* **Какво се случва:** Извикваш метод рекурсивно, без да подсигуриш правилно крайно условие. На всяко извикване се добавя нов Stack Frame. Паметта от 1 MB свършва за части от секундата и приложението се срива фатално.
* **Как да избегнеш:** Винаги тествай дъното на рекурсивните алгоритми. При дълбоки структури предпочитай итеративни цикли (`while`, `for`).
