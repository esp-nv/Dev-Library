## 1. ЗЛАТНОТО ПРАВИЛО ЗА ИЗБОР (МАТРИЦА ЗА БЪРЗА ДИАГНОСТИКА)

Изборът на правилната база данни се определя от характера на бизнес изискванията на твоето приложение:

| Бизнес сценарий | Подходящ избор | Основна архитектурна причина |
| :--- | :--- | :--- |
| Данните имат **много сложни връзки** и изискват **100% точност** (транзакции, банкови сметки, финализиране на поръчки). | **SQL (Postgres / MS SQL)** | Гарантира пълно съответствие с ACID правилата и поддържа мощни `JOIN` заявки. |
| Всеки запис съдържа **различни характеристики** или динамични полета (продуктови каталози, потребителски профили, CMS платформи, логове). | **Document NoSQL (MongoDB)** | Гъвкава и отворена схема (Schema-less) — данните се пазят като JSON/BSON обекти. |
| Изисква се **максимална скорост (< 1 ms)** за временни или силно натоварени данни (кеширане, потребителски сесии в RAM, виртуални колички). | **Key-Value Cache (Redis)** | Данните живеят директно в RAM паметта на сървъра, елиминирайки дисковия достъп. |

## 2. СРАВНИТЕЛЕН АНАЛИЗ НА ПАРАДИГМИТЕ: ACID СРЕЩУ BASE

Релационните и нерелационните технологии се управляват от две коренно различни софтуерни философии:

| Архитектурен критерий | SQL Парадигма ➔ ACID (Сигурност) | NoSQL Парадигма ➔ BASE (Скорост и Мащаб) |
| :--- | :--- | :--- |
| **Главен приоритет** | Абсолютна точност на данните и предотвратяване на разминавания. | Постоянна наличност (Availability) и мигновена скорост при милиони заявки. |
| **Схема на таблиците** | **Строго фиксирана** — първо дефинираш таблица, колони и точни типове данни. | **Гъвкава (Schema-less)** — базата приема нови полета директно по време на запис. |
| **Релации и Връзки** | Вградени на софтуерно ниво чрез силно оптимизирани `JOIN` операции. | Избягват се напълно — данните се вграждат (Embed) директно вътре в обекта. |
| **Мащабиране (Scaling)** | **Вертикално** — добавяне на повече мощност (RAM/CPU) на един основен сървър. | **Хоризонтално** — лесно разпределяне на данните в клъстер от много евтини сървъри. |

## 3. СИМУЛАЦИЯ НА ЕДНА И СЪЩА ЗАЯВКА В 4 РАЗЛИЧНИ БАЗИ

**Задача:** Да се извлекат активните потребители на възраст над 18 години, сортирани по име, като се вземат само първите 10 записа.

### MS SQL Server (T-SQL)
```sql
SELECT TOP 10 Id, Name 
FROM Users 
WHERE Age >= 18 AND IsActive = 1 
ORDER BY Name ASC;
```

### PostgreSQL
```sql
SELECT id, name 
FROM users 
WHERE age >= 18 AND is_active = true 
ORDER BY name ASC 
LIMIT 10;
```

### MongoDB (JSON / Shell)
```json
db.users.find(
    { age: { \$gte: 18 }, isActive: true }, 
    { name: 1 }
).sort({ name: 1 }).limit(10);
```

### Redis (Key-Value — Директно четене по ключ)
```bash
GET user:101
```

## 4. ЧЕСТИ ГРЕШКИ, КАПАНИ И КАК ДА ГИ ИЗБЕГНЕМ

### Грешка 1: Избор на FLOAT или DOUBLE за финансови операции и пари
* **Какво се случва:** Използваш тип `FLOAT` в SQL или `double` в C# за съхранение на парични баланси. Поради спецификата на стандарта IEEE 754 за плаваща запетая, базата започва да прави грешки при закръгляне (`0.1 + 0.2` става `0.30000000000000004`), което води до финансови дефицити в отчетите.
* **Как да избегнеш:** В SQL винаги ползвай `DECIMAL(18,2)` / `NUMERIC(18,2)`, а в C# – типа `decimal`.

### Грешка 2: Използване на Redis като единствена и основна база данни
* **Какво се случва:** Базираш цялата система единствено на Redis, без релационна база зад него. Тъй като Redis пази данните основно в RAM паметта на сървъра, при внезапен рестарт, спиране на тока или хардуерна авария рискуваш да загубиш критични данни.
* **Как да избегнеш:** Използвай Redis изцяло като **кеширащ слой (Cache)** пред стабилна персистентна база данни (SQL или MongoDB).

### Грешка 3: Игнориране на малките и главните букви в PostgreSQL (Case Sensitivity)
* **Какво се случва:** Създаваш таблица с име `Users` (с главна буква) в PostgreSQL през C# код. Когато се опиташ да пуснеш сурова SQL заявка `SELECT * FROM Users`, Postgres хвърля грешка, че таблицата не съществува, защото по подразбиране превръща всичко в малки букви (`users`).
* **Как да избегнеш:** В PostgreSQL винаги използвай `snake_case` конвенция за именуване на таблици и колони (напр. `user_orders`, `is_active`).
