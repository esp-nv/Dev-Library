## 1. КАК ДА СЕ ЗАПОМНИ И ЧЕТЕ ПО-ЛЕСНО (МНЕМОНИКА)

*   **Dynamic Programming = „Умна рекурсия, която си записва в тефтерче“:** Представи си, че ти дам лист с надпис `1 + 1 + 1 + 1 + 1` и те питам колко прави. Ти броиш и казваш: *„5“*. После дописвам още едно `+ 1` отдясно и питам колко прави сега. Ти не броиш отначало — просто казваш *„6“*, защото **помниш отговора от предишната стъпка**!
*   **Кога една задача се решава с Dynamic Programming? (Двете златни правила):**
    1.  **Overlapping Subproblems (Припокриващи се подзадачи):** Едни и същи малки сметки се повтарят десетки или милиони пъти (например `fib(3)` се смята многократно).
    2.  **Optimal Substructure (Оптимална подструктура):** Най-доброто решение на голямата задача се сглобява директно от най-добрите решения на по-малките ѝ части.

## 2. ДВАТА ПОДХОДА В DP (TOP-DOWN СРЕЩУ BOTTOM-UP) И БЛОК-СХЕМА

```text
1. TOP-DOWN (MEMOIZATION = Рекурсия + Кеш речник):
   Започваш от голямата цел fib(5) ➔ слизаш надолу до fib(0) и fib(1)
   ➔ на връщане записваш всеки отговор в memo[n], за да не го смяташ втори път!

2. BOTTOM-UP (TABULATION = Цикъл for + Масив dp[]):
   Започваш от дъното:
   dp[0] = 0 ──► dp[1] = 1 ──► dp[2] = 1 ──► dp[3] = 2 ──► dp[4] = 3 ──► dp[5] = 5
   (Няма рекурсия, няма Call Stack, попълваш таблицата стъпка по стъпка!)
```

## 3. АРХИТЕКТУРНО СРАВНЕНИЕ: TOP-DOWN (MEMOIZATION) СРЕЩУ BOTTOM-UP (TABULATION)

| Критерий | Top-Down (Memoization) | Bottom-Up (Tabulation) |
| :--- | :--- | :--- |
| **Механизъм** | Рекурсия + Hash Map / `@cache` | Итеративен цикъл (`for`) + Масив `dp[]` |
| **Посока на мислене** | От крайната цел N надолу към базовия случай | От базовия случай (`0, 1`) нагоре към N |
| **Изчислява ли ненужни състояния?** | **Не** (смята само нужните подзадачи) | **Да** (попълва цялата таблица подред) |
| **Риск от Stack Overflow** | **Да** (при дълбочина > 1000 в Python) | **Не** (използва обикновен цикъл) |
| **Оптимизация на паметта** | Трудна (пази целия кеш + Call Stack) | **Лесна** (често пази само последните 2 реда/числа → O(1)) |
| **Инструменти по езици** | Python: `@functools.cache`; C#/JS: `Dictionary`/`Map` | Масив `dp` в Python, C# и JavaScript |

## 4. ПЛЮСОВЕ И МИНУСИ НА DYNAMIC PROGRAMMING

### 🟢 Предимства (Pros):
*   **Превръща невъзможни задачи във възможни:** Сваля времевата сложност от експоненциална \(O(2^n)\) (която при n=50 отнема 35 години) до полиномиална O(n) или O(n²) (която минава за 0.001 секунди!).
*   **100% гаранция за глобален оптимум:** За разлика от алчните алгоритми (Greedy), DP проверява всички възможни състояния и гарантирано намира най-добрия отговор (напр. при произволни монети в Coin Change).

### 🔴 Недостатъци (Cons):
*   **Трудно намиране на рекурентната зависимост (State Transition):** Най-сложната част е да измислиш как да дефинираш състоянието `dp[i]` и формулата за преход между състоянията.
*   **По-висок разход на RAM памет:** Изисква пазене на 1D или 2D таблица с междинни резултати.

## 5. КОДОВ ОДИТ: НАИВНА РЕКУРСИЯ \(O(2^n)\) СРЕЩУ DP O(n)

### ❌ ГРЕШЕН КОД (Наивна рекурсия без мемоизация — \(O(2^n)\) катастрофа):
```python
def fib_exponential(n: int) -> int:
    # 🚨 ГРЕШКА: При n = 45 функцията прави над 3 милиарда рекурсивни извиквания
    # и забива процесора за близо минута!
    if n <= 1:
        return n
    return fib_exponential(n - 1) + fib_exponential(n - 2)
```
*   **Как да се избегне:** Добави кеширане (Memoization) или пренапиши задачата с цикъл отдолу нагоре (Tabulation) с две променливи.

### 🟢 ПРАВИЛЕН КОД (Bottom-Up DP с O(n) време и O(1) памет):
```python
def fib_optimal(n: int) -> int:
    if n <= 1:
        return n

    prev2, prev1 = 0, 1
    for _ in range(2, n + 1):
        current = prev1 + prev2
        prev2, prev1 = prev1, current

    return prev1
```

## 6. ИНТЕРВЮ КАПАНИ, ВЪПРОСИ И УЛОВКИ

*   **Въпрос на интервюто:** *„Каква е разликата между **0/1 Knapsack** (Целочислена раница, където предметите не могат да се режат) и **Unbounded Knapsack / Coin Change** (където можеш да вземеш един и същ предмет/монета неограничен брой пъти), и как това променя посоката на вътрешния цикъл при 1D оптимизацията на паметта?“*
*   **Уловката:** Това е един от най-известните капани на технически интервюта — разликата е само в посоката на обхождане на капацитета (`for w in range(...)`)!
*   **Точен Senior отговор:** 
    1.  **При 0/1 Knapsack (всеки предмет се ползва най-много 1 път):** Когато оптимизираме таблицата до едномерна `dp[w]`, вътрешният цикъл за капацитета **задължително върви НАЗАД (от `W` надолу към `weight`)**. Така гарантираме, че при смятането на `dp[w]` четем стойности от **предишния ред** и не използваме един и същ предмет два пъти!
    2.  **При Unbounded Knapsack / Coin Change (неограничени монети):** Вътрешният цикъл върви **НАПРЕД (от `coin` нагоре към `amount`)**. Така умишлено позволяваме `dp[w]` да стъпи върху вече обновена стойност от текущия ред, което означава *„Вземи още една монета от същия номинал“*!
