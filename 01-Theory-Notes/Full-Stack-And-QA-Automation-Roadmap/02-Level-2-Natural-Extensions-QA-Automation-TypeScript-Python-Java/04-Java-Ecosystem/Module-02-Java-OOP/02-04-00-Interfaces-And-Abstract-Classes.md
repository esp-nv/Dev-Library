## 1. КАК ДА СЕ ЗАПОМНИ И ЧЕТЕ ПО-ЛЕСНО (МНЕМОНИКА)

*   **Абстрактен клас = Недовършен чертеж на къща (`IS-A` родство):** Има общи стени и покрив (полета със състояние и готови методи), но оставя една стая празна (`abstract void decorate()`), която всеки наследник трябва да обзаведе по свой вкус. Не можеш да построиш директно недовършения чертеж (`new AbstractClass()` е забранено).
*   **Интерфейс = Договор / Контакт в стената (`CAN-DO` способност):** Контактът в стената не знае дали в него ще включиш лаптоп, тостер или прахосмукачка — стига уредът да спазва стандарта за щепсел (`implements Plugable`), той ще работи!
*   **Скритите модификатори в Java интерфейс:**
    *   Всички полета в интерфейс са автоматично **`public static final`** (константи).
    *   Всички обикновени методи без тяло са автоматично **`public abstract`**.

## 2. АРХИТЕКТУРНА РАЗЛИКА: `ABSTRACT CLASS` СРЕЩУ `INTERFACE` (БЛОК-СХЕМА)

```text
           ┌───────────────────────────────────────────────────────────┐
           │ КОГА ДА ИЗПОЛЗВАМ ABSTRACT CLASS СРЕЩУ INTERFACE?         │
           └─────────────────────────────┬─────────────────────────────┘
                                         │
          ┌──────────────────────────────┴──────────────────────────────┐
          ▼                                                             ▼
┌───────────────────────────────────┐   ┌───────────────────────────────────────┐
│ ABSTRACT CLASS (Базов модел)      │   │ INTERFACE (Договор за поведение)      │
│ • Има полета със състояние        │   │ • Няма инстанционни полета (само const)│
│ • Има конструктори                │   │ • Няма конструктори                   │
│ • Наследява се САМО ЕДИН (extends)│   │ • Имплементират се МНОГО (implements) │
│ • Може да има protected/private   │   │ • Има default/static/private методи   │
└───────────────────────────────────┘   └───────────────────────────────────────┘
```

## 3. СРАВНИТЕЛНА КАРТА В 4 ЕЗИКА (JAVA, C#, PYTHON, JAVASCRIPT)

| Концепция | ☕ Java 21+ | 🟣 C# 12+ (.NET) | 🐍 Python 3.x | 🟡 JavaScript / TypeScript |
| :--- | :--- | :--- | :--- | :--- |
| **Дефиниция на интерфейс** | `interface Payable { ... }` | `interface IPayable { ... }` | `class Payable(ABC):` / `Protocol` | `interface Payable` (само в TS) |
| **Именна конвенция** | Без `I` (`Payable`, `Runnable`) | Задължително с `I` (`IPayable`) | Без `I` (`Payable`) | Без `I` в модерния TS |
| **Имплементация** | `class Card implements Payable` | `class Card : IPayable` | `class Card(Payable):` | `class Card implements Payable` (TS) |
| **Абстрактен клас** | `abstract class Shape` | `abstract class Shape` | `class Shape(ABC):` | `abstract class Shape` (само в TS) |
| **Метод с готова логика в интерфейс** | `default void log() { ... }` | `void Log() { ... }` (C# 8+) | Обикновен метод в `ABC` | Няма |
| **Функционален интерфейс** | `@FunctionalInterface` (1 метод) | Делегат (`Func<T>`, `Action<T>`) | `Callable[[int], str]` | Function type `(x: number) => void` |

## 4. ПЛЮСОВЕ И МИНУСИ НА ИНТЕРФЕЙСИТЕ И АБСТРАКТНИТЕ КЛАСОВЕ

### 🟢 Предимства (Pros):
*   **Пълно разкачване на зависимостите (Loose Coupling):** В Spring Boot и enterprise проектите слоевете комуникират през интерфейси (`UserService` интерфейс ➔ `UserServiceImpl` клас), което позволява лесна подмяна на имплементацията и лесно тестване с Mockito.
*   **Еволюция на стари API-та без чупене на код:** Благодарение на `default` методите (Java 8+), екипът на Java успя да добави `.stream()` и `.forEach()` в интерфейса `Collection`, без да счупи милионите съществуващи класове по света.

### 🔴 Недостатъци (Cons):
*   **Интерфейсите не могат да пазят състояние (State):** Ако искаш да споделиш общи `private` или `protected` полета и конструктор между 5 класа, интерфейсът не може да ти помогне — трябва ти `abstract class`.

## 5. КОДОВ ОДИТ: ПРАВИЛЕН СРЕЩУ ГРЕШЕН КОД (DIAMOND PROBLEM ПРИ `DEFAULT` МЕТОДИ И МОДИФИКАТОРИ В ИНТЕРФЕЙС)

### ❌ ГРЕШЕН КОД (По-тесен модификатор при имплементация и неразрешен конфликт между два `default` метода):
```java
interface LoggerA {
    default void log(String msg) { System.out.println("A: " + msg); }
}

interface LoggerB {
    default void log(String msg) { System.out.println("B: " + msg); }
}

// 🚨 ГРЕШКА 1 (Diamond Problem): Класът имплементира два интерфейса с еднакъв default метод log()!
// Компилаторът гърми: "class AppLogger inherits unrelated defaults for log(String)"!
class AppLogger implements LoggerA, LoggerB {
    // 🚨 ГРЕШКА 2: Ако напишеш 'void log(String msg)' БЕЗ 'public', компилаторът гърми,
    // защото в класа липсата на модификатор означава package-private (по-тясно от public в интерфейса)!
}
```
*   **Как да се избегне:** Когато имплементираш метод от интерфейс, **винаги** слагай **`public`**. При конфликт на два `default` метода пренапиши метода в класа и извикай желания родител чрез **`LoggerA.super.log(msg);`**.

### 🟢 ПРАВИЛЕН КОД (Разрешаване на Diamond Problem и функционален интерфейс):
```java
@FunctionalInterface
interface DiscountPolicy {
    // Единствен абстрактен метод (SAM) -> може да се подава като Lambda израз!
    double applyDiscount(double price);

    // Помощен default метод
    default double applyWithVat(double price) {
        return applyDiscount(price) * 1.20;
    }

    // Помощен private метод (Java 9+) за преизползване на логика вътре в интерфейса
    private boolean isValid(double price) {
        return price > 0;
    }
}
```

## 6. ИНТЕРВЮ КАПАНИ, ВЪПРОСИ И УЛОВКИ

*   **Въпрос на интервюто:** *„Може ли един `abstract class` да има **конструктор**, след като не може да бъде инстанциран директно с `new AbstractClass()`?“*
*   **Уловката:** Половината кандидати отговарят *„Не, щом не може да се направи `new`, няма смисъл от конструктор“*!
*   **Точен Senior отговор:** **Да, абстрактният клас ВИНАГИ има конструктор** (ако не напишеш такъв, компилаторът генерира празен конструктор по подразбиране). Той не се вика директно с `new`, а се извиква чрез **`super(...)` от конструкторите на неговите конкретни наследници**, за да инициализира `private` и `final` полетата, дефинирани в самия абстрактен клас!

## 7. АРХИТЕКТУРНО СРАВНЕНИЕ: JAVA 21+ СРЕЩУ C# 12+ (.NET)

| Архитектурен детайл | ☕ Java 21+ (JVM) | 🟣 C# 12+ (.NET 8+ CLR) |
| :--- | :--- | :--- |
| **Именна конвенция за интерфейси** | Без префикс `I` (`List`, `Comparable`, `Serializable`) | Задължителен префикс `I` (`IList`, `IComparable`) |
| **Модификатор за default метод** | Изисква изрична ключова дума **`default`** | Не изисква дума (просто пишеш тяло `{ ... }` в интерфейса) |
| **Разрешаване на конфликт (Diamond)** | `InterfaceA.super.myMethod();` вътре в пренаписания метод | Explicit Interface Implementation: `void IInterfaceA.MyMethod() { ... }` |
| **Полета и състояние в интерфейс** | Само `public static final` константи | Само `static` полета (инстанционни полета са забранени и в двата езика) |
| **Properties в интерфейс** | Няма (дефинират се `getX()` и `setX()` методи) | Поддържа `string Name { get; set; }` в интерфейса |
| **Функционални интерфейси / Ламбди** | `@FunctionalInterface` (1 абстрактен метод = Lambda) | Вградени делегати (`Func<T, R>`, `Action<T>`, `Predicate<T>`) |
