## 1. КАК ДА СЕ ЗАПОМНИ И ЧЕТЕ ПО-ЛЕСНО (МНЕМОНИКА)

*   **Django Admin е „Рентгенът“ на твоята база данни:** Той чете метаданните на твоите класове в `models.py` и автоматично строи пълен уеб интерфейс за управление, филтриране и търсене без да пишеш HTML.
*   **Петте златни настройки на `ModelAdmin`:**
    1.  `list_display` ➔ Кои колони да се виждат в таблицата.
    2.  `list_filter` ➔ Страничната лента вдясно за бързо филтриране.
    3.  `search_fields` ➔ Полето за търсене най-отгоре.
    4.  `readonly_fields` ➔ Заключени полета (като `created_at`), които никой не може да променя.
    5.  `inlines` ➔ Редакция на децата директно вътре в страницата на родителя (напр. Поръчка + редовете с продукти вътре в нея).

## 3. АРХИТЕКТУРНО СРАВНЕНИЕ: DJANGO ADMIN СРЕЩУ C# И NODE.JS ЕКОСИСТЕМИТЕ

| Възможност | Django Admin (Python) | C# / .NET екосистема | Node.js / TypeScript екосистема |
| :--- | :--- | :--- | :--- |
| **Наличие** | **Вграден в ядрото** по подразбиране | Няма вграден (ползва се Blazor / Radzen / Orchard) | Няма вграден (ползва се AdminJS / Strapi) |
| **Конфигурация** | Декларативен клас в `admin.py` | Писане на отделни Razor/Blazor страници | Конфигурационни ресурси в JS/TS |
| **История на промените** | **Вградена** (`django_admin_log` таблица) | Изисква ръчно писане на Audit Interceptor | Изисква външни плъгини |
| **Групови действия (Actions)** | Декоратор `@admin.action` | Ръчни бутони и таблични селектори | Custom Actions в AdminJS |
| **Потребителски права** | Автоматични (`add`, `change`, `delete`, `view`) | Политики и роли в Identity | RBAC конфигурация |

## 4. ПЛЮСОВЕ И МИНУСИ НА ВГРАДЕНИЯ DJANGO ADMIN

### 🟢 Предимства (Pros):
*   **Спестява седмици разработка:** Екипът по поддръжка, редакторите и модераторите получават готов бек-офис още в първия ден на проекта.
*   **Пълен одит на действията (Audit Trail):** Всеки запис, редакция или изтриване през админ панела се записва автоматично в таблицата `django_admin_log` (кой потребител, кога и какво точно е променил).

### 🔴 Недостатъци (Cons):
*   **Не е предназначен за крайни клиенти (End Users):** Дизайнът и логиката му са създадени за вътрешен доверен персонал (`is_staff=True`), а не за публичен клиентски портал.
*   **Риск от N+1 заявки при големи таблици:** Ако сложиш `ForeignKey` поле в `list_display`, админ панелът ще направи отделна SQL заявка за всеки ред на страницата, освен ако не добавиш `list_select_related`.

## 5. КОДОВ ОДИТ: ПРАВИЛЕН СРЕЩУ ГРЕШЕН КОД

### ❌ ГРЕШЕН КОД (Скрит N+1 срив в списъка и бавно падащо меню със 100 000 потребители):
```python
from django.contrib import admin
from .models import Order

@admin.register(Order)
class BadOrderAdmin(admin.ModelAdmin):
    # 🚨 ГРЕШКА 1: 'customer' и 'product' са ForeignKey полета!
    # При 100 реда на страница админът ще пусне 201 SQL заявки (N+1 проблем)!
    list_display = ["id", "customer", "product", "total_price"]

    # 🚨 ГРЕШКА 2: Липсва autocomplete_fields / raw_id_fields!
    # При отваряне на поръчка Django ще зареди 100 000 потребители в един HTML <select> таг и ще забие браузъра!
```
*   **Как да се избегне:** Винаги добавяй `list_select_related = ["customer", "product"]` за `ForeignKey` колоните в `list_display` и използвай **`autocomplete_fields = ["customer"]`** при големи таблици.

### 🟢 ПРАВИЛЕН КОД (Високопроизводителен `ModelAdmin` с Action и защита):
```python
from django.contrib import admin
from .models import Order

@admin.register(Order)
class OrderAdmin(admin.ModelAdmin):
    list_display = ["id", "customer", "status", "total_price", "created_at"]
    list_select_related = ["customer"]                  # Решава N+1 проблема с 1 JOIN!
    list_filter = ["status", "created_at"]              # Страничен панел за филтри
    search_fields = ["id", "customer__email"]           # Търсене по ID или имейл на клиента
    autocomplete_fields = ["customer"]                  # AJAX търсачка вместо огромен <select>
    readonly_fields = ["created_at", "total_price"]     # Защита против ръчна подмяна на цената
    actions = ["mark_as_shipped"]

    @admin.action(description="Маркирай избраните поръчки като ИЗПРАТЕНИ")
    def mark_as_shipped(self, request, queryset):
        updated_count = queryset.update(status="SHIPPED")
        self.message_user(request, f"Успешно обновени {updated_count} поръчки.")
```

## 6. ИНТЕРВЮ КАПАНИ, ВЪПРОСИ И УЛОВКИ

*   **Въпрос на интервюто:** *„Как се защитава Django Admin панелът в реална продукционна среда, за да не стане лесна мишена за автоматизирани атаки?“*
*   **Уловката:** По подразбиране админ панелът винаги стои на адрес `/admin/`, което е първото място, което ботовете атакуват с речникови пароли (Brute-force).
*   **Точен Senior отговор:** Защитата се изгражда на 3 нива:
    1.  **Смяна на стандартния URL адрес:** В `config/urls.py` никога не оставяй `path("admin/", ...)`, а го смени на секретен път, четен от `.env` файла (напр. `path(os.environ.get("ADMIN_URL"), admin.site.urls)`).
    2.  **Двуфакторна автентикация (2FA) и Rate Limiting:** Добавяне на пакети като `django-axes` (блокира IP адреса след 5 грешни опита за парола) и `django-otp` (Google Authenticator).
    3.  **Мрежова изолация (Nginx / VPN):** Ограничаване на достъпа до админ адреса по IP адрес (само от офисния VPN) директно на ниво уеб сървър (Nginx).
