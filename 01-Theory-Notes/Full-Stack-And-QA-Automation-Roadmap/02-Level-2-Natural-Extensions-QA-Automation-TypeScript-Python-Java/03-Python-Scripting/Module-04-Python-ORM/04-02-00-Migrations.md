## 1. КАК ДА СЕ ЗАПОМНИ И ЧЕТЕ ПО-ЛЕСНО (МНЕМОНИКА)

*   **Миграциите са „Git за базата данни“:** Както Git пази историята на промените в твоя код по комити, така миграциите пазят историята на промените по таблиците във вид на номерирани Python файлове (`0001_initial.py`, `0002_add_email.py`).
*   **Двустъпков процес (Чертеж ➔ Строеж):**
    1.  **Генериране (`makemigrations` / `alembic revision`):** Само рисува чертежа на промените на диска, **без да пипа реалната база данни**.
    2.  **Прилагане (`migrate` / `alembic upgrade`):** Чете чертежа и реално строи/променя колоните в SQL сървъра, като записва в специална системна таблица (`django_migrations` или `alembic_version`), че тази стъпка вече е минала.

## 3. АРХИТЕКТУРНО СРАВНЕНИЕ: DJANGO MIGRATIONS СРЕЩУ ALEMBIC И C# EF CORE

| Операция | Django Migrations | SQLAlchemy (Alembic) | C# Entity Framework Core |
| :--- | :--- | :--- | :--- |
| **Инсталация** | Вградено в Django | `pip install alembic` + `alembic init` | Вградено в EF Core Tools |
| **Създаване на миграция** | `python manage.py makemigrations` | `alembic revision --autogenerate -m "..."` | `dotnet ef migrations add Name` |
| **Прилагане към базата** | `python manage.py migrate` | `alembic upgrade head` | `dotnet ef database update` |
| **Връщане назад (Rollback)** | `python manage.py migrate app 0001` | `alembic downgrade -1` | `dotnet ef database update PrevName` |
| **Преглед на генерирания SQL** | `python manage.py sqlmigrate app 0001` | `alembic upgrade head --sql` | `dotnet ef migrations script` |
| **Системна таблица в SQL** | `django_migrations` | `alembic_version` | `__EFMigrationsHistory` |

## 4. ПЛЮСОВЕ И МИНУСИ НА ДВАТА ПОДХОДА

### 🟢 Django Migrations — Предимства и Недостатъци:
*   **Предимства:** Напълно вградени, нулева настройка; много умни при преименуване на колона (питат в конзолата *„Did you rename field X to Y?“*, за да не изтрият данните!); поддържат лесни Data Migrations чрез `RunPython`.
*   **Недостатъци:** Създават много отделни файлове във всяко приложение (App), които при големи проекти могат да станат стотици и да забавят старта на тестовете.

### 🔵 SQLAlchemy (Alembic) — Предимства и Недостатъци:
*   **Предимства:** Независим инструмент, работи с всякакви бази и рамки; позволява разклонени миграции (Branching) и фин контрол върху всеки индекс и външен ключ.
*   **Недостатъци:** Изисква ръчна начална настройка на файла `env.py`, за да му посочиш къде се намира твоят `Base.metadata`; при `autogenerate` понякога пропуска промени по имена на ограничения или видове типове.

## 5. КОДОВ ОДИТ: ПРАВИЛЕН СРЕЩУ ГРЕШЕН КОД

### ❌ ГРЕШЕН КОД (Изтриване на миграционни файлове и промяна на вече приложена миграция):
```python
# 🚨 ГРЕШКА 1: Ръчно редактиране на миграция 0001_initial.py, след като тя ВЕЧЕ е пусната на сървъра!
# Когато я качиш в продукция, Django/Alembic ще видят в базата, че 0001 вече е минала,
# и изобщо НЯМА да изпълнят новите ти редове!

# 🚨 ГРЕШКА 2: Използване на Base.metadata.create_all(engine) в продукция вместо миграции!
# create_all() само създава липсващи таблици, но НЕ МОЖЕ да добави нова колона към вече съществуваща таблица!
```
*   **Как да се избегне:** Никога не променяй вече приложена миграция — винаги генерирай **нова миграция** (`0002_...`) за всяка промяна. Използвай `create_all()` само в малки тестове, а в реални проекти — винаги `Alembic` или `Django Migrations`.

### 🟢 ПРАВИЛЕН КОД (Data Migration за безопасно прехвърляне на данни в Django):
```python
from django.db import migrations

# Функция, която преобразува съществуващи записи по време на миграция
def populate_full_names(apps, schema_editor):
    # ВАЖНО: Взимаме историческата версия на модела чрез apps.get_model, а не с директен import!
    User = apps.get_model("accounts", "User")
    for user in User.objects.all():
        user.full_name = f"{user.first_name} {user.last_name}"
        user.save()

class Migration(migrations.Migration):
    dependencies = [
        ("accounts", "0001_initial"),
    ]

    operations = [
        migrations.RunPython(populate_full_names),
    ]
```

## 6. ИНТЕРВЮ КАПАНИ, ВЪПРОСИ И УЛОВКИ

*   **Въпрос на интервюто:** *„Какъв е най-опасният проблем при добавяне на нова задължителна колона (`NOT NULL` без стойност по подразбиране) към таблица с 10 милиона записа в продукция (Zero-Downtime Migration)?“*
*   **Уловката:** Начинаещите директно добавят `phone = models.CharField(max_length=20)` и пускат `migrate`, което може да заключи таблицата или да срине стария код, докато се обновяват сървърите.
*   **Точен Senior отговор:** Прилага се **3-стъпковият модел на безопасна миграция (Expand and Contract Pattern)**:
    1.  **Стъпка 1 (Expand):** Добавяш новата колона като **опционална (`null=True` / `nullable=True`)** и пускаш миграцията (в PostgreSQL това става за милисекунди без заключване на таблицата).
    2.  **Стъпка 2 (Backfill):** Пускаш фонов скрипт, който попълва стойностите на малки порции (Batches), и пускаш новия код, който вече пише в тази колона.
    3.  **Стъпка 3 (Contract):** Чак когато всички 10 милиона реда са попълнени, пускаш втора миграция, която слага ограничението `NOT NULL`.
