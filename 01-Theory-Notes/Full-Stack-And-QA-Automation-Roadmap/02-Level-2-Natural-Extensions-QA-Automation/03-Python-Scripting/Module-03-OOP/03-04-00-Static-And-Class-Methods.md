## 1. КАК ДА СЕ ЗАПОМНИ И ЧЕТЕ ПО-ЛЕСНО (МНЕМОНИКА)

*   **Обикновен метод (`def method(self):`):** Има достъп до **всичко** — вижда конкретния обект (`self`) и вижда класа (`self.__class__`).
*   **Класов метод (`@classmethod` + `def method(cls):`):** Получава самия **Клас (`cls`)** като първи аргумент, но **не вижда** конкретните обекти (`self`). Използва се най-често като **алтернативен конструктор (Factory Method)** — например създаване на обект от текстов стринг или JSON.
*   **Статичен метод (`@staticmethod` + `def method():`):** Не получава **нито `self`, нито `cls`**. Това е обикновена самостоятелна функция, прибрана вътре в класа само за логическа прегледност (напр. калкулатор или валидатор).

## 3. АРХИТЕКТУРНО СРАВНЕНИЕ: PYTHON СРЕЩУ C# И JAVASCRIPT

| Концепция | Python 3.x | C# (.NET) | JavaScript (ES6+) |
| :--- | :--- | :--- | :--- |
| **Статичен метод** | `@staticmethod` (без `self`/`cls`) | `public static void Calc()` | `static calc()` |
| **Класов метод (с контекст)** | `@classmethod` (получава `cls`) | **Няма директен еквивалент** | `static create()` (ползва `this` за класа) |
| **Алтернативен конструктор** | `@classmethod def from_str(cls, s):` | Предефинирани конструктори (Overloading) | Статични фабрични методи |
| **Викане през инстанция** | Позволено (`obj.static_func()`) | **Забранено** (само през `Class.Func()`) | **Забранено** (само през `Class.func()`) |

## 4. ПЛЮСОВЕ И МИНУСИ НА CLASS И STATIC МЕТОДИТЕ

### 🟢 Предимства (Pros):
*   **Полиморфизъм при наследяване чрез `@classmethod`:** Тъй като Python няма Method Overloading (множество конструктори `__init__`), `@classmethod` решава този проблем елегантно. Още по-важно: ако клас `Admin` наследи `User.from_string()`, параметърът `cls` автоматично става `Admin` и връща инстанция на `Admin`, а не на родителя `User`!
*   **Чиста архитектура с `@staticmethod`:** Позволява групирането на помощни валидационни функции вътре в самия бизнес клас, вместо да се разхвърлят като глобални функции из целия файл.

### 🔴 Недостатъци (Cons):
*   **Объркване между двата декоратора:** Начинаещите често слагат `@staticmethod` за фабрични методи и хардкодват името на класа вътре (`return User(...)`), което чупи наследяването.

## 5. КОДОВ ОДИТ: ПРАВИЛЕН СРЕЩУ ГРЕШЕН КОД

### ❌ ГРЕШЕН КОД (Хардкоднато име на клас в `@staticmethod` вместо `@classmethod`):
```python
class User:
    def __init__(self, username: str):
        self.username = username

    # 🚨 ГРЕШКА: Използван е @staticmethod и името 'User' е заковано вътре!
    @staticmethod
    def from_email(email: str):
        name = email.split("@")
        return User(name)  # ВИНАГИ връща User, дори ако се извика от Admin.from_email()!

class Admin(User):
    pass

# Уловка: Извикваме го през Admin, но получаваме обикновен User!
admin_obj = Admin.from_email("eli@softuni.bg")
print(type(admin_obj))  # <class '__main__.User'> вместо <class '__main__.Admin'>!
```
*   **Как да се избегне:** Всеки метод, който създава и връща нова инстанция на класа (Factory Method), **задължително** трябва да бъде `@classmethod` и да връща `cls(...)`!

### 🟢 ПРАВИЛЕН КОД (Чист Pythonic стандарт с `@classmethod` и `@staticmethod`):
```python
class User:
    def __init__(self, username: str):
        self.username = username

    # 1. Фабричен класов метод (работи полиморфно за всички наследници!)
    @classmethod
    def from_email(cls, email: str):
        if not cls.is_valid_email(email):
            raise ValueError("Невалиден формат на имейл адреса!")
        username = email.split("@")
        return cls(username)  # Създава инстанция на точния извикващ клас (User или Admin)

    # 2. Статичен помощен валидатор (не се нуждае нито от self, нито от cls)
    @staticmethod
    def is_valid_email(email: str) -> bool:
        return "@" in email and "." in email.split("@")[-1]

class Admin(User):
    pass

# Тестване на полиморфизма с @classmethod
regular_user = User.from_email("ivan@gmail.com")
super_admin = Admin.from_email("elizabeth@softuni.bg")

print(f"Тип 1: {type(regular_user).__name__} | Име: {regular_user.username}")
print(f"Тип 2: {type(super_admin).__name__}  | Име: {super_admin.username}")
```
*   **Изход в конзолата:**
    ```text
    Тип 1: User | Име: ivan
    Тип 2: Admin | Име: elizabeth
    ```

## 6. ИНТЕРВЮ КАПАНИ, ВЪПРОСИ И УЛОВКИ

*   **Въпрос на интервюто:** *„Кога на интервю или в реален проект трябва да избереш `@classmethod`, кога `@staticmethod` и кога обикновена функция извън класа?“*
*   **Уловката:** Кандидатите често казват, че `@staticmethod` е просто по-бърз, но пропускат архитектурния замисъл.
*   **Точен Senior отговор:** 
    1.  Избирам **`@classmethod`**, когато методът трябва да достъпва или променя състояние на самия клас (Class Attributes) или когато пиша **алтернативен конструктор (Factory Method)**, който трябва да работи коректно и при наследяване чрез `cls`.
    2.  Избирам **`@staticmethod`**, когато функцията не докосва нито обекта (`self`), нито класа (`cls`), но е **логически и домейн-обвързана** с този клас (напр. `DateValidator.is_leap_year(2026)`) и искам наследниците да могат да я пренаписват (Override) при нужда.
    3.  Избирам **обикновена функция на ниво модул**, ако тя е общопомощна (Utility) и няма директна връзка с конкретен клас.
