## 1. ОПТИМИЗАЦИЯ 1: КОНКАТЕНАЦИЯ НА НИЗОВЕ В ЦИКЪЛ (`+=`) СРЕЩУ `"".JOIN()` (O(N²) СРЕЩУ O(N))

### Блок-схема на проблема и решението:
```text
❌ БАВЕН ПОДХОД (result += item в цикъл — Неизменяеми str обекти):
   Итерация 1: Създава нов str с дължина 10 байта   ──► Записва в RAM
   Итерация 2: Копира старите 10 + новите 10 = 20 Б ──► Нова алокация + старият става боклук
   ...
   Итерация 50 000: Копира 500 000 байта на всяка стъпка! ──► Огромно натоварване на CPU/RAM!

✅ БЪРЗ ПОДХОД ("".join(parts) — Еднократна алокация в C):
   1. Събира референциите в list (O(1) амортизирано)
   2. "".join() изчислява точната крайна дължина наведнъж и копира всичко в 1 буфер!
```

### Кодово сравнение:
```python
# ❌ ГРЕШНО И БАВНО: Многократно презаписване на неизменяеми str обекти
def build_csv_slow(rows: list[str]) -> str:
    output = ""
    for row in rows:
        output += row + "\n"
    return output

# ✅ ПРАВИЛНО И ОПТИМИЗИРАНО: Еднократна алокация в паметта
def build_csv_fast(rows: list[str]) -> str:
    return "\n".join(rows)
```
*   **Защо е по-добре:** В Python типът `str` е **неизменяем (immutable)**. Операторът `+=` в цикъл принуждава интерпретатора да заделя нова памет и да копира целия натрупан текст наново при всяка итерация. `"".join()` е написан на чист C и заделя точния размер памет само веднъж.

## 2. ОПТИМИЗАЦИЯ 2: LIST COMPREHENSION `[...]` СРЕЩУ GENERATOR EXPRESSION `(...)` (RAM ПАМЕТ)

### Блок-схема на паметта:
```text
❌ БАВЕН ЗА ПАМЕТТА (List Comprehension върху 10 милиона реда):
   [parse(line) for line in huge_file] ──► Зарежда ВСИЧКИ 10 000 000 обекта в RAM едновременно (~1.5 GB)!

✅ ОПТИМИЗИРАН ЗА ПАМЕТТА (Generator Expression — Lazy Evaluation):
   (parse(line) for line in huge_file) ──► Държи в RAM САМО 1 елемент в даден момент (~120 байта)!
```

### Кодово сравнение:
```python
# ❌ ГРЕШНО ПРИ ГОЛЕМИ ДАННИ: Заделя списък с милиони елементи в RAM само за да ги сумира
def sum_squares_memory_heavy(n: int) -> int:
    return sum([x * x for x in range(n)])

# ✅ ПРАВИЛНО: Generator expression подава числата едно по едно без междинен списък
def sum_squares_optimal(n: int) -> int:
    return sum(x * x for x in range(n))
```
*   **Защо е по-добре:** Когато подаваш данни към агрегиращи функции (`sum()`, `any()`, `all()`, `max()`, `min()`) или обхождаш големи файлове, генераторът изчислява стойностите мързеливо (*on-the-fly*), без да заема гигабайти RAM.

## 3. ОПТИМИЗАЦИЯ 3: ПРОВЕРКА ЗА ПРИНАДЛЕЖНОСТ `X IN LIST` СРЕЩУ `X IN SET` (O(N) СРЕЩУ O(1))

### Блок-схема на проблема и решението:
```text
❌ БАВЕН ПОДХОД (Търсене в list — Линейно сканиране O(N) при всяка проверка):
   [10, 42, 7, ..., 99999] ──► Проверява индекс 0, 1, 2, 3 ... до края!
   При 10 000 търсения в списък от 10 000 елемента = 100 000 000 стъпки!

✅ БЪРЗ ПОДХОД (Търсене в set или dict — Хеш таблица O(1)):
   {10, 42, 7, ..., 99999} ──► Изчислява hash(x) и скача директно на адреса в паметта!
   При 10 000 търсения = 10 000 стъпки! (До 1000x по-бързо!)
```

### Кодово сравнение:
```python
# ❌ ГРЕШНО И БАВНО: Линейно търсене в списък при всяка итерация
def find_common_slow(ids_a: list[int], ids_b: list[int]) -> list[int]:
    return [x for x in ids_a if x in ids_b]

# ✅ ПРАВИЛНО И ОПТИМИЗИРАНО: Преобразуване в set за O(1) достъп
def find_common_fast(ids_a: list[int], ids_b: list[int]) -> list[int]:
    lookup_set = set(ids_b)
    return [x for x in ids_a if x in lookup_set]
```
*   **Защо е по-добре:** В Python `set` и `dict` са реализирани като високооптимизирани хеш таблици в C. Еднократното конвертиране `set(ids_b)` струва \(O(M)\), след което всяка проверка `x in lookup_set` отнема средно \(O(1)\).

## 4. ОПТИМИЗАЦИЯ 4: ОЛЕКОТЯВАНЕ НА КЛАСОВЕ С `__SLOTS__` (ДО 60% ПО-МАЛКО RAM)

### Блок-схема на паметта на един Python обект:
```text
❌ СТАНДАРТЕН КЛАС (Всяка инстанция създава собствен динамичен речник __dict__):
   Point(10, 20) ──► [ Обект (56 Б) ] + [ __dict__ хеш таблица (104 Б) ] = ~160+ байта на обект!
   При 1 000 000 обекта ──► ~160 MB RAM само за празни речници!

✅ КЛАС С __SLOTS__ (Фиксиран масив от указатели в C, БЕЗ __dict__):
   PointSlotted(10, 20) ──► [ Обект с фиксирани слотове (48 Б) ] = ~48 байта на обект! (~3x по-малко RAM!)
```

### Кодово сравнение:
```python
# ❌ СТАНДАРТЕН КЛАС: Позволява произволни атрибути, но харчи много памет при милиони инстанции
class TelemetryPoint:
    def __init__(self, x: float, y: float, timestamp: int) -> None:
        self.x = x
        self.y = y
        self.timestamp = timestamp

# ✅ ОПТИМИЗИРАН КЛАС: Забранява __dict__ и заключва атрибутите за минимална RAM и по-бърз достъп
class TelemetryPointOptimized:
    __slots__ = ("x", "y", "timestamp")

    def __init__(self, x: float, y: float, timestamp: int) -> None:
        self.x = x
        self.y = y
        self.timestamp = timestamp
```
*   **Защо е по-добре:** Когато моделираш милиони записи (напр. при обработка на логове, данни от сензори или DTO обекти), `__slots__` елиминира вътрешния `__dict__` на всеки обект и ускорява четенето на атрибути с ~15–20%.

## 5. БЪРЗ ОДИТ НА ОПТИМИЗАЦИИТЕ В PYTHON (ОТ ОСНОВИ ДО ORM & WEB)

| Сценарий | Бавен подход | Оптимизиран подход | Печалба |
| :--- | :--- | :--- | :--- |
| **Сглобяване на дълги низове** | `text += part` в цикъл | `"".join(parts)` | От $O(n^2)$ на $O(n)$ време и памет |
| **Обработка на големи потоци** | List Comprehension `[...]` | Generator Expression `(...)` | Константна RAM памет $O(1)$ |
| **Търсене на елементи** | `if x in my_list:` в цикъл | `if x in my_set:` | От $O(n)$ на $O(1)$ за проверка |
| **Милиони инстанции на клас** | Обикновен клас с `__dict__` | Клас с `__slots__` (или `@dataclass(slots=True)`) | До 60% по-малко заемана RAM |
| **Django / SQLAlchemy N+1 заявки** | Достъп до релации в `for` цикъл | `.select_related()` / `.prefetch_related()` | От $N+1$ SQL заявки на 1–2 заявки |
| **Използване на локални променливи** | Многократно четене на `math.sin` в цикъл | Локална референция `sin = math.sin` преди цикъла | Избягва глобално търсене в речника на модула |
