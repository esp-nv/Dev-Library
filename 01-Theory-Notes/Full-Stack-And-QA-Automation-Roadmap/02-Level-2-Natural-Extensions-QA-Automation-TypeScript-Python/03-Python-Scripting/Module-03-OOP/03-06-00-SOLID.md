## 1. КАК ДА СЕ ЗАПОМНИ И ЧЕТЕ ПО-ЛЕСНО (МНЕМОНИКА)

*   **S — Single Responsibility (Единствена отговорност):** *„Един клас трябва да има само една причина да се променя“.* Не прави „Швейцарско ножче“ (клас, който едновременно смята заплати, праща имейли и записва в база данни).
*   **O — Open/Closed (Отворен/Затворен):** *„Отворен за разширение, затворен за промяна“.* Когато добавяш нов начин на плащане (напр. Apple Pay), не отваряш стария работещ код с безкрайни `elif` проверки, а създаваш нов клас-наследник.
*   **L — Liskov Substitution (Замяна на Лисков):** *„Детето не трябва да чупи обещанията на родителя“.* Ако функция очаква клас `Bird`, тя трябва да работи безпроблемно с всеки негов наследник (не слагай метод `fly()` в базов клас `Bird`, ако `Penguin` го наследява и хвърля грешка!).
*   **I — Interface Segregation (Разделяне на интерфейсите):** *„Много малки специализирани договори, вместо един гигантски“.* Не принуждавай един обикновен принтер да имплементира интерфейс `IMultiDevice` с методи `.scan()` и `.fax()`, които той не притежава.
*   **D — Dependency Inversion (Обръщане на зависимостите):** *„Зависи от абстракции, не от конкретни класове“.* Високонивовият бизнес клас не трябва сам да създава `db = MySQLDatabase()` вътре в себе си, а да получава абстрактен `Database` отвън (Dependency Injection).

## 2. АРХИТЕКТУРНА КАРТА НА SOLID И БЛОК-СХЕМА

Прилагането на **Open/Closed** и **Dependency Inversion** обръща посоката на контрол и предпазва ядрото на приложението от промени във външните технологии:

```text
❌ БЕЗ SOLID (Силно обвързване):
[ OrderProcessor ] ──(зависи директно от)──► [ StripePayment ] (Трудно за смяна и тест!)

✅ СЪС SOLID (Dependency Inversion & Open/Closed):
[ OrderProcessor ] ──(зависи от договор)──► [ IPaymentGateway (ABC) ]
                                                      ▲
                                       ┌──────────────┴──────────────┐
                               [ StripePayment ]             [ PayPalPayment ]
```

## 3. АРХИТЕКТУРНО СРАВНЕНИЕ: PYTHON СРЕЩУ C# И JAVASCRIPT

| Принцип | Python 3.x | C# (.NET) | JavaScript / TypeScript |
| :--- | :--- | :--- | :--- |
| **Абстракции (OCP / DIP)** | `ABC` или `typing.Protocol` | `interface` / `abstract class` | TypeScript `interface` |
| **Interface Segregation (ISP)** | Малки `ABC` класове или `Protocols` | Множество малки `IService` интерфейси | Композиция на малки TS типове |
| **Dependency Injection (DIP)** | Подаване през `__init__(self, repo)` | Вграден IoC контейнер (`AddScoped`) | Конструктор или рамки (NestJS) |
| **Нарушение на LSP** | `raise NotImplementedError()` в наследник | `throw new NotImplementedException()` | `throw new Error("Not supported")` |

## 4. ПЛЮСОВЕ И МИНУСИ НА SOLID В PYTHON

### 🟢 Предимства (Pros):
*   **Лесно автоматизирано тестване (Unit Testing):** Благодарение на Dependency Inversion можеш да подадеш фалшив тестов обект (Mock) вместо реална база данни.
*   **Безопасно мащабиране:** Нови функционалности се добавят чрез нови файлове и класове, без риск да счупиш вече тестван код в продукция.

### 🔴 Недостатъци (Cons):
*   **Риск от Over-engineering (Прекалено усложняване):** В Python е грешка да пишеш `ABC` интерфейси за абсолютно всеки малък клас с 10 реда код. Прилагай SOLID там, където се очаква промяна и разширение.

## 5. КОДОВ ОДИТ: ПРАВИЛЕН СРЕЩУ ГРЕШЕН КОД

### ❌ ГРЕШЕН КОД (Нарушаване на SRP, OCP и DIP наведнъж):
```python
class BadOrderService:
    def process_order(self, amount: float, payment_type: str):
        # 🚨 Нарушение на OCP: Всеки нов метод на плащане изисква редактиране на този клас!
        if payment_type == "card":
            print(f"Плащане с карта: {amount} лв.")
        elif payment_type == "crypto":
            print(f"Плащане с крипто: {amount} лв.")

        # 🚨 Нарушение на SRP & DIP: Класът за поръчки сам праща имейли и сам инстанцира услугата!
        print("Изпращане на имейл за потвърждение...")
```
*   **Как да се избегне:** Раздели плащането и известията в отделни класове зад абстракции (`ABC`) и ги подай в конструктора `__init__`.

### 🟢 ПРАВИЛЕН КОД (Чист SOLID дизайн в Python):
```python
from abc import ABC, abstractmethod

# 1. Абстракция за плащане (Open/Closed & Dependency Inversion)
class PaymentMethod(ABC):
    @abstractmethod
    def pay(self, amount: float) -> None:
        pass

class CardPayment(PaymentMethod):
    def pay(self, amount: float) -> None:
        print(f"[💳 Карта] Успешно плащане на {amount:.2f} лв.")

class CryptoPayment(PaymentMethod):
    def pay(self, amount: float) -> None:
        print(f"[₿ Крипто] Успешен трансфер на {amount:.2f} лв.")

# 2. Отделна отговорност само за известия (Single Responsibility)
class EmailNotifier:
    def notify(self, message: str) -> None:
        print(f"[📧 Email] {message}")

# 3. Бизнес клас, който получава зависимостите си отвън (Dependency Injection)
class OrderProcessor:
    def __init__(self, payment_method: PaymentMethod, notifier: EmailNotifier):
        self.payment_method = payment_method
        self.notifier = notifier

    def checkout(self, amount: float) -> None:
        self.payment_method.pay(amount)
        self.notifier.notify(f"Поръчка за {amount:.2f} лв. е завършена.")

# Изпълнение с лесна подмяна на стратегията
order = OrderProcessor(CardPayment(), EmailNotifier())
order.checkout(150.0)
```
*   **Изход в конзолата:**
    ```text
    [💳 Карта] Успешно плащане на 150.00 лв.
    [📧 Email] Поръчка за 150.00 лв. е завършена.
    ```

## 6. ИНТЕРВЮ КАПАНИ, ВЪПРОСИ И УЛОВКИ

*   **Въпрос на интервюто:** *„Дайте класически пример за нарушаване на принципа за замяна на Лисков (Liskov Substitution Principle - LSP) с Квадрат и Правоъгълник и обяснете как се решава архитектурно.“*
*   **Уловката:** Математически квадратът е правоъгълник, затова кандидатите правят `class Square(Rectangle):` и се хващат в капана!
*   **Точен Senior отговор:** Ако `Square` наследява `Rectangle` и в сетърите на `Square` заложим, че промяната на ширината (`width = 5`) автоматично променя и височината (`height = 5`), това **нарушава очакваното поведение на родителя `Rectangle`** (където ширина и височина са независими). Функция, която очаква `Rectangle`, задава `rect.width = 5; rect.height = 4` и очаква лице `20`, но при подаден `Square` получава `16`!
    *   **Правилен фикс:** Квадратът и Правоъгълникът не трябва да се наследяват един друг — и двата трябва да наследяват общ абстрактен базов клас **`Shape(ABC)`** с абстрактен метод `area()`.
