## 1. КАГВО Е TTL (TIME TO LIVE) И ЗАЩО Е ВАЖЕН ЗА RAM ПАМЕТТА?

Тъй като оперативната памет (RAM) е скъп и силно ограничен хардуерен ресурс, NoSQL средите не могат да съхраняват данни вечно. **TTL (Time to Live)** е софтуерен брояч — времеви лимит в секунди или милисекунди, който се прикрепя към всеки ключ при неговия запис в Redis.

След изтичането на заложеното време, Redis автоматично изтрива ключа и неговите байтове от паметта насила. Това предпазва сървъра от препълване и гарантира, че базата данни периодично опреснява съдържанието си с нови, актуални данни от бекенда.

---

## 2. СОФТУЕРНА РАЗЛИКА МЕЖДУ ABSOLUTE EXPIRATION И SLIDING EXPIRATION

В .NET средите през `DistributedCacheEntryOptions` можем да наложим два коренно различни типа контроли за изтичане на времето:

1.  **Absolute Expiration (Абсолютно изтичане):** Ключът ще бъде изтрит твърдо точно в определения час или след фиксираното време (напр. след точно 30 минути), без значение колко пъти потребителите са го чели или извиквали по мрежата.
2.  **Sliding Expiration (Плаващо изтичане):** Времето на живот на ключа се удължава автоматично при всяко негово успешно прочитане (Cache Hit). Ако заложиш 10 минути плаващо време и потребител извика данните на 9-тата минута, броячът се рестартира обратно на 10 минути в RAM паметта. Ключът ще умре само тогава, когато никой не го е търсил в рамките на заложения прозорец.

---

## 3. АРХИТЕКТУРНИЯТ ПАТЕРН CACHE-ASIDE (ПОДАВАНЕ ПРИ ПОИСКВАНЕ)

**Cache-Aside (известен още как Lazy Caching)** е най-масовият индустриален патерн за управление на разпределен кеш. При него бекенд приложението комуникира паралелно с Redis и с релационната база (SQL Server), следвайки три строги стъпки:

```text
                    1. Търсене по Ключ
  .NET Application ───────────────────► Redis Cache (In-Memory)
         │                                    │
         │ 2. ИМА ДАННИ (Cache Hit)            │ ВРЪЩА БАЙТОВЕ
         ▼                                    ▼
   Връща Веднага ◄────────────────────────────┘
         │
         │ 2. НЯМА ДАННИ (Cache Miss)
         ▼
   SQL Database ───► 3. Записва обратно в Кеша с TTL ───► Краен обект
```

### ⚙️ Алгоритмичен ход:
1.  Уеб заявката пристига в контролера. Софтуерът първо сканира Redis (`GetAsync`).
2.  **Успех (Cache Hit):** Данните са в RAM паметта. Десериализират се и се връщат към клиента за милисекунди, без изобщо да се натоварва SQL базата.
3.  **Неуспех (Cache Miss):** Данните липсват в Redis. Софтуерът прави тежка заявка към SQL Server, взима данните, записва ги обратно в Redis с дефиниран TTL (`SetAsync`) за следващите потребители и тогава ги затваря в HTTP отговора.
