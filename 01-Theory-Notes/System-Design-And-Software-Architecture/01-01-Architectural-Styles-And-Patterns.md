## 1. МОНОЛИТНА АРХИТЕКТУРА (MONOLITHIC ARCHITECTURE)

*   **Философия:** Цялата бизнес логика, уеб интерфейсът, обработката на заявки и достъпът до данни са компилирани, капсулирани и пакетирани заедно като една единствена, неделима единица (едно уеб приложение).
*   **Плюсове:** Изключително бърза първоначална разработка, лесна трасировка на грешки стъпка по стъпка (End-to-End Debugging), ниско софтуерно забавяне и прост деплой на една машина.
*   **Минуси:** Превръща се в „голямо кълбо от кал“ (Big Ball of Mud) при нарастване на екипа. Всеки софтуерен компонент е силно обвързан с останалите. Ако едно малко уеб поле крашне или препълни паметта, умира цялото приложение за всички клиенти едновременно.

## 2. МИКРОУСЛУГИ (MICROSERVICES ARCHITECTURE) И КОМУНИКАЦИЯ

*   **Философия:** Системата се разбива на напълно декуплирани, самостоятелни и безсъстоятелни (Stateless) малки услуги. Всяка услуга отговаря за едно конкретно бизнес ограничение (Bounded Context), притежава своя собствена, изолирана база данни и се деплоява независимо в Docker/Kubernetes контейнери.
*   **Комуникация:** Услугите комуникират през мрежата по два начина:
    1.  *Синхронно (Блокиращо):* Чрез чисти REST Web APIs или бързи бинарни **gRPC** повиквания.
    2.  *Асинхронно (Неблокиращо):* Чрез брокери на съобщения (RabbitMQ, Kafka).

### 📄 C# Софтуерен код на Синхронна комуникация между Микроуслуги:
Услугата за Поръчки (`OrderService`) има нужда да извика отдалечено през мрежата Услугата за Наличности (`InventoryService`), за да провери дали даден продукт е наличен:

```csharp
using Microsoft.AspNetCore.Mvc;
using System.Net.Http;
using System.Net.Http.Json;
using System.Threading.Tasks;

public class InventoryResponseDto { public bool IsAvailable { get; set; } }

[ApiController]
[Route("api/v1/orders")]
public class OrderApiController : ControllerBase
{
    private readonly HttpClient _httpClient;

    // Инжектираме HttpClient за извършване на между-сървърни мрежови заявки
    public OrderApiController(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    [HttpPost("checkout")]
    public async Task<IActionResult> ProcessCheckout([ some input args ])
    {
        int productId = 105;
        // Извикваме по мрежата външната независима микроуслуга за наличности
        string inventoryUrl = $"https://localhost:5001/api/v1/inventory/check/{productId}";
        
        // Синхронно изчакване на HTTP отговор от съседния сървър
        var response = await _httpClient.GetAsync(inventoryUrl);

        if (!response.IsSuccessStatusCode)
        {
            return StatusCode(503, "Грешка: Услугата за наличности не отговаря навреме!");
        }

        var result = await response.Content.ReadFromJsonAsync<InventoryResponseDto>();

        if (result == null || !result.IsAvailable)
        {
            return BadRequest("Операцията е отказана: Продуктът е изчерпан в склада!");
        }

        return Ok("Поръчката е създадена успешно в базата!");
    }
}
```

#### 🎯 Очакван изход (Expected Output в Postman):
Ако съседният сървър отговори, че продуктът е наличен, клиентът получава чист статус `200 OK`:
```json
{
  "message": "Поръчката е създадена успешно в базата!"
}
```

## 3. СЪБИТИЕ-ОРИЕНТИРАНИ (EVENT-DRIVEN) И SERVERLESS СРЕДИ

*   **Event-Driven Architecture:** Компонентите спират да се викат директно по мрежата (което ги прави зависими от скоростта на съседния сървър). Вместо това, когато една услуга свърши работа, тя изстрелва събитие (Event) в централен **Message Broker** (напр. *„Създадена е поръчка №12“*). Всички съседни микроуслуги (напр. за доставки, за фактуриране), които слушат за това събитие, го улавят асинхронно и си довършват работата независимо, в пълна автономия.
*   **Serverless (FaaS - Function as a Service):** Пълно премахване на концепцията за постоянно работещи уеб сървъри. Твоят C# код живее в облака като единична изолирана функция. Когато пристигне HTTP пакет, облакът я събужда мигновено, тя изчислява данните за милисекунди и след това заспива обратно, изчиствайки се от RAM паметта. Плащаш само за чистите секунди процесорно време на изпълнение.

## 4. СИСТЕМНИ КАПАНИ: МРЕЖОВИ СРИВОВЕ (HTTPCLIENT CRASH) И КОРЕКЦИЯ

При разпределените микроуслуги най-честите системни крашове възникват поради падания на съседни сървъри.

### 🚨 Капан №1: Срив на HttpClient при грешен адрес (Грешка 503)
*   **Какво правиш:** Твоят `OrderApiController` се опитва да направи мрежово повикване към `https://localhost:5001`, но сървърът на инвентара е паднал или рестартиран в момента.
*   **Точен софтуерен срив (Exception Message) в конзолата на Kestrel:**
    ```text
    HttpRequestException: Failed to connect to localhost port 5001: Connection refused.
    (SocketException: Error 10061 - No connection could be made because the target machine actively refused it)
    ```
*   **Защо се случва:** Понеже комуникацията е синхронна и директна, твоето приложение засича затворена дигитална врата на съседния компютър, хвърля червен ексепшън и прекъсва трансакцията на клиента веднага.
*   **Как да го поправиш (Архитектурно решение):** Обвий мрежовите повиквания в защитни блокове през патeрна **Circuit Breaker** (използвайки библиотека `Polly` в .NET). Ако съседният сървър спре да отговаря 3 пъти подред, софтуерният предпазител „изключва“ автоматично. Вместо да крашва и да товари мрежата, приложението незабавно връща капсулиран кеширан отговор, предпазвайки системата от верижен срив.
