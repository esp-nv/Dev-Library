## 1. ВЕРТИКАЛНО СРЕЩУ ХОРИЗОНТАЛНО МАЩАБИРУЕМОСТ (SCALE-UP VS. SCALE-OUT)

Когато потребителският интерес към уеб платформата нарасне експоненциално, един софтуерен сървър спира да се справя с трафика. Инженерната наука предлага два коренно различни подхода за справяне с натоварването:

*   **Вертикално мащабиране (Scale-up):** Добавяне на повече физически хардуерни ресурси (по-мощни процесорни ядра, по-бърза RAM памет, NVMe твърди дискове) към твоята текуща единствена работеща машина.
    *   *Търговски компромис (Trade-off):* Изключително лесно за изпълнение, защото кодът не се променя. Но носи **тежък хардуерен лимит** (най-скъпият процесор в света пак има таван) и създава риск от пълно спиране на софтуера (`Single Point of Failure`), ако тази единствена машина изгори.
*   **Хоризонтално мащабиране (Scale-out):** Добавяне на още уеб сървъри към мрежовата инфраструктура (напр. вместо 1 гигантски сървър, купуваш 5 малки и евтини сървъра, работещи паралелно).
    *   *Търговски компромис (Trade-off):* Позволява **практически безкрайно мащабиране** в облака чрез Docker/Kubernetes контейнеризация. Но изисква софтуерният код на твоето ASP.NET Core приложение да бъде напълно безсъстоятелен (`Stateless`), за да може всяка заявка да бъде обслужена от произволна машина.

## 2. БАЛАНСИРАНЕ НА НАТОВАРВАНЕТО: РОЛЯ НА NGINX И HAPROXY

За да може хоризонталната мрежа от 5 сървъра да работи единно пред клиента, пред тях се поставя специален софтуерен шлюз, наречен **Балансьор на натоварването (Load Balancer)** (напр. Nginx, HAProxy, AWS ALB).

Клиентът извиква уеб адреса, пакетите удрят първо Load Balancer-а, а той разпределя трафика по специфични софтуерни алгоритми:
*   **Round Robin:** Изпраща заявките последователно по списъка (Заявка 1 ➔ Сървър 1, Заявка 2 ➔ Сървър 2...).
*   **Least Connections:** Изпраща новия потребител към този сървър, който в момента обработва най-малък брой активни HTTP връзки.

### 📄 Примерен архитектурен конфигурационен код на Nginx като Load Balancer (nginx.conf):
```nginx
# Дефинираме групата от нашите самостоятелни ASP.NET Core уеб сървъри (Upstream)
upstream dotnet_kestrel_cluster {
    server 10.0.0.10:5001; # Уеб Сървър №1
    server 10.0.0.11:5001; # Уеб Сървър №2
    server 10.0.0.12:5001; # Уеб Сървър №3
}

server {
    listen 80;
    server_name my-enterprise-app.com;

    location / {
        # Препращаме целия входящ трафик към Kestrel клъстера автоматично
        proxy_pass http://dotnet_kestrel_cluster;
        proxy_set_header Host \$host;
        proxy_set_header X-Real-IP \$remote_addr;
    }
}
```

## 3. ОПТИМИЗАЦИЯ НА ДАННИТЕ: КЕШИРАНЕ, РЕПЛИКАЦИЯ И ШАРДИНГ (SHARDING)

Докато уеб сървърите Kestrel се мащабират хоризонтално изключително лесно (защото не пазят състояние), истинското тясно гърло (`Bottleneck`) на всяка софтуерна архитектура е **Базата данни (SQL Server / PostgreSQL)**, тъй като всички нишки пишат и четат на едно място. Оптимизираме я чрез три стълба:

1.  **Кеширане (Caching):** Изнасяне на най-натоварените четения изцяло в бърза RAM памет (Redis клъстер) с цел светкавичен отговор за милисекунди и пълно разтоварване на хард дисковете на базата.
2.  **Репликация (Replication — Master-Slave):** Копиране на базата данни на няколко машини. Единият сървър е **Master** (в него само се пише и се извършват промени), а останалите са **Slaves / Read Replicas** (те копират автоматично промените от Master-а и обслужват единствено `GET` заявките за четене на клиентите).
3.  **Шардинг (Sharding — Хоризонтално разцепване):** Разделяне на една гигантска SQL таблица на по-малки самостоятелни физически части (Shards) на базата на логически ключ (Sharding Key). Например, поръчките от клиенти в България се записват в База №1 (Shard 1), а поръчките от Германия — в База №2 (Shard 2).

## 4. СИСТЕМНИ КАПАНИ: ЗАГУБА НА СЕСИИ (STICKY SESSIONS) И ГРЕШКИ ПРИ РЕПЛИКАЦИЯ

Хоризонталното мащабиране крие тежки капани за удържане на потребителското състояние, ако архитектурата е проектирана грешно.

### 🚨 Капан №1: Срив на уеб сесията при липса на безсъстоятелност (Stateless нарушаване)
*   **Какво правиш:** Твоето ASP.NET Core приложение използва вградения `HttpContext.Session.SetString()` за съхранение на количката за пазаруване локално в паметта на сървъра. Слагаш приложението зад Nginx Load Balancer с Round Robin алгоритъм.
*   **Бизнес капан (Изчезваща количка):** Потребителят отваря сайта, Заявка 1 удря Сървър 1 и той записва продукта в своята RAM памет. Клиентът натиска бутона „Плащане“, изпраща се Заявка 2. Load Balancer-ът я пренасочва към Сървър 2. Сървър 2 проверява своята RAM памет, не открива такава сесия и изплюва червена грешка, изтривайки количката на клиента.
*   **Как да го избегнеш (Два начина за корекция):**
    1.  *Архитектурният стандарт (Stateless):* Спри използването на локална сесия. Изнасяй състоянието в централна разпределена RAM памет през `AddStackExchangeRedisCache()` или пази токените в JWT Payload клетките.
    2.  *Инфраструктурно закърпване (Sticky Sessions):* Промени конфигурацията на Nginx да използва алгоритъма `ip_hash`. Той привързва IP адреса на потребителя твърдо към един конкретен сървър, гарантирайки, че всички следващи заявки ще удрят само него:
        ```nginx
        upstream dotnet_kestrel_cluster {
            ip_hash; # 🟢 Активира Sticky Sessions - привързва клиента по IP
            server 10.0.0.10:5001;
            server 10.0.0.11:5001;
        }
        ```
