## 1. АНАТОМИЯ НА РАЗЦЕПВАНЕТО: ХОРИЗОНТАЛЕН СРЕЩУ ВЕРТИКАЛЕН ШАРДИНГ

Когато обемът на записите или броят на паралелните SQL трансакции надхвърли тавана на една голяма база данни, системата трябва да премине към разцепване. То бива два вида:

*   **Вертикално Разцепване (Vertical Sharding / Partitioning):**
    *   *Концепция:* Разделяне на една физическа таблица по нейната структура (по колони). Често достъпните и леки колони се изнасят в една база, а тежките текстови блокове — в друга.
    *   *Пример:* Таблица `Users` се цепи на `UsersCore` (пазеща само `Id`, `Username`, `PasswordHash` за бърз Login) и `UsersProfiles` (пазеща `ProfilePictureBlob` и `BiographyText`).
*   **Хоризонтално Разцепване (Horizontal Sharding):**
    *   *Концепция:* Разделяне на таблицата по нейните редове. Схемата и колоните на базата остават напълно идентични на всички сървъри, но различните парчета от реални редове (записи) се разпределят по напълно самостоятелни физически машини (Shards).

## 2. МАТЕМАТИЧЕСКИ АЛГОРИТМИ ЗА ШАРДИНГ (RANGE, HASH, CONSISTENT HASHING)

Начинът, по който софтуерната архитектура изчислява кой ред на кой сървър отива, зависи от избора на **Шардинг Ключ (Sharding Key)**:

### А. Range-Based Sharding (Мащабиране по Диапазони)
*   Данните се разпределят въз основа на предварително дефинирани граници на стойностите на ключа.
*   *Пример:* Потребители с имена от А до И отиват в `Shard 1`, от К до Р — в `Shard 2`, от С до Я — в `Shard 3`.
*   *Проблем:* Води до брутално неравномерно натоварване (ако имаш милиони потребители с буквата „И“ и нито един с „Я“).

### Б. Hash-Based Sharding (Алгоритмичен Хеш)
*   Софтуерът взима стойността на Sharding ключа (напр. `UserId`), прекарва я през математическа хеш функция и прилага оператора за деление с остатък (`Modulo %`) спрямо броя на наличните сървъри.
*   *Математическа формула:*
    \[\text{Shard Index} = \text{Hash}(\text{Sharding Key}) \pmod N\]
    *(Където $N$ е общият брой на физическите бази данни в клъстера).*

### 📄 Примерна C# Логика за Hash-Based Sharding рутер:
```csharp
using System;
using System.Security.Cryptography;
using System.Text;

public class ShardRouter
{
    private readonly int _totalShards;

    public ShardRouter(int totalShards)
    {
        _totalShards = totalShards; // Общ брой физически SQL сървъри в облака
    }

    public int GetShardIndex(string shardingKey)
    {
        using (MD5 md5 = MD5.Create())
        {
            // Превеждаме стринговия ключ (напр. "user_guid_9412") до байтов масив
            byte[] inputBytes = Encoding.UTF8.GetBytes(shardingKey);
            byte[] hashBytes = md5.ComputeHash(inputBytes);

            // Превръщаме първите 4 байта в положително целочислено число
            int hashAsInt = BitConverter.ToInt32(hashBytes, 0) & int.MaxValue;

            // Намираме точния индекс на базата чрез Modulo оператора
            int targetShard = hashAsInt % _totalShards;
            return targetShard; // Връща индекс от 0 до (_totalShards - 1)
        }
    }
}
```

## 3. ПРЕДИЗВИКАТЕЛСТВА ПРИ РАЗПРЕДЕЛЕНИ БАЗИ ДАННИ И ACID ЛИМИТИ

Въпреки че хоризонталният Sharding визуално решава проблема с капацитета, той разрушава основните закони на традиционните релационни бази данни:

1.  **Загуба на ACID Трансакциите (Cross-Shard Transactions Failure):** Ако твоето ASP.NET Core приложение се опита да изпълни една обща трансакция, която модифицира ред в `Shard 1` и ред в `Shard 2`, класическият `DbContext.SaveChanges()` се проваля. Той не може да гарантира атомарност (Atomicity) на две отделни физически машини едновременно.
2.  **Забрана на Сложните Съединения (Joins Collision):** Изпълнението на SQL заявка с `JOIN` оператор между две шардирани таблици е архитектурно невъзможно, освен ако софтуерът не изтегли и двете таблици изцяло в RAM паметта на Kestrel, което срива пропускателната способност (Throughput).

## 4. СИСТЕМНИ КАПАНИ: ГОРЕЩИ ТОЧКИ (HOTSPOTS) И СРИВОВЕ ПРИ КРОС-ШАРД ЗАЯВКИ

### 🚨 Капан №1: Феноменът Гореща Точка (The Hotspot Bottleneck)
*   **Какво правиш:** Проектираш глобална Twitter-подобна система. Избираш за Sharding Ключ полето `CelebrityId` или датата на създаване на поста (`CreatedAt`).
*   **Бизнес капан:** Когато световна известност с милиони последователи публикува пост, милиарди четения и коментари удрят в рамките на една секунда **точно една единствена физическа база данни (напр. Shard 4)**. Всички останали 20 сървъра в клъстера стоят празни и почиват с 0% натоварване, докато `Shard 4` прегрява, препълва I/O лимита на диска и умира, сривайки платформата за милиони потребители.
*   **Как да го избегнеш:** **Никога не избирай Sharding Ключ, който се базира на времеви диапазони или полета с ниска вариация!** Ключът трябва да бъде равномерно разпределен (High Cardinality) — например комбинация от `Hash(UserId + OrderId)`. Това гарантира, че дори при милиарди поръчки, те ще бъдат перфектно разпръснати по всички сървъри поравно.

### 🚨 Капан №2: Срив при промяна на броя на сървърите ($N$) при класическия Модулен Хеш
*   **Какво правиш:** Използваш формулата `Hash(Key) % N` с 3 налични сървъра ($N=3$). Проектът нараства и купуваш 4-ти сървър ($N=4$). Променяш стойността в C# кода.
*   **Фатален системен хаос:** Тъй като числото в оператора за деление се променя от 3 на 4, математическият резултат на абсолютно всички ключове се подменя на мига. Когато потребител А потърси своите стари данни, софтуерът изчислява новата формула, насочва го към `Shard 2`, а реалните му файлове лежат заключени в `Shard 1`. Система влиза в пълен колапс — 99% от кеша и ключовете стават невалидни.
*   **Как да го избегнеш:** За мащабируеми облачни среди не използвай просто `Modulo %`. Задължително налагай алгоритъма **Consistent Hashing** (чрез разпределяне на ключовете по виртуален софтуерен пръстен), при който добавянето на нов сървър размества и релокира едва $\frac{1}{N}$ от общите данни в паметта, запазвайки останалите 90% непокътнати.
