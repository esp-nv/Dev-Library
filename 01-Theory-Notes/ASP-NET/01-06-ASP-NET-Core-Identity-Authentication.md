## 1. КАКВО Е ASP.NET CORE IDENTITY И КАК НИ ПАЗИ СОФТУЕРНО?

В съвременния уеб е абсолютно забранено да пазим паролите на потребителите като обикновен чист текст в базата данни (напр. `Password = "123456"`). Ако хакер пробие SQL Server, той ще открадне самоличността на всички клиенти веднага.

**ASP.NET Core Identity** е пълна, автоматизирана система за сигурност, предоставена от Microsoft. Тя управлява:
*   **Паролно хеширане (Password Hashing):** Използва алгоритъма *PBKDF2* с еднопосочно криптографско разбиване и добавяне на случаен софтуерен „сол“ (Salt). Паролата се превръща в дълъг неразчитаем низ в базата.
*   **Authentication Cookies (Бисквитки за автентификация):** При успешен вход в профила, Identity генерира криптиран софтуерен билет, наречен `Identity Cookie`. Браузърът го пази локално и го прикачва към всяка следваща HTTP заявка, за да знае сървърът Kestrel коя нишка на кой потребител принадлежи.

## 2. ПРАКТИЧЕСКА КОНФИГУРАЦИЯ НА IDENTITY И ЗАЩИТА НА МЕТОДИ

За да активираш защитата, първо трябва да регистрираш услугите на Identity в твоя `DbContext` и `Program.cs`. Класът `IdentityUser` автоматично генерира нужните SQL колони (Username, PasswordHash, Email).

### 📄 1. Софтуерен код на Защитения Контролер:
```csharp
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;

[Authorize] // 🔒 ЖЕЛЯЗНА ЗАЩИТА: Нито един метод в този контролер не може да се извика без валидна бисквитка!
public class ProfileController : Controller
{
    [HttpGet("/api/profile/my-data")]
    public IActionResult GetPrivateData()
    {
        // Чрез вградения обект User извличаме името на текущо логнатия потребител от бисквитката
        string? username = User.Identity?.Name;

        return Ok(new { Message = $"Добре дошли в защитеното табло, {username}!" });
    }

    [Authorize(Roles = "Admin")] // 🔒 РОЛЕВА ЗАЩИТА: Достъпен САМО за потребители с роля Администратор!
    [HttpPost("/api/profile/delete-system-logs")]
    public IActionResult DeleteLogs()
    {
        return Ok(new { Message = "Системните логове бяха изтрити от администратора!" });
    }
}
```

### 🎯 2. Очакван изход (Expected Output в Postman) при УСПЕШЕН вход:
Ако потребителят се е аутентикирал правилно и извика адреса `/api/profile/my-data`, сървърът разчита бисквитката и връща статус `200 OK` и следния JSON:
```json
{
  "message": "Добре дошли в защитеното табло, ivan_developer!"
}
```

## 3. СИСТЕМНИ КАПАНИ: ГРЕШКИ ПРИ НЕОТОРИЗИРАН ДОСТЪП (401 СРЕЩУ 403)

Когато изграждаш защита с Identity, софтуерът хвърля две коренно различни езикови изключения на базата на правата на потребителя. Разбирането на разликата между тях е критично за изпити.

### 🚨 Капан №1: Опит за достъп без вход в профила (Грешка 401)
*   **Какво правиш:** Отваряш чисто нов прозорец в Postman и без да си извикала метода за लॉगिन, изпращаш директна `GET` заявка към защитения адрес `https://localhost:7214/api/profile/my-data`.
*   **Точен върнат статус код от сървъра (Response Status):**
    ```text
    401 Unauthorized (Неаутентикиран / Непознат потребител)
    ```
*   **Защо се случва:** Атрибутът `[Authorize]` спира заявката още на входа на контролера, тъй като в HTTP пакета липсва изискваната криптирана `Identity` бисквитка. Сървърът Kestrel казва: *"Аз изобщо не знам кой си ти, влез първо в профила си!"*.
*   **Как да го избегнеш:** Извикай първо твоя Login API метод, улови върнатата бисквитка и подсигури нейното присъствие в таба `Cookies` или `Headers` на Postman при следващото повикване.

### 🚨 Капан №2: Влязъл си в профила, но нямаш нужните права (Грешка 403)
*   **Какво правиш:** Влизаш успешно в системата с потребителски акаунт, който има стандартна роля `"User"`. След това се опитваш да извикаш администраторския метод `POST` към `/api/profile/delete-system-logs`.
*   **Точен върнат статус код от сървъра (Response Status):**
    ```text
    403 Forbidden (Забранен достъп / Липса на права)
    ```
*   **Защо се случва:** Този път сървърът разчита бисквитката успешно и знае точно кой си ти (`Аутентификацията е успешна`). Когато обаче стигне до втория атрибут `[Authorize(Roles = "Admin")]`, системата проверява твоя акаунт и вижда, че нямаш изискваната роля `"Admin"`. Сървърът казва: *"Аз знам кой си, но ти нямаш бизнес право (Авторизация) да триеш тези данни!"*.
*   **Как да го избегнеш:** Подсигури софтуерно в кода, че при регистрация или промяна на потребителя, на съответния акаунт е наложена правилната роля през класа `RoleManager`, преди да викаш метода.
