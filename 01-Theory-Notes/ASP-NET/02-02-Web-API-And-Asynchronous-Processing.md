## 1. RESTFUL API ДИЗАЙН: ПРАВИЛА ЗА БЕЗСЪСТОЯТЕЛНА КОМУНИКАЦИЯ

За разлика от монолитните уеб страници, които връщат тежък HTML код, **Web API (Application Programming Interface)** платформите връщат чисти, структурирани данни, капсулирани като JSON обекти. Те работят по стандартите на **REST (Representational State Transfer)** архитектурата:

*   **Безсъстоятелност (Stateless):** Сървърът не пази информация за сесии (липсва `app.UseSession()`). Всяка заявка от клиента трябва да носи сама по себе си всички нужни метаданни и токени за сигурност, за да бъде изпълнена.
*   **Идентификация на ресурсите чрез URL:** Пътят описва *колекцията* (съществително име в множествено число), а операцията се определя от HTTP глагола.
    *   `GET /api/v1/students` ➔ Извлича списък (Read).
    *   `POST /api/v1/students` ➔ Добавя нов студент (Create).

## 2. JWT АВТЕНТИФИКАЦИЯ ПОД КАПАКА (АНАТОМИЯ НА СИГУРНОСТТА)

Тъй като NoSQL и облачните REST среди не поддържат традиционните бисквитки за сесия, сигурността се налага чрез **JWT (JSON Web Token)**. Този токен е дълъг низ, разделен на три секции, кодирани в *Base64Url* формат:

```text
  hhhhhh.bbbbbb.ssssss  ➔  [ Header (Алгоритъм) ] . [ Payload (Потребител/Роли) ] . [ Signature (Криптографски подпис) ]
```

Клиентът изпраща този токен в заглавните части на всеки пакет: `Authorization: Bearer <token>`. Изграждаме защитен API метод, който извлича системното ID на логнатия потребител от Payload клетките (Claims) на токена:

### 📄 1. Софтуерен код на API Контролера:
```csharp
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using System.Security.Claims;

[ApiController]
[Route("api/v1/assets")]
[Authorize(AuthenticationSchemes = "Bearer")] // 🔒 Изисква изрично сигурен JWT Bearer Токен
public class AssetApiController : ControllerBase
{
    [HttpGet("my-portfolio")]
    public IActionResult GetUserPortfolio()
    {
        // Чрез ClaimsPrincipal извличаме уникалното ID на потребителя, закодирано вътре в самия токен
        var userId = User.FindFirst(ClaimTypes.NameIdentifier)?.Value;

        if (string.IsNullOrEmpty(userId))
        {
            return Unauthorized(new { Error = "Грешка: Токенът не съдържа валиден NameIdentifier обект!" });
        }

        // Симулация на извличане на финансово портфолио
        var portfolioData = new { OwnerId = userId, AssetCount = 5, TotalValueUSD = 24500.00 };
        return Ok(portfolioData);
    }
}
```

### 🎯 2. Очакван изход (Expected Output в Postman) при УСПЕШЕН токен:
Ако инжектираш валиден JWT токен в таба `Authorization`, бекендът Kestrel връща статус `200 OK` и следния чист JSON:
```json
{
  "ownerId": "usr_94a2b8c5-3f11",
  "assetCount": 5,
  "totalValueUSD": 24500.00
}
```

## 3. НАПРЕДНАЛИ АСИНХРОННИ НИШКИ И КАПАНЪТ THREAD STARVATION

В силно натоварени Enterprise уеб приложения, Kestrel уеб сървърът разпределя трафика в хардуерна структура, наречена **Thread Pool (Пул от нишки)**. Когато използваме чист и дълбок асинхронен модел (`async/await`), нишките се освобождават веднага по време на бавни входно-изходни (I/O) операции (например чакане на тежка заявка от SQL базата данни или отдалечено външно API).

### 🚨 Тежкият капан Thread Starvation (Гладуване на нишките):
Ако в напреднал проект допуснеш хардкоднато синхронно блокиране на нишка (например извикване на бавна операция през `.Result` или `Thread.Sleep()`), тази нишка замръзва. Когато пристигнат 500 паралелни заявки от потребители едновременно, всички нишки в Thread Pool-а се блокират в чакане. Сървърът изразходва лимита си, не може да задели нова нишка за следващите пристигащи пакети и приложението ти спира да отговаря, влизайки в състояние на пълен отказ от обслужване (`Denial of Service`).

## 4. СИСТЕМНИ КАПАНИ: СРИВОВЕ ПРИ НЕВАЛИДНА JWT ВАЛИДАЦИЯ И БЛОКИРАНИЯ

При проектирането на безсъстоятелни API среди най-честите технически крашове се проявяват чрез следните ексепшъни:

### 🚨 Капан №1: Срив на криптографския подпис на токена (Грешка 401)
*   **Какво правиш:** Променяш на ръка една буква от JWT токена в Postman или тайната ти криптографска фраза (`Secret Key`) в `appsettings.json` е била променена. Изпращаш заявката към защитения API Контролер.
*   **Точен върнат статус код от сървъра (Response Status):**
    ```text
    401 Unauthorized (Невалиден или неразпознат токен)
    ```
*   **Точен софтуерен лог зад кулисите в конзолата на Kestrel:**
    ```text
    [WARN] Microsoft.AspNetCore.Authentication.JwtBearer.JwtBearerHandler: Exception occurred while processing message.
    Microsoft.IdentityModel.Tokens.SecurityTokenInvalidSignatureException: Signature validation failed. Keys tried: ...
    ```
*   **Защо се случва:** Сигурността на .NET сканира третата секция на токена (`Signature`). Понеже хешът от изчислените данни не съвпада с оригиналния криптографски ключ, системата засича опит за фалшификация и прекратява заявката на мига.
*   **Как да го поправиш:** Подсигури, че симетрийният криптографски ключ (`SymmetricSecurityKey`), дефиниран при генерирането на токена, съвпада на 100% с настройките в `builder.Services.AddAuthentication().AddJwtBearer()` метода в `Program.cs`.

### 🚨 Капан №2: Използване на блокиращи методи в уеб нишки ( Thread Starvation Trigger )
*   **Какво правиш:** За да спреш изпълнението на кода за 2 секунди с цел симулация, използваш класическия десктоп метод `Thread.Sleep()` вътре в уеб метода на твоето натоварено API.
*   **Очакван лош изход при Performance тест:** Приложението забавя своята работа драстично, времето за реакция скача до небесата, а конзолата започва да изплюва съобщения за недостиг на нишки.
*   **Защо се случва:** `Thread.Sleep(2000)` замразява физически текущата уеб нишка от пула, забранявайки ѝ да върши каквато и да е друга работа. На софтуерно ниво това е блокиране на ценен ресурс.
*   **Как да го поправиш:** Винаги използвай неблокиращия, асинхронен еквивалент **`Task.Delay()`**, придружен задължително от ключовата дума **`await`**. Той освобождава нишката обратно в пула веднага, поддържайки Kestrel в перфектна бойна готовност:
    ```csharp
    // ❌ АНТИ-ПАТЕРН (Убива уеб нишката!):
    Thread.Sleep(2000); 

    // 🟢 ПРАВИЛЕН АРХИТЕКТУРЕН СТАНДАРТ:
    await Task.Delay(2000); // Нишката отива да обслужва други клиенти през тези 2 секунди
    ```
