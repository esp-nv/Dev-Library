## 1. ЗАЩО GIT Е ЗАДЪЛЖИТЕЛЕН: ПРОБЛЕМИТЕ, КОИТО РЕШАВА

В модерната софтуерна разработка проектите се променят постоянно и се пишат от големи екипи. Без система за контрол на версиите (Version Control System - VCS) като **Git**, екипите се сблъскват с фатални проблеми: неволно презаписване на файлове, липса на хронологична история, невъзможност за сигурен заден ход (Rollback) при грешка и пълен хаос при екипна работа.

### Ключево разграничение: Git срещу GitHub
*   **Git:** Софтуерният инструмент (двигателят), който работи локално на твоя компютър и записва хронологичните промени по кода под формата на моментни снимки (Snapshots).
*   **GitHub:** Облачна хостинг платформа (хранилище), която пази отдалечено копие на твоя Git проект и служи за споделяне, съвместна работа и преглед на кода (Pull Requests).

## 2. АНАТОМИЯ НА ПРОФЕСИОНАЛНИЯ COMMIT (АТОМАРНОСТ И КУЛТУРА)

Всеки **Commit** е официален спасителен чекпоинт (Checkpoint) в паметта на твоя проект. Той съдържа уникален 40-символен идентификатор (SHA-1 Hash), информация за автора и текстово съобщение, описващо промяната.

### ⚖️ Good vs. Bad Commits:
*   **Лоша практика (Mystery Commit):** Съобщения като `git commit -m "update"`, `git commit -m "fix bug"` или `git commit -m "stuff"` са напълно безполезни за проследяване след време.
*   **Професионален стандарт (Documentation Commit):** Използвай ясни, императивни съобщения: `git commit -m "Add Movie entity"`, `git commit -m "Configure EF Core DbContext"`.

> **Тестът "И" за Атомарност (Atomic Commits):** Всеки commit трябва да съдържа само една логическа промяна или фичър. Ако твоето съобщение съдържа думата "и" (напр. *"Fix header CSS and update database schema"*), това е ясен знак, че трябва да разбиеш промените в **два отделни, самостоятелни коммита**.

## 3. ПРОФЕСИОНАЛНА ASP.NET СТРУКТУРА И РОЛИ НА ФАЙЛОВЕТЕ

Един правилно структуриран ASP.NET уеб проект съдържа папки за архитектурните слоеве (`/Controllers`, `/Models`, `/Views`) и папка `/wwwroot` за статични уеб ресурси (CSS, JS). В корена на проекта обаче стоят три критични файла, които управляват Git жизнения цикъл:

1.  **`.sln` (Solution File):** Главният входен пункт, който обединява всички подпроекти.
2.  **`appsettings.json`:** Основният конфигурационен файл. **Критично правило:** Никога не качвай реални пароли и производствени тайни (Secrets) вътре в него.
3.  **`.gitignore` — Филтърът за чист код:** Специален текстов файл, който казва на Git кои папки са служебни и трябва да бъдат напълно игнорирани при запис.

### 🛠️ Задължителни .NET изключения вътре в `.gitignore`:
```text
# Генерирани папки при компилация (Build Artifacts)
bin/
obj/

# Специфични настройки на средите за разработка (IDE Settings)
.vs/
.vscode/
*.user

# Конфигурационни файлове, съдържащие пароли и тайни
secrets.json
```

## 4. ЗЛАТНИЯТ README.MD СТАНДАРТ (ЛИЦЕТО НА ПРОЕКТА)

Файлът **`README.md`** (написан на Markdown език) е „предната врата“ на твоето софтуерно хранилище. Проект без детайлен README файл се счита за незавършен на професионално ниво. Той дава бърз технически контекст на проверяващите софтуера инженери и разяснява бизнес целта на приложението.

### 🧭 5-те задължителни компонента на едно софтуерно README:
*   **Заглавие на проекта (Project Title):** Ясно, описателно и техническо име.
*   **Описание (Description):** Какъв реален бизнес проблем решава това приложение и за кои потребители е предназначено.
*   **Технологичен стек (Tech Stack):** Специфичен списък с използваните версии на рамките (напр. *.NET 8.0, EF Core, SQL Server, AutoMapper*).
*   **Инструкции за инсталация (Setup Instructions):** Ръководство стъпка по стъпка как един непознат програмист да клонира проекта, да обнови връзките, да изпълни миграциите (`dotnet ef database update`) и да стартира кода локално за секунди.
*   **Потребителски роли и права (Usage & Permissions):** Спецификация на правата в уеб системата (напр. *Guest* – разглежда, *User* – наема, *Admin* – контролира наличностите).
