## 1. КАК ПЪТУВАТ ДАННИТЕ: ПАКЕТНА КОМУНИКАЦИЯ, IP И DNS

Всяка уеб информация се превежда до дигитални битове и се разбива на малки парчета, наречени **Пакети (Packets)**, преди да бъде изпратена по мрежата [Протоколи, 13]. Всеки пакет пътува независимо по различни трасета (оптични кабели, сателити) и се сглобява обратно на финалната спирка [Протоколи, 13, 22].

Комуникацията се управлява от два фундаментални компонента:
*   **IP Адрес (Internet Protocol):** Уникалният цифров координатен адрес на всяко устройство в мрежата [Протоколи, 16].
    *   *IPv4:* 32-битов адрес, изразен като 4 числа, разделени с точка (напр. `192.168.10.5`). Осигурява около 4.3 милиарда адреса [Протоколи, 17, 18].
    *   *IPv6:* 128-битов съвременен стандарт, изразен в шестнадесетична бройна система и разделен с двоеточие (напр. `3FFE:F200:...`), осигуряващ практически безкраен брой адреси [Протоколи, 18, 19].
*   **DNS (Domain Name System):** Глобален преводач (телефонен указател), който превръща четимите от хора имена на домейни (напр. `www.softuni.bg`) в реални машинни IP адреси за браузъра [Протоколи, 20].

## 2. ТРАНСПОРТНИЯТ СЛОЙ: TCP СРЕЩУ UDP И МРЕЖОВИТЕ МОДЕЛИ

Протоколът **HTTP**, на който се базира целият уеб трафик на ASP.NET Core, живее на най-високото (**Приложно ниво — Application Layer**) на мрежовия модел [Протоколи, 29, 30]. За да пренася данни обаче, той стъпва върху **Транспортния слой (Transport Layer)** [Протоколи, 29, 30].

### Сравнение на транспортните среди:
*   **TCP (Transmission Control Protocol):** Дава абсолютен приоритет на **надеждността и сигурността** [Протоколи, 26]. Той извършва одитиране и проверка на пакетите — подрежда ги хронологично, проверява размерите им и изисква повторно изпращане, ако някое парче е изгубено [Протоколи, 22, 23, 24]. Това е основата на уеб сайтовете.
*   **UDP (User Datagram Protocol):** Дава абсолютен приоритет на **скоростта и ниската латентност** [Протоколи, 26]. Работи на принципа „изстреляй и забрави“ (Fire-and-forget) — изпраща потока и не проверява дали е пристигнал (използва се за видео разговори, стрийминг и онлайн игри) [Протоколи, 25].

## 3. АНАТОМИЯ НА URL АДРЕСА И HTTP СЪОБЩЕНИЯТА

Всеки уеб ресурс се намира чрез форматиран стринг, наречен **URL (Uniform Resource Locator)** [Протоколи, 39, 40]. 

### Разглобяване на един URL адрес:
```text
  http://  mysite.com  :8080  /demo/index.php  ?id=27&lang=en  #slides
  ───────  ──────────  ─────  ───────────────  ──────────────  ───────
 Protocol     Host      Port        Path        Query String   Fragment
```
*(Параметрите са извлечени от [Протоколи, 41]).*

Когато браузърът (Client) извика този адрес, он изпраща към Kestrel сървъра **HTTP Request Message** със следната сурова текстова структура [Протоколи, 43]:

```text
POST /demo/index.php HTTP/1.1  <── [Request Line: Метод, Път и Версия]
Host: mysite.com               <── [Headers: Метаданни, Браузър, Кодировка]
Content-Type: application/json
                               <── [Празен ред - Задължителен разделител!]
{ "id": 27, "lang": "en" }     <── [Body: Опционални данни / JSON тяло]
```

### Съпоставка на методите с CRUD операциите [Протоколи, 44]:
*   **`GET`** ➔ `READ` (Извличане на данни - няма тяло / Body).
*   **`POST`** ➔ `CREATE` (Записване на нов ресурс на сървъра).
*   **`PUT`** ➔ `UPDATE` (Пълна подмяна/заместване на съществуващ обект).
*   **`PATCH`** ➔ `UPDATE` (Частична модификация само на някои полета).
*   **`DELETE`** ➔ `DELETE` (Премахване на ресурс от диска).
