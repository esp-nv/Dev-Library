# 01-01. Жизнен цикъл и Middleware компоненти в ASP.NET Core

**Цел:** Разбиране на пътя на една HTTP заявка от браузъра на клиента през уеб сървъра Kestrel до контролерите, как се изгражда HTTP конвейерът чрез Middleware компоненти и как се контролира двупосочният поток на данни.

## 1. АНАТОМИЯ НА HTTP КОНВЕЙЕРА (THE REQUEST PIPELINE)

В ASP.NET Core уеб сървърът **Kestrel** приема входящата HTTP заявка и я изпраща по затворен софтуерен тръбопровод, наречен **Request Pipeline**. Този тръбопровод е изграден от отделни малки софтуерни блокове, наречени **Middleware (Междинен софтуер)**.

Всеки Middleware компонент има точно две задачи:
1.  **Преди изпълнението:** Може да прегледа, промени или филтрира входящата заявка, след което да я предаде на следващия компонент по веригата чрез делегата `next()`.
2.  **След изпълнението:** Когато заявката стигне до края (Контролера) и се генерира отговор, потокът се връща **обратно по същия път в огледален ред**. Всеки Middleware може да промени изходящия HTTP отговор, преди той да напусне сървъра към браузъра.

### 🗺️ Визуален модел на двупосочния поток:
```text
   HTTP Request  ──> [ Middleware 1 ] ──(next)──> [ Middleware 2 ] ──(next)──> [ Контролер / API ]
                           │                                  │                        │
   HTTP Response <── [ Логване / Екшън ] <─────────── [ Валидация ] <──────────────────┘
```

> **Късо съединение (Short-circuiting):** Даден Middleware може да реши да **НЕ** извика `next()`. Тогава конвейерът прекъсва внезапно и отговорът се връща веднага. Пример: Ако `AuthMiddleware` открие, че потребителят няма права, той блокира заявката и мигновено връща статус `401 Unauthorized`, без изобщо да натоварва контролера на базата данни.

## 2. ХРОНОЛОГИЧЕН РЕД НА СИСТЕМНИТЕ MIDDLEWARE КОМПОНЕНТИ

В ASP.NET Core **редът на регистриране на Middleware компонентите в `Program.cs` е закован**. Ако объркаш местата на два компонента, приложението ти или ще изтече данни, или ще спре да работи правилно.

Ето златния архитектурен ред, по който се подрежда софтуерният тръбопровод:

```csharp
var app = builder.Build();

// 1. Първа защита: Хваща абсолютно всички необработени изключения по веригата
if (app.Environment.IsDevelopment()) { app.UseDeveloperExceptionPage(); }
else { app.UseExceptionHandler("/Home/Error"); }

// 2. Сигурност на мрежата: Пренасочва HTTP заявките автоматично към HTTPS порт
app.UseHttpsRedirection();

// 3. Статични файлове: Връща директно снимки, CSS и JS без да натоварва C# кода
app.UseStaticFiles();

// 4. Маршрутизация: Разглобява URL адреса и разбира кой Контролер трябва да се извика
app.UseRouting();

// 5. Корпоративна защита (CORS): Дефинира кои външни сайтове и фронтенд домейни имат достъп до това API
app.UseCors();

// 6. Аутентификация: Проверява "Кой си ти?" (Разчита JWT токени или бисквитки)
app.UseAuthentication();

// 7. Авторизация: Проверява "Имаш ли право да правиш това?" (Проверява роли и политики)
app.UseAuthorization();

// 8. Финална спирка: Изпълнява реалния код вътре в твоите Контролери (Endpoints)
app.MapControllers();

app.Run();
```

## 3. РАЗЛИКАТА МЕЖДУ RUN, USE И MAP ОПЕРАЦИИТЕ

За да регистрираш твои собствени Middleware правила в `Program.cs`, .NET ни предоставя три различни метода:

*   **`app.Use(...)` — Кръстопътният пазител:** Позволява ти да изпълниш код и **задължително** ти дава достъп до делегата `next()`, за да продължиш веригата напред. Използва се за логване, валидиране на заглавни части (Headers) и модификации.
*   **`app.Run(...)` — Финалната тапа (Terminal Middleware):** Този метод прекратява конвейера. Той **не** притежава и не може да извика `next()`. Всичко, което напишеш след `app.Run()`, никога няма да бъде достигнато от HTTP заявката.
*   **`app.Map(...)` — Разклонителят:** Разклонява тръбопровода на базата на URL пътя. Например `app.Map("/api/health", ...)` ще създаде напълно отделен мини-конвейер само за този адрес.

## 4. КРИТИЧНИ АРХИТЕКТУРНИ КАПАНИ И ГРЕШКИ

### Капан 1: Размяна на местата на `UseAuthentication()` и `UseAuthorization()`
*   **Какво се случва:** Регистрираш авторизацията преди аутентификацията (`app.UseAuthorization();` последвано от `app.UseAuthentication();`). Програмата ще започне да хвърля статус `403 Forbidden` или ще забие с грешка при всеки опит за достъп до защитен метод.
*   **Защо се случва:** Системата се опитва да провери дали потребителят има роля "Администратор", *преди* изобщо да е проверила кой е той и дали JWT токенът му е валиден.
*   **Как да избегнеш:** Винаги първо проверяваш идентичността (`UseAuthentication`) и чак тогава налагаш правата (`UseAuthorization`).

### Капан 2: Забравен `await next()` в `app.Use()` блок
*   **Какво се случва:** Написваш твой къстъм Middleware за логване на заявки, но в края на кода забравиш да напишеш `await next();`. Браузърът на клиента ще замръзне в безкрайно чакане, а контролерите ти никога няма да се изпълнят.
*   **Защо се случва:** Тъй като не си извикала следващото звено, ти си предизвикала неволно "късо съединение" и си превърнала твоя Middleware в терминален (`Run`).
*   **Как да избегнеш:** Винаги подсигурявай извикването на `await next();` във всеки Use блок, освен ако изрично не искаш да блокираш заявката по бизнес причина.
