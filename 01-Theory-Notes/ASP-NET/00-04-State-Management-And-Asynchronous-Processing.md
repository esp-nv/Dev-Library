## 1. ПРOБЛЕМЪТ STATELESS: КАKВО Е STATE MANAGEMENT?

По своята дълбока софтуерна архитектура протоколът **HTTP е безсъстоятелен (Stateless)** [Протоколи, 39]. Това означава, че всяка една HTTP заявка е напълно независима и изолирана от предходната [Протоколи, 43]. Уеб сървърът Kestrel няма памет — той не знае дали заявката, която пристига в момента, идва от същия потребител, който преди една секунда е въвел правилната си парола на страницата за вход.

**State Management (Управление на състоянието)** е съвкупност от техники и технологии, които ни позволяват да „залепим“ отделните заявки една за друга, да създадем изкуствена памет за браузъра и да поддържаме състоянието на потребителя (напр. пазарен кош, вход в профил) [Git, 21].

## 2. COOKIES (БИСКВИТКИ) И SESSION (СЕСИЯ) В C# КОДА

За да помни информация между заявките, софтуерът използва два основни компонента, управлявани през обекта `HttpContext` в ASP.NET Core [Git, 21]:

### А. Cookies (Бисквитки — Запис при Клиента)
Малки текстови файлове, съхранявани в браузъра на потребителя [Git, 21]. Сървърът ги записва чрез `Response.Cookies.Append` и автоматично ги получава обратно при следваща заявка през `Request.Cookies` [Протоколи, 43].

```csharp
// 1. ЗАПИСВАНЕ НА БИСКВИТКА: Изпраща се от бекенда към браузъра на клиента
[HttpGet("/api/state/set-cookie")]
public IActionResult SetCookie()
{
    var options = new CookieOptions
    {
        Expires = DateTime.UtcNow.AddDays(7), // Бисквитката ще живее точно 7 дни
        HttpOnly = true, // Желязна защита: Предотвратява кражба на бисквитката през JavaScript (XSS атаки)
        Secure = true    // Бисквитката пътува само по криптирана HTTPS връзка
    };

    Response.Cookies.Append("UserTheme", "Dark", options);
    return Ok("Бисквитката за тема е записана успешно в браузъра!");
}

// 2. ЧЕТЕНЕ НА БИСКВИТКА: Браузърът я праща автоматично при всяко следващо кликване
[HttpGet("/api/state/get-cookie")]
public IActionResult GetCookie()
{
    if (Request.Cookies.TryGetValue("UserTheme", out string? theme))
    {
        return Ok($"Избраната тема на потребителя е: {theme}");
    }
    return Ok("Няма открита бисквитка. Зарежда се стандартна тема.");
}
```

#### 🎯 Очакван изход в Postman / Браузър:
Ако извикаш `/api/state/get-cookie` след като вече си посетила първия адрес, браузърът ти връща:
```text
Status: 200 OK
Избраната тема на потребителя е: Dark
```

### Б. Session (Сесия — Сигурна памет на Сървъра)
Сигурно пространство в RAM паметта на уеб сървъра за критични бизнес данни [Git, 21]. В браузъра се пази единствено едно служебно **Session ID** под формата на бисквитка, което отключва съответната кутия с данни на сървъра [Git, 21].

```csharp
// Преди да използваш Session, той трябва да бъде активиран в Program.cs: app.UseSession();

// 1. ЗАПИСВАНЕ В СЕСИЯТА: Данните остават сигурно скрити в RAM паметта на сървъра
[HttpGet("/api/state/start-session")]
public IActionResult StartSession()
{
    HttpContext.Session.SetString("UserRole", "Administrator");
    HttpContext.Session.SetInt32("CartItemsCount", 3);
    
    return Ok("Сесията е стартирана. Критичните данни са заключени на сървъра!");
}

// 2. ЧЕТЕНЕ ОТ СЕСИЯТА: Извлича се мигновено на базата на Session ID токена от браузъра
[HttpGet("/api/state/read-session")]
public IActionResult ReadSession()
{
    string? role = HttpContext.Session.GetString("UserRole");
    int? cartCount = HttpContext.Session.GetInt32("CartItemsCount");

    if (role == null) return Unauthorized("Сесията е изтекла или не съществува.");

    return Ok($"Добре дошли! Вие сте влезли като: {role}. Продукти в количката: {cartCount}");
}
```

#### 🎯 Очакван изход в Postman / Браузър:
Ако извикаш `/api/state/read-session` при активна сесия, ще получиш:
```text
Status: 200 OK
Добре дошли! Вие сте влезли като: Administrator. Продукти в количката: 3
```

## 3. АСИНХРОННА ОБРАБОТКА (ASYNCHRONOUS PROCESSING) ПОД КАПАКА

Когато милиони потребители едновременно отворят твоя сайт, уеб сървърът Kestrel разпределя заявките в т.нар. **Thread Pool (Пул от нишки)**.

*   **Синхронна обработка (Блокираща):** Пристига заявка ➔ заделя се Thread (процесорна нишка) ➔ нишката отива до базата данни и засяда в чакане диска да отговори. Докато чака, тази нишка е напълно замръзнала и блокирана — тя не може да обслужва други клиенти. При голям трафик наличните нишки свършват (`Thread Starvation`) и сайтът забива.
*   **Асинхронна обработка (Неблокираща през `async/await`):** Когато кодът ти извика асинхронна операция (напр. извличане на студенти от базата), нишката не засяда в чакане. Тя незабавно се освобождава, връща се в Thread Pool-а и обслужва следващите пристигащи потребители. Когато базата данни е готова с резултата, хардуерът изпраща сигнал, IoC контейнерът взима произволна свободна нишка от пула и тя довършва изпълнението на метода.

### 🛠️ Кодов пример за Асинхронен уеб контролер:
```csharp
// Маркираме метода с async и задължително връщаме Task<IActionResult> (Софтуерно обещание за бъдещ резултат)
[HttpGet("/api/students/async-list")]
public async Task<IActionResult> GetAllStudentsAsync()
{
    // Използваме ключовата дума await. Нишката се освобождава веднага, докато SQL Server чете диска!
    var students = await _context.Students.ToListAsync(); 

    return Ok(students); // Методът се довършва от следващата свободна нишка в пула
}
```

## 4. СИСТЕМНИ КАПАНИ: МЪРТВА ХВАТКА НА НИШКИТЕ (DEADLOCKS)

Един от най-тежките архитектурни капани при уеб програмирането възниква, когато извикаш асинхронна операция по синхронен начин.

### 🚨 Капан №1: Синхронно викане през свойствата `.Result` или `.Wait()`
*   **Какво правиш:** Вместо да използваш ключовата дума `await`, ти извикваш свойството `.Result` директно върху асинхронен метод в твоя контролер, опитвайки се да вземеш данните насила.
*   **Очакван лош изход в браузъра:** Сайтът замръзва в безкрайно зареждане, а след около 30-60 секунди браузърът прекратява хода си поради изтекло време за реакция (`Gateway Timeout`).

### ⚙️ Точен софтуерен механизъм на срива:
```csharp
// ❌ АНТИ-ПАТЕРН (Предизвиква Deadlock и срива Kestrel сървъра!):
[HttpGet("/api/data/deadlock")]
public IActionResult GetBadData()
{
    // Свойството .Result блокира текущата уеб нишка и я кара да чака!
    var data = _service.GetRecordsAsync().Result; 
    return Ok(data);
}
```
1. Входящата HTTP заявка заема Нишка №1 от пула.
2. Нишка №1 извиква асинхронния метод и засяда на свойството `.Result`, блокирайки текущия контекст на изпълнение.
3. Асинхронният метод приключва работата си на заден план в хардуера и се опитва да се върне обратно в уеб контекста, за да предаде данните.
4. Тъй като Нишка №1 държи контекста блокиран, асинхронната операция не може да стъпи вътре. Двата процеса влизат в безкрайна **Мъртва хватка (Deadlock)**.

### 🟢 Как да го избегнеш:
Винаги пренасяй `async` и `await` по абсолютно целия софтуерен път на твоето уеб приложение:
```csharp
// 🟢 ПРАВИЛЕН АРХИТЕКТУРЕН СТАНДАРТ:
[HttpGet("/api/data/safe")]
public async Task<IActionResult> GetGoodData()
{
    // Акуратна неблокираща обработка - нишката се освобождава веднага
    var data = await _service.GetRecordsAsync(); 
    return Ok(data);
}
```
