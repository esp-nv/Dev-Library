**Цел:** Пълно софтуерно разглобяване на интерфейса, работните прозорци и напредналите функционалности в Postman за симулиране на HTTP клиенти, управление на CRUD заявки и диагностика на REST API среди.

## 1. СТРАНИЧНА КОНТРОЛНА КУТИЯ (SIDEBAR: COLLECTIONS, ENVIRONMENTS, HISTORY)

Лявата вертикална лента в Postman служи като командно табло за организиране на твоите софтуерни уеб проекти:

*   **Collections (Колекции):** Логически папки, в които групираш заявките си за конкретен проект (напр. папка `StudentManagement API`). Спестява време, тъй като не се налага да пренаписваш URL адресите наново всеки ден.
*   **Environments (Среди):** Специфични софтуерни превключватели, които ти позволяват да дефинираш променливи (Variables). Например дефинираш променлива `{{baseUrl}}`. Когато тестваш локално, тя сочи към `https://localhost:7214`, а когато проектът се качи на реален сървър, просто превключваш средата на `Production` и променливата автоматично се сменя с реалния уеб адрес, без да пипаш заявките си.
*   **History (История):** Хронологичен дневник на абсолютно всяка HTTP заявка, която си изпратила. Изключително полезна за бърз заден ход и преглед на тестовете от по-ранния ден.

## 2. ПРОЗОРЕЦ ЗА ИЗГРАЖДАНЕ НА ЗАЯВКАТА (REQUEST BUILDER: PARAMS, HEADERS, BODY)

Централният прозорец съответства на суровата текстова структура на HTTP протокола и се разделя на три ключови компонента:

*   **Params (Параметри):** Управлява Query String параметрите в URL адреса. Ако въведеш ключ `page` и стойност `2`, Postman автоматично ще го допише в заглавния адрес: `?page=2`.
*   **Headers (Заглавни части):** Мястото за вкарване на метаданни. При работа с ASP.NET Core уеб API-та най-критичният заглавен параметър е: `Content-Type: application/json`. Той казва на C# сървъра Kestrel, че му изпращаме структуриран JSON текст, а не обикновен текст.
*   **Body (Тяло на заявката):** Използва се при `POST`, `PUT` и `PATCH` операции за пренос на големи обекти данни на диска. За реална работа се избира опцията **`raw`** и от падащото меню вдясно задължително се маркира **`JSON`**:
    ```json
    {
      "name": "Геймърска клавиатура",
      "price": 120.00
    }
    ```

## 3. НАПРЕДНАЛИ ТАБОВЕ ЗА СИГУРНОСТ И СКРИПТОВЕ (AUTHORIZATION, PRE-REQUEST, TESTS)

Тези три прозореца се намират между URL редицата и тялото и отварят вратите към автоматизацията и уеб сигурността:

*   **Authorization (Авторизация):** Използва се за достъп до уеб методи, защитени с пароли или роли. От падащото меню се избира най-модерният стандарт **`Bearer Token`** и вътре се поставя дългият криптиран **JWT (JSON Web Token)**, който ASP.NET Core Identity ти връща при успешен вход в профила ти.
*   **Pre-request Script:** Прозорец, в който можеш да пишеш JavaScript код, който се изпълнява **ПРЕДИ** Postman да изпрати HTTP пакета по мрежата (напр. динамично генериране на днешна дата или криптиране на данни).
*   **Tests (Тестове):** JavaScript прозорец, който се изпълнява **СЛЕД** като сървърът Kestrel върне отговор. Тук се пишат автоматизирани асерции (Assertions) за изпити и контроли:
    ```javascript
    // Автоматичен тест: Проверява дали сървърът ни е върнал статус 200 OK
    pm.test("Статус кодът е 200", function () {
        pm.response.to.have.status(200);
    });
    ```

## 4. ПРОЗОРЕЦ ЗА АНАЛИЗ НА ОТГОВОРА (RESPONSE PANE: STATUS, BODY, COOKIES)

Долният голям прозорец се ражда чак тогава, когато натиснеш бутона **`Send`**. Той ти показва какво точно е изчислил твоят C# бекенд код:

*   **Status (Статус код и време):** Най-важната бизнес метрика. Показва ти дигиталния отговор (напр. `201 Created` при успешен запис, `401 Unauthorized` при липсващ токен или `404 Not Found`). Виждаш и времето за реакция в милисекунди (`Latency`).
*   **Response Body (Pretty, Raw, Preview):** Показва суровия JSON или HTML резултат, дошъл от сървъра. Опцията `Pretty` автоматично го форматира с цветни кодове и отстояния за максимално лесно четене от програмиста.
*   **Cookies & Headers:** Показва бисквитките, които ASP.NET сървърът се опитва да запише в твоя браузър (напр. `.AspNetCore.Identity.Application` бисквитка за сесия), и системните заглавия на Kestrel.

## 5. ЧЕСТИ ГРЕШКИ ПРИ ТЕСТВАНЕ И КАК ДА ГИ ПОПРАВИМ

### Капан 1: Тотален срив със статус 415 (Unsupported Media Type)
*   **Защо се случва:** Пишеш JSON обект в Body-то, но си оставила типа на `Text` или `GraphQL` в Postman. ASP.NET Core отхвърля пакета моментално.
*   **Решение:** Влез в таб `Body` ➔ избери `raw` ➔ от падащото меню вдясно изрично избери **`JSON`**. Това автоматично ще добави нужния `Content-Type` заглавен маркер.

### Капан 2: Червена системна SSL грешка при локално тестване (Self-signed Certificate)
*   **Защо се случва:** Тъй като твоето C# приложение работи на `localhost`, то използва временен локален криптографски сертификат. Понеже е защитна програма, Postman се уплашва и блокира мрежовия ход насила.
*   **Решение:** Отиди в настройките (Иконката със зъбно колело в горния десен ъгъл ➔ **Settings** ➔ таб **General**) и изключи флага **`SSL certificate verification`** на **`OFF`**. Това ще позволи свободно тестване в локални среди за разработка.
