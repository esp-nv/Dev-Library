## 1. ГОЛЯМОТО ПРЕЧИСТВАНЕ: КАКВО ОТПАДНА ОТ СТАРИТЕ ВЕРСИИ?

Когато Microsoft пренаписаха уеб платформата си изцяло от нулата (раждането на .NET Core), те взеха радикално решение: **да отрежат и изхвърлят абсолютно всички тежки Windows-зависими технологии**, които забавяха работата на уеб сървърите.

### ❌ Списък на напълно отпадналите софтуерни компоненти:
*   **`System.Web.dll`:** Най-тежката системна библиотека в стария .NET Framework. Тя управляваше HTTP заявките, но беше толкова силно обвързана с Windows и уеб сървъра IIS, че правеше крос-платформената работа невъзможна.
*   **`Global.asax`:** Файл за глобални събития (`Application_Start`, `Session_Start`). Днес неговата роля е изцяло иззета от лекия конвейер в `Program.cs`.
*   **`web.config`:** Огромен XML файл за конфигурации и настройки на сървъра. Заменен е от леки и лесни за четене JSON структури (`appsettings.json`).
*   **`Web Forms (.aspx)`:** Старата компонентна уеб система, която симулираше десктоп приложения чрез тежки механизми като `ViewState` (скрито пренасяне на състоянието на целия екран в едно скрито текстово поле).

## 2. АРХИТЕКТУРНА СЪПОСТАВКА: ПРЕДИ СРЕЩУ СЕГА

Начинът, по който се сглобява, конфигурира и стартира едно уеб приложение, претърпя коренна еволюция:

| Архитектурен компонент | Как се правеше преди (ASP.NET MVC 5) | Как се прави сега (ASP.NET Core / .NET 8+) |
| :--- | :--- | :--- |
| **Входна точка (Entry Point)** | Приложението нямаше `Main` метод. То се стартираше като библиотека, прикачена насила към уеб сървъра IIS. | Приложението е чиста, независима **Конзолна програма** с класически `static void Main` метод (скрит зад Top-Level Statements в `Program.cs`). |
| **Уеб сървър (Web Server)** | Изцяло зависим от големия Windows IIS сървър. | Приложението си носи собствена, вградена, лека и крос-платформена уеб машина, наречена **Kestrel**. |
| **Конфигурации** | XML файлове (`web.config`), които изискваха рестарт на уеб сървъра при промяна. | Гъвкави, динамични JSON файлове (**`appsettings.json`**), които се зареждат и опресняват директно в паметта. |
| **Зависимости (DI)** | Липсваше вградена DI. Изискваше ръчно инсталиране на външни библиотеки (Autofac, Ninject). | **Вграден на native системно ниво IoC контейнер** през интерфейса `IServiceCollection`. |

## 3. ПЛЮСОВЕ, МИНУСИ И ТЪРГОВСКИ КОМПРОМИСИ (TRADE-OFFS)

В софтуерното инженерство няма перфектни технологии — всяко архитектурно решение е компромис (Trade-off). Ето как се съпоставят двете среди:

### 🟢 Модерното ASP.NET Core
*   **Плюсове:** 
    *   *Брутална производителност:* Премахването на `System.Web` направи платформата до 10 пъти по-бърза от Node.js и Java в независимите TechEmpower тестовете.
    *   *Крос-платформеност:* Спестява огромен разход за лицензи, тъй като софтуерът може да се хоства в евтини Linux Docker контейнери.
    *   *Модулност:* Приложението стартира напълно празно. Чрез Middleware добавяш само тези пакети, от които наистина имаш нужда, без излишен баласт в паметта.
*   **Минуси:** 
    *   *Липса на задна съвместимост:* Стари големи корпоративни системи, писани на Web Forms, не могат да се прехвърлят автоматично към Core — изисква се пълно пренаписване на кода от нулата.

### 🔴 Класическият ASP.NET Framework (Legacy)
*   **Плюсове:** Изключително стабилен за стари затворени системи, които не са променяни от 15 години и са тясно обвързани със специфичен Microsoft хардуер.
*   **Минуси:** Огромен разход на RAM памет, обвързаност само с Windows и бавен жизнен цикъл на заявките поради остарялата архитектура.

## 4. СИСТЕМНИ КАПАНИ: ГРЕШКИ ПРИ МИГРАЦИЯ НА КОНФИГУРАЦИИТЕ

Когато преминаваш от стара архитектура към ASP.NET Core, най-честите сривове в конфигурационния код възникват при четенето на параметри.

### 🚨 Капан №1: Опит за използване на стария `ConfigurationManager`
*   **Какво правиш:** Опитваш се да прочетеш Connection String от базата данни по стария начин, използвайки библиотека `System.Configuration`:
    ```csharp
    // ❌ АНТИ-ПАТЕРН (Ще върне NULL или ще срине приложението в ASP.NET Core!):
    string conn = ConfigurationManager.ConnectionStrings["DefaultConnection"].ConnectionString;
    ```
*   **Точно съобщение за грешка (Exception Message):**
    ```text
    NullReferenceException: Object reference not set to an instance of an object.
    ```
*   **Защо се случва:** В ASP.NET Core старият файл `web.config` не съществува. Тъй като няма откъде да прочете XML структурата, стария мениджър връща `null`, което срива следващите методи по веригата.
*   **Как да го поправиш:** Използвай модерното вградено инжектиране на `IConfiguration` и чети директно от `appsettings.json`:

```json
// 1. Настройката в appsettings.json:
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=Localhost;Database=MyDb;Trusted_Connection=True;"
  }
}
```

```csharp
// 2. Правилният архитектурен стандарт в C# Контролера:
public class HomeController : Controller
{
    private readonly IConfiguration _configuration;

    // Вграденият IoC контейнер инжектира конфигурацията автоматично!
    public HomeController(IConfiguration configuration)
    {
        _configuration = configuration;
    }

    public IActionResult Index()
    {
        // Акуратно и сигурно четене на низа от JSON файла
        string? conn = _configuration.GetConnectionString("DefaultConnection");
        return Ok($"Успешна връзка към: {conn}");
    }
}
```

#### 🎯 Очакван изход (Expected Output в браузъра):
```text
Status: 200 OK
Успешна връзка към: Server=Localhost;Database=MyDb;Trusted_Connection=True;
```
