## 1. КАК ПЪТУВАТ ДАННИТЕ: ПАКЕТНА КОМУНИКАЦИЯ, IP И DNS

Всяка уеб информация се превежда до дигитални битове (нули и единици). За да се предаде тази памет по уеб мрежата, тя се разбива на малки парчета с фиксиран обем, наречени **Пакети (Packets)**. Всеки пакет пътува самостоятелно по наличните трасета и се сглобява обратно на крайната дестинация.

### Координация на трафика:
*   **IP Адрес (Internet Protocol):** Уникален машинен координатен адрес. 
    *   *IPv4:* 32-битова йерархична структура, представена като четири числа от 0 до 255, разделени с точка (напр. `192.168.10.5`). Осигурява около 4.3 милиарда адреса.
    *   *IPv6:* 128-битов съвременен стандарт (измислен поради недостиг на IPv4 адреси). Изразен е в шестнадесетична бройна система и е разделен с двоеточие (напр. `3FFE:F200:0234:AB00:0123:4567:8901:ABCD`).
*   **DNS (Domain Name System):** Глобална децентрализирана база данни, работеща като „телефонен указател“. Превежда четимите от хора уеб домейни (напр. `www.softuni.bg`) в сурови машинни IP адреси.

## 2. ТРАНСПОРТНИЯТ СЛОЙ: TCP СРЕЩУ UDP И МРЕЖОВИТЕ МОДЕЛИ

Вместо сложния 7-слоен OSI модел (който е за мрежови инженери), софтуерната разработка използва опростения 4-слоен **TCP/IP модел**:

```text
 ┌─────────────────────────────────────────────────────────────────────────┐
 │ 4. Application Layer  ──> [ HTTP, HTTPS, DNS, SMTP, FTP ]               │
 ├─────────────────────────────────────────────────────────────────────────┤
 │ 3. Transport Layer    ──> [ TCP, UDP, QUIC ]                            │
 ├─────────────────────────────────────────────────────────────────────────┤
 │ 2. Internet Layer     ──> [ IP (IPv4 / IPv6), ICMP ]                    │
 ├─────────────────────────────────────────────────────────────────────────┤
 │ 1. Link Layer         ──> [ Ethernet, Physical Hardware / Wires ]       │
 └─────────────────────────────────────────────────────────────────────────┘
```
*(Архитектурата съответства на).*

Модерният уеб се върти около два коренно различни транспортни протокола:

### А. TCP (Transmission Control Protocol) — Надеждният одитор
*   **Философия:** Изгражда твърда софтуерна сесия. Използва заглавната информация на пакетите, за да провери дали всички парчета са пристигнат в точния ред и без грешки. Ако открие несъответствие, изисква повторно изпращане.
*   **Търговски компромис (Trade-off):** Гарантира **100% надеждност на данните**, но носи по-високо мрежово забавяне (`Latency`) поради постоянните проверки.

### Б. UDP (User Datagram Protocol) — Бързият куриер
*   **Философия:** Работи на принципа „изстреляй и забрави“ (Fire-and-forget). Изпраща пакетите по мрежата без предварително изградена сесия и без изобщо да го интересува дали отсрещната страна ги получава (напр. при стрийминг, видео разговори).
*   **Търговски компромис (Trade-off):** Гарантира **максимална скорост**, но има риск от загуба на данни.

## 3. АНАТОМИЯ НА URL АДРЕСА И СУРОВИТЕ HTTP СЪОБЩЕНИЯ

Всеки уеб ресурс се локализира чрез уникален форматиран низ, наречен **URL (Uniform Resource Locator)**.

### Разглобяване на URL структурата:
```text
  http://  mysite.com  :8080  /demo/index.php  ?id=27&lang=en  #slides
  ───────  ──────────  ─────  ───────────────  ──────────────  ───────
 Protocol     Host      Port        Path        Query String   Fragment
```
*(Параметрите са извлечени от).*

Комуникацията се състои от два текстови пакета:

### 📥 1. Структура на сурова HTTP Заявка (Request):
```text
POST /demo/index.php HTTP/1.1                <── [Request Line: Метод, Път, Версия]
Host: mysite.com                             <── [Headers: Метаданни / Указания]
Content-Type: application/json
                                             <── [Задължителен празен ред!]
{ "id": 27, "lang": "en" }                   <── [Body: Полезен товар / JSON данни]
```

### 📤 2. Структура на суров HTTP Отговор (Response):
```text
HTTP/1.1 200 OK                              <── [Status Line: Версия, Статус код]
Content-Type: application/json
                                             <── [Задължителен празен ред!]
{ "status": "success" }                      <── [Body: Върнати данни от C#]
```

## 4. ЕВОЛЮЦИЯ НА ПРОТОКОЛА: HTTP/1.1 СРЕЩУ HTTP/2 И HTTP/3

Това е фундаментална напреднала подточка от презентацията, която описва как се променя софтуерната скорост в интернет:

### А. Старият HTTP/1.1 стандарт
*   Работи изцяло в текстов формат. За всяка отделна снимка или CSS файл на сайта браузърът е длъжен да отваря **нова, самостоятелна TCP връзка** по мрежата, което води до огромно забавяне и претоварване на сървъра Kestrel.

### Б. Модерният HTTP/2 стандарт (Индустриален закон)
*   Преминава изцяло към бинарни софтуерни рамки (Binary data frames). Въвежда три революционни архитектурни фичъра:
    1.  **Multiplexing (Мултиплексиране):** Позволява пренос на десетки различни файлове (снимки, кодове) едновременно **само по една-единствена споделена TCP връзка**, премахвайки чакането.
    2.  **Header Compression (HPACK):** Поддържа специална „свързваща таблица“ (Header Table) между заявките. Вместо да изпраща дълги еднакви текстови метаданни всеки път, той прави дедупликация в паметта и пренася само новите промени.
    3.  **Server Push:** Бекенд сървърът Kestrel може автономно да изпрати критични CSS/JS файлове към браузъра на клиента, **преди той изобщо да ги е поискал**, ускорявайки зареждането.

### В. Бъдещият HTTP/3 стандарт
*   Изхвърля изцяло TCP протокола поради системни забавяния. Преминава изцяло над **UDP средите**, използвайки новия свръхбърз облачен протокол **QUIC**, осигуряващ незабавна връзка без първоначални мрежови ръкостискания (Handshakes).

## 5. СРИВОВЕ В МРЕЖАТА: ЧЕСТИ ГРЕШКИ, ЕКСПЕШЪНИ И КОРЕКЦИЯ

### 🚨 Капан №1: Зает или грешен Порт (Port Collision)
*   **Какво се случва:** Стартираш твоето уеб приложение, но си оставила друго приложение да работи на същия порт (напр. порт `5001`).
*   **Точен софтуерен Crash в конзолата при стартиране:**
    ```text
    IOException: Failed to bind to address https://127.0.0.1:5001: address already in use.
    ```
*   **Как да го избегнеш:** Отвори файла `Properties/launchSettings.json` и промени цифрата на порта на напълно произволна свободна стойност (напр. `7214`).
