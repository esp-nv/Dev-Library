## 1. АНАТОМИЯ НА HTTP КОНВЕЙЕРА (THE REQUEST PIPELINE)

В ASP.NET Core уеб сървърът **Kestrel** приема входящата HTTP заявка и я изпраща по затворен софтуерен тръбопровод, наречен **Request Pipeline**. Този тръбопровод е изграден от отделни малки софтуерни блокове, наречени **Middleware (Междинен софтуер)**.

Всеки Middleware компонент има точно две задачи:
1.  **Преди изпълнението:** Може да прегледа, промени или филтрира входящата заявка, след което да я предаде на следващия компонент по веригата чрез извикване на делегата `next()`.
2.  **След изпълнението:** Когато заявката стигне до края (Контролера) и се генерира отговор, потокът се връща **обратно по същия път в огледален ред**. Всеки Middleware може да промени изходящия HTTP отговор, преди той да напусне сървъра към браузъра на клиента.

```text
   HTTP Request  ──> [ Middleware 1 ] ──(next)──> [ Middleware 2 ] ──(next)──> [ Контролер / API ]
                           │                                  │                        │
   HTTP Response <── [ Логване / Екшън ] <─────────── [ Валидация ] <──────────────────┘
```

> **Късо съединение (Short-circuiting):** Даден Middleware може да прецени да **НЕ** извика `next()`. Тогава конвейерът прекъсва внезапно и отговорът се връща веднага. Пример: Ако `AuthMiddleware` открие, че потребителят няма права, той блокира заявката и мигновено връща статус `401 Unauthorized`, без изобщо да натоварва контролера или базата данни.

## 2. ХРОНОЛОГИЧЕН РЕД НА СИСТЕМНИТЕ MIDDLEWARE КОМПОНЕНТИ

В ASP.NET Core **редът на регистриране на Middleware компонентите в `Program.cs` е закован**. Ако объркаш местата на два компонента, приложението ти или ще изтече данни, или ще спре да работи правилно.

Ето златния архитектурен ред, по който се подрежда софтуерният тръбопровод:

```csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

// 1. Глобален улавящ слой: Хваща абсолютно всички необработени изключения напред по веригата
if (app.Environment.IsDevelopment()) { app.UseDeveloperExceptionPage(); }
else { app.UseExceptionHandler("/Home/Error"); }

// 2. Сигурност на мрежата: Пренасочва HTTP заявките автоматично към HTTPS порт
app.UseHttpsRedirection();

// 3. Статични файлове: Връща директно снимки, CSS и JS файлове от /wwwroot, без да натоварва C# кода нагоре
app.UseStaticFiles();

// 4. Маршрутизация: Разглобява URL адреса и разбира кой Контролер трябва да се извика
app.UseRouting();

// 5. Корпоративна защита (CORS): Дефинира кои външни сайтове/фронтенд домейни имат право да викат това API
app.UseCors();

// 6. Аутентификация: Проверява "Кой си ти?" (Разчита JWT токени или бисквитки)
app.UseAuthentication();

// 7. Авторизация: Проверява "Имаш ли право да правиш това?" (Проверява роли и политики)
app.UseAuthorization();

// 8. Финална спирка: Изпълнява реалния код вътре в твоите Контролери (Endpoints)
app.MapControllers();

app.Run();
```

## 3. ИМПЛЕМЕНТИРАНЕ НА КЪСТЪМ MIDDLEWARE: РЪЧЕН КОД И ИЗПОЛЗВАНЕ НА USE

За да регистрираме наше собствено Middleware правило директно в конвейера, използваме метода **`app.Use(...)`**. Той ни дава пълен достъп до текущия `HttpContext` и до делегата `next`.

Например, искаме да напишем Middleware, който проверява дали в заглавките (Headers) на входящата заявка пристига специален таен ключ `X-App-Secret`.

### 📄 1. Софтуерен код (в Program.cs):
```csharp
app.Use(async (context, next) =>
{
    // 1. Действие ПРЕДИ следващия Middleware: Проверяваме заглавната част
    if (!context.Request.Headers.TryGetValue("X-App-Secret", out var extractedSecret) 
        || extractedSecret != "SystemSuperSecret123")
    {
        // КЪСО СЪЕДИНЕНИЕ: Блокираме заявката, не викаме next() и връщаме 401
        context.Response.StatusCode = StatusCodes.Status401Unauthorized;
        context.Response.ContentType = "text/plain; charset=utf-8";
        await context.Response.WriteAsync("Грешка: Невалиден или липсващ секретен системен ключ!");
        return; 
    }

    // Извикваме следващия Middleware по веригата
    await next();

    // 2. Действие СЛЕД изпълнението на Контролера (на връщане): Дописваме лог
    Console.WriteLine($"[LOG] Заявката се завърна успешно със статус: {context.Response.StatusCode}");
});
```

### 🎯 2. Очакван изход (Expected Output в Postman) при ГРЕШЕН ключ:
Ако изпратиш `GET` заявка към произволен адрес без правилната заглавна част, Postman веднага ще прихване следния сигурен отговор:
```text
Status: 401 Unauthorized
Грешка: Невалиден или липсващ секретен системен ключ!
```

## 4. СИСТЕМНИ КАПАНИ: ГРЕШКИ ПРИ "КЪСО СЪЕДИНЕНИЕ" И ЛИПСВАЩ AWAIT

Неправилното управление на асинхронните нишки вътре в уеб конвейера води до тежки системни изключения.

### 🚨 Капан №1: Забравен `await next()` (Принудителна тапа)
*   **Какво правиш:** Пишеш къстъм Middleware за логване на IP адреси, но в края на софтуерния блок забравяш да извикаш `await next();`.
*   **Очакван изход в браузъра на клиента:** Страницата замръзва напълно бяла. Контролерите ти никога не се изпълняват, въпреки че в конзолата няма хвърлено червено изключение.
*   **Защо се случва:** Понеже не си извикала следващото звено по веригата, ти неволно си предизвикала „късо съединение“ и си превърнала твоя софтуерен блок в терминален Middleware (`Run`), затваряйки тръбопровода.
*   **Как да го поправиш:** Винаги подсигурявай присъствието на `await next();` във всеки логически клон, който не трябва да блокира трафика.

### 🚨 Капан №2: Модификация на Headers след като отговорът вече е тръгнал (Status 200 Crash)
*   **Какво правиш:** Опитваш се да добавиш нова заглавна част към HTTP отговора, но поставяш кода **СЛЕД** извикването на `await next();`.
    ```csharp
    await next(); // Контролерът се изпълнява и изпраща данните към браузъра
    context.Response.Headers.Add("X-Custom-Header", "Value"); // ❌ ГРЪМВА ТУК!
    ```
*   **Точен софтуерен Crash (Exception Message) в конзолата на Kestrel:**
    ```text
    InvalidOperationException: Headers are read-only, response has already started.
    ```
*   **Защо се случва:** Когато конвейерът се връща обратно и стигне до твоето правило, софтуерният пакет вече е физически изпратен по мрежата към клиента. Браузърът е получил статус `200 OK` и заглавните части са станали заключени само за четене (`read-only`).
*   **Как да го поправиш:** Всички промени и дописвания на Headers по HTTP отговора трябва да се извършват **ПРЕДИ** да извикаш `await next();`, или да се закачат към събитието `OnStarting`:
    ```csharp
    context.Response.OnStarting(() => {
        context.Response.Headers.Add("X-Custom-Header", "Value");
        return Task.CompletedTask;
    });
    await next();
    ```
