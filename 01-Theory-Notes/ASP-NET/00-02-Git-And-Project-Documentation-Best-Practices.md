## 1. ЗАЩО GIT Е ЗАДЪЛЖИТЕЛЕН: ПРОБЛЕМИТЕ, КОИТО РЕШАВА

Софтуерните проекти се променят непрекъснато и се разработват съвместно от много хора. Без система за управление на версиите (VCS), екипите страдат от необратимо презаписване на файлове, липса на исторически контекст, липса на ясна отчетност за промените и невъзможност за сигурен заден ход (Rollback).

### ⚖️ Сравнителен анализ: Git срещу GitHub

| Критерий | Git (Локален Двигател) | GitHub (Облачна Платформа) |
| :--- | :--- | :--- |
| **Основна Роля** | Проследява промените в софтуерния код под формата на хронологични снимки (Snapshots). | Хоства отдалечени Git хранилища и предоставя инструменти за екипна работа. |
| **Къде работи?** | Директно на твоята машина, напълно офлайн. | В облака на Microsoft сървърите, изисква интернет. |
| **Управление** | Използва локална скрита папка `.git` („мозъкът“ на проекта). | Използва уеб интерфейс, Pull Requests за Code Review и роли. |

* **Архитектурен компромис (Trade-off):** Git ти дава пълна скорост и автономност локално в паметта, но изисква отдалечена централна платформа (като GitHub), която да служи за „Единствен източник на истината“ (Single Source of Truth) при екипна интеграция.

## 2. АНАТОМИЯ НА ПРОФЕСИОНАЛНИЯ COMMIT (АТОМАРНОСТ И КУЛТУРА)

Всеки **Commit** представлява официално записано състояние на целия проект в локалната история, придружено от уникален 40-символен идентификатор (SHA-1 Hash), автор, времеви отпечатък и съобщение. Твоята Git история описва мисловния ти процес и е техническото ти резюме пред работодателите.

### 🟢 Правило за Атомарност (Atomic Commits):
Всеки commit трябва да съдържа точно **една логическа промяна или фичър**. 
*   **Тестът "И":** Ако коммит съобщението съдържа думата "и" (напр. `git commit -m "Fix header CSS and update database schema"`), това означава, че промените трябва да бъдат разделени в два отделни коммита.
*   **Правило на Видео играта:** Приемай коммитите като контролни точки (Checkpoints). Коммитвай винаги преди тежък рефакторинг или рискова промяна, за да имаш право на незабавно спасително връщане.

```text
 ❌ ИЗБЯГВАЙ (Mystery Timeline):   "update" ──> "fix bug" ──> "stuff"
 🟢 ИЗБИРАЙ (Professional History): "Add Movie entity" ──> "Fix validation in Create action"
```

## 3. ПРОФЕСИОНАЛНА ASP.NET СТРУКТУРА И РОЛИ НА ФАЙЛОВЕТЕ

Един правилен ASP.NET проект съдържа папки за слоевете (`/Controllers`, `/Models`, `/Views`) и статична папка `/wwwroot`. В корена обаче живеят три критични компонента:
*   **`.sln` (Solution файл):** Свързва подпроектите на едно място.
*   **`appsettings.json`:** Пази базовите конфигурации. **Железен закон:** Ръчното хардкодване на производствени пароли и API ключове вътре в него е абсолютно забранено, за да не изтекат публично в GitHub.
*   **`.gitignore` — Филтърът за почистване:** Казва на Git кои служебни файлове и директории да игнорира, за да не се запълва хранилището с излишен боклук.

### 🛠️ Задължителен .NET списък за изключване в `.gitignore`:
```text
# Компилиран софтуерен код (Build Artifacts)
bin/
obj/

# Специфични настройки на редакторите (IDE Settings)
.vs/
.vscode/
*.user

# Локални файлове с производствени тайни
secrets.json
appsettings.Development.json
```

## 4. ЗЛАТНИЯТ README.MD СТАНДАРТ (ЛИЦЕТО НА ПРОЕКТА)

Файлът **`README.md`** е уводната страница на твоето софтуерно хранилище в GitHub. Проект без документация се счита за незавършен и непрофесионален.

### 🧭 Чеклист за 5-те задължителни компонента на README:
1.  **Project Title:** Изчистено, техническо и ясно име (напр. `MovieRental - ASP.NET Core MVC Portal`).
2.  **Description:** Какъв реален бизнес проблем решава това уеб приложение и за кои крайни потребители е създадено.
3.  **Tech Stack:** Подробен списък с дефинирани версии на езиците и библиотеките (*.NET 8.0, EF Core, SQL Server, AutoMapper*).
4.  **Setup Instructions:** Кратко и точно ръководство стъпка по стъпка как друг колега програмист да стартира проекта локално:
    ```bash
    git clone https://github.com
    dotnet restore
    dotnet ef database update
    dotnet run
    ```
    *(Инструкциите съответстват на).*
5.  **User Roles & Permissions:** Дефиниране на правата (напр. *Guest* – преглежда, *User* – купува, *Admin* – управлява).

## 5. СИСТЕМНИ КАПАНИ: ГРЕШКИ ПРИ СИНХРОНИЗАЦИЯ И КАК ДА ГИ ПОПРАВИМ

При съвместна работа в GitHub или при качване на проекти, най-честите мрежови сривове са следните:

### 🚨 Капан 1: Конфликт при изтласкване (Merge Conflict / Rejected Push)
*   **Какво правиш:** Променяш код по проекта, правиш локален коммит и пишеш `git push`. В същия момент твой колега вече е качил негови промени в GitHub преди теб.
*   **Точно съобщение за грешка в конзолата на Git:**
    ```text
    error: failed to push some refs to 'https://github.com... .git'
    hint: Updates were rejected because the remote contains work that you do
    hint: not have locally. Anyhow, 'git pull' first before pushing again.
    ```
*   **Защо се случва:** GitHub блокира твоя ход, защото твоята локална история няма запис за промените на колегата ти. Нарушава се синхронизацията на „източника на истината“.
*   **Как да го поправиш (Златното правило на програмиста):** **Pull преди Push**! Първо изпълни `git pull`, за да изтеглиш промените на колегата си локално, разреши конфликтите в кодовите редове, ако има такива, направи нов коммит и чак тогава изтласкай сигурно с `git push`.

### 🚨 Капан 2: Качване на излишен боклук в GitHub (Срив без .gitignore)
*   **Какво правиш:** Започваш нов проект, но забравяш да създадеш файл `.gitignore` в корена на папката. Изпълняваш `git add .` и изтласкваш проекта.
*   **Очакван лош изход в GitHub:** В твоя онлайн профил се появяват хиляди служебни компилирани файлове от папките `bin/` и `obj/`. Проверяващият вижда хаос, а тегленето на проекта се забавя драстично.
*   **Как да го поправиш:**
    1. Не трий папките ръчно. Създай веднага файл `.gitignore` с нужните правила.
    2. Изпълни следните команди в терминала, за да изчистиш кеша на Git, без да триеш реалния си код:
       ```bash
       git rm -r --cached bin/
       git rm -r --cached obj/
       git commit -m "Remove build artifacts from tracking using gitignore"
       git push
       ```
