## 1. ЗАЩО GIT Е ЗАДЪЛЖИТЕЛЕН: ПРОБЛЕМИТЕ, КОИТО РЕШАВА

В модерната софтуерна разработка проектите се променят постоянно и се пишат от големи екипи [Git, 5]. Без система за контрол на версиите (Version Control System - VCS) като **Git**, екипите се сблъскват с фатални проблеми: неволно презаписване на файлове, липса на хронологична история, невъзможност за сигурен заден ход (Rollback) при грешка и хаос при екипна работа [Git, 6, 7].

### Ключево разграничение: Git срещу GitHub [Git, 7, 8]
*   **Git:** Софтуерният инструмент (двигателят), който работи локално на твоя компютър и записва хронологичните промени по кода под формата на моментни снимки (Snapshots) [Git, 7, 8, 13].
*   **GitHub:** Облачна хостинг платформа (хранилище), която пази отдалечено копие на твоя Git проект и служи за споделяне, съвместна работа и преглед на кода (Pull Requests) [Git, 8, 20].

## 2. АНАТОМИЯ НА ПРОФЕСИОНАЛНИЯ COMMIT (АТОМАРНОСТ И КУЛТУРА)

Всеки **Commit** е официален спасителен чекпоинт (Checkpoint) в паметта на твоя проект [Git, 13, 17]. Той съдържа уникален 40-символен идентификатор (SHA-1 Hash), информация за автора и текстово съобщение, описващо промяната [Git, 13, 14].

### ⚖️ Good vs. Bad Commits [Git, 15]:
*   **Лоша практика (Mystery Commit):** Съобщения като `git commit -m "update"`, `git commit -m "fix bug"` или `git commit -m "stuff"` са напълно безполезни за проследяване след време [Git, 15].
*   **Професионален стандарт (Documentation Commit):** Използвай ясни, императивни съобщения: `git commit -m "Add Movie entity"`, `git commit -m "Configure EF Core DbContext"` [Git, 15].

> **Тестът "И" за Атомарност (Atomic Commits):** Всеки commit трябва да съдържа само една логическа промяна или фичър [Git, 16]. Ако твоето съобщение съдържа думата "и" (напр. *"Fix header CSS and update database schema"*), това е ясен знак, че трябва да разбиеш промените в **два отделни, самостоятелни коммита** [Git, 16].

## 3. ПРОФЕСИОНАЛНА ASP.NET СТРУКТУРА И РОЛИ НА ФАЙЛОВЕТЕ

Един правилно структуриран ASP.NET уеб проект съдържа папки за архитектурните слоеве (`/Controllers`, `/Models`, `/Services`, `/DTOs`) и папка `/wwwroot` за статични уеб ресурси (CSS, JS) [Git, 21]. В корена на проекта обаче стоят три критични файла, които управляват Git жизнения цикъл:

1.  **`.sln` (Solution File):** Главният входен пункт, който обединява всички подпроекти [Git, 21].
2.  **`appsettings.json`:** Основният конфигурационен файл. **Критично правило:** Никога не качвай реални пароли и производствени тайни (Secrets) вътре в него [Git, 21, 22].
3.  **`.gitignore` — Филтърът за чист код:** Специален текстов файл, който казва на Git кои папки са служебни и трябва да бъдат напълно игнорирани при запис [Git, 21, 22].

### 🛠️ Задължителни .NET изключения вътре в `.gitignore` [Git, 21, 22]:
```text
# Генерирани папки при компилация (Build Artifacts)
bin/
obj/

# Специфични настройки на средите за разработка (IDE Settings)
.vs/
.vscode/
*.user

# Конфигурационни файлове, съдържащи пароли и тайни
secrets.json
```

## 4. ЗЛАТНИЯТ README.MD СТАНДАРТ (ЛИЦЕТО НА ПРОЕКТА)

Файлът **`README.md`** (написан на Markdown език) е „предната врата“ на твоето софтуерно хранилище [Git, 21, 29, 30]. Проект без детайлен README файл се счита за незавършен на професионално ниво [Git, 25]. Той дава бърз технически контекст на проверяващите софтуера инженери и разяснява бизнес целта на приложението [Git, 29, 30, 32].

### 🧭 5-те задължителни компонента на едно софтуерно README [Git, 31]:
*   **Заглавие на проекта (Project Title):** Ясно, описателно и техническо име [Git, 31].
*   **Описание (Description):** Какъв реален бизнес проблем решава това приложение и за кои потребители е предназначено [Git, 31, 32].
*   **Технологичен стек (Tech Stack):** Специфичен списък с използваните версии на рамките (напр. *.NET 8.0, EF Core, SQL Server, AutoMapper*) [Git, 31, 33, 34].
*   **Инструкции за инсталация (Setup Instructions):** Ръководство стъпка по стъпка как един непознат програмист да клонира проекта, да обнови връзките, да изпълни миграциите (`dotnet ef database update`) и да стартира кода локално за секунди [Git, 31, 35, 36].
*   **Потребителски роли и права (Usage & Permissions):** Спецификация на правата в уеб системата (напр. *Guest* – разглежда, *User* – наема, *Admin* – контролира наличностите) [Git, 31, 37].
