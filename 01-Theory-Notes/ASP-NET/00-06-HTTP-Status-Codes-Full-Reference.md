## 1. КАКВО ПРЕДСТАВЛЯВАТ HTTP СТАТУС КОДОВЕТЕ И КЪДЕ ЖИВЕЯТ?

Всеки път, когато уеб браузърът (Client) или Postman извика уеб адрес, сървърът Kestrel обработва заявката и е длъжен да върне трицифрено число в първия ред на своя софтуерен отговор (`Status Line`). Това число казва на клиента какво се е случило под капака с неговите данни, без да се налага браузърът да чете и парсва дълги текстови съобщения.

В ASP.NET Core имаш два начина да викаш тези кодове:
1.  **Чрез вградени методи (Helper Methods):** Наследени от класа `Controller` (напр. `Ok()`, `BadRequest()`).
2.  **Чрез служебния клас `StatusCodes`:** Част от библиотеката `Microsoft.AspNetCore.Http`, съдържащ твърди константи (напр. `StatusCodes.Status201Created`). **Това е индустриалният стандарт за чист код!**

## 2. КАТЕГОРИИ И СПРАВОЧНИК: ЗНАЧЕНИЕ И БИЗНЕС УПОТРЕБА

Кодовете са разделени логически на пет цифрови стотици в зависимост от тяхното значение:

### 🟢 2xx Success (Успешни операции)
*   **`200 OK`** ➔ *Употреба:* Стандартен успех за `GET` или `PUT` заявки. Казва: *"Данните бяха намерени или обновени и ти ги изпращам"*.
*   **`201 Created`** ➔ *Употреба:* Златен стандарт за `POST` заявки. Казва: *"Ресурсът беше успешно записан на диска"*. Задължително връща локация на новия обект.
*   **`204 No Content`** ➔ *Употреба:* Използва се за `DELETE` операции. Казва: *"Заявката премина успешно, изтрих обекта, затова няма какво повече да ти върна като тяло"*.

### 🟡 3xx Redirection (Пренасочване)
*   **`301 Moved Permanently`** ➔ *Употреба:* Адресът на сайта е сменен завинаги. Браузърът кешира новия адрес и не търси стария.
*   **`302 Found / Temporary Redirect`** ➔ *Употреба:* Временен пренасочващ ход (напр. потребителят се опитва да отвори кошницата, но не е влязъл в профила си ➔ сървърът го пренасочва временно към страницата за Login).

### 🟠 4xx Client Errors (Грешки от страна на Клиента/Браузъра)
*   **`400 Bad Request`** ➔ *Употреба:* Срив в сигурността на данните. Казва: *"Изпратил си ми невалиден JSON, празни задължителни полета или букви вместо числа. Поправи формите си!"*.
*   **`401 Unauthorized`** ➔ *Употреба:* Клиентът е непознат за софтуера. Липсва или е изтекъл криптираният JWT токен или сесийна бисквитка.
*   **`403 Forbidden`** ➔ *Употреба:* Клиентът е познат, влязъл е в профила си, но няма администраторска роля или бизнес права за тази папка.
*   **`404 Not Found`** ➔ *Употреба:* Опит за търсене по ID, което не съществува в SQL Server (напр. няма продукт с `Id = 9999`).

### 🔴 5xx Server Errors (Фатални сривове в C# кода на Сървъра)
*   **`500 Internal Server Error`** ➔ *Употреба:* Твоят C# код е хвърлил необработен ексепшън зад кулисите (напр. `NullReferenceException` или делене на нула).
*   **`503 Service Unavailable`** ➔ *Употреба:* Kestrel сървърът е претоварен, няма свободни нишки в пула или базата данни е изключена напълно.

## 3. ПРАКТИЧЕСКИ C# ПРИМЕР: КАК ДА ВИКАМЕ КОДОВЕТЕ В КОНТРОЛЕРА

Ето как се реализира сигурно извикване на пет различни статус кода в рамките на един класически бизнес контролер:

```csharp
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Mvc;

public class ProductDto
{
    public int Id { get; set; }
    public string Name { get; set; } = null!;
}

[ApiController]
[Route("api/v1/store")]
public class StockController : ControllerBase
{
    // 1. ВРЪЩАНЕ НА 201 CREATED И 400 BAD REQUEST
    [HttpPost("create-item")]
    public IActionResult CreateItem([FromBody] ProductDto dto)
    {
        if (!ModelState.IsValid)
        {
            return BadRequest(ModelState); // ➔ SQL: Връща 400 Bad Request
        }

        // Логика за запис в базата...
        dto.Id = 105; 

        // Връщаме 201 Created, линк за достъп и новия обект
        return CreatedAtAction(nameof(GetItemById), new { id = dto.Id }, dto);
    }

    // 2. ВРЪЩАНЕ НА 200 OK И 404 NOT FOUND
    [HttpGet("item/{id}")]
    public IActionResult GetItemById([FromRoute] int id)
    {
        if (id == 999)
        {
            // Симулираме, че продуктът липсва в SQL Server
            return NotFound(new { Message = \$"Продукт с ID {id} не съществува!" }); // ➔ Връща 404
        }

        var product = new ProductDto { Id = id, Name = "Ударна Бормашина" };
        return Ok(product); // ➔ Връща 200 OK
    }

    // 3. ВРЪЩАНЕ НА 204 NO CONTENT (Успешно изтриване)
    [HttpDelete("item/delete/{id}")]
    public IActionResult DeleteItem([FromRoute] int id)
    {
        // Логика за триене...
        
        // Връщаме 204 No Content - обектът е изтрит, няма тяло за четене
        return StatusCode(StatusCodes.Status204NoContent); // ➔ Връща 204
    }
}
```

## 4. СИСТЕМНИ КАПАНИ: ГРЕШНА УПОТРЕБА НА СТАТУСИ И ПОСЛЕДСТВИЯ

Объркването на статусите може да парализира работата на уеб фронтенда.

### 🚨 Капан №1: Връщане на `200 OK` при бизнес грешка (Анти-патерн "Лъжец")
*   **Какво правиш:** Когато потребителят въведе празна парола, вместо да върнеш статус `400 BadRequest`, ти написваш следния код:
    ```csharp
    // ❌ ТЕЖЪК АНТИ-ПАТЕРН:
    return Ok(new { Error = "Името е задължително!" }); 
    ```
*   **Защо е опасно:** Фронтенд библиотеки (като Axios или Angular HttpClient) проверяват само трицифрения статус. Тъй като виждат `200 OK`, те приемат операцията за напълно успешна, пропускат блоковете за грешки (`.catch()`) и се опитват да вкарат невалидните данни в уеб екрана, сривайки интерфейса на клиента.
*   **Как да го избегнеш:** Винаги използвай `BadRequest(ModelState)` или изрични статус кодове при неуспех.
